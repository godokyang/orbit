## 目标与理由

从[Orbit 核心诉求](../reference/codex-source-lessons-20261009.md#从-orbit-的诉求筛选而不是从-codex-的功能清单排期)出发，上下文处理要让执行者和检查者得到当前任务所需的有效信息，减少遗忘、误判和重复读取，并控制监督开销。压缩质量取决于保留的信息能否支持正确下一动作与核验，不能以字数最少为目标。

本项让独立检查收到的测试输出和故障日志，在现有长度约束内同时保留执行开头与失败结尾，减少单纯保留前缀丢失错误总结的风险。该风险来自当前裁剪方式的源码对照，本次没有新增真实漏检现场，也未证明费用或质量收益。首尾保留主要是同等容量内的证据质量改进，不预设总输入 token 一定下降。

来源：[Codex 源码研究 §6](../reference/codex-source-lessons-20261009.md#6-上下文按模型容量裁剪长日志保留首尾)。借鉴的是确定性的内容保留策略，在 Orbit 现有压缩器上作局部增量。

## 当前实现与边界

[CheckRunner](../../lib/orbit/check_runner.rb) 已将检查输入中的程序上下文限制在 65,536 bytes，按确定性顺序降级。通用长字符串保留前缀，并附原始字符长度和 SHA-256；原始要求、有效修订与命名依据另列，保持原文。当前执行验证回执有版本匹配与优先保留规则，失败或 unknown 不因压缩变成成功。

64 KiB 是程序上下文的字节上限，不是完整模型请求的 token 上限。完整请求还包含要求、依据、工具定义及后续工具读取结果。宿主或回执采集层可能已裁剪日志，最终输入压缩器无法恢复此前丢失的尾部。

实施准备补核：当前 [root-verifications.mjs](../../plugins/root-verifications.mjs) 的 `boundedText` 在采集 bash/eval 输出时先按 `TEXT_CAP=4000` 的 JS 字符串长度裁掉尾部；command/script 也使用此 helper。Ruby `build_compressed_context` 随后再经 `bound_value/bound_string` 保留前缀。C01 必须处理这两个实际投影点的日志输出，不能只改 Ruby，也不能把同一个 helper 的所有字段一并改写。具体依赖、验收与总清单见[实施依据 §3](codex-lessons-implementation.md#3-c01-可直接实施的接缝与验收)。

现行任务语义仍由[任务运行合同](../../contracts/task-runtime.md)及 ADR-008/009 定义；此方案记录待实施方向，不声明已有产品能力。

## 上下文的三条路径

| 路径 | 当前责任与本次借鉴边界 |
| --- | --- |
| 检查者的程序上下文 | Orbit 按既有 64 KiB 规则投影状态与证据；本项只改选定日志的内容保留策略，原要求/修订/依据仍单独提供 |
| Root/成员的会话历史 | 历史压缩与 provider 请求由 OMP 承担；核对压缩后有效目标、授权阶段与未完成事项的注入，不在 Orbit 再造通用会话压缩器 |
| 成员交接材料 | 现有工作单元提供必要目标、决定、输入、权限和验收；按任务需要提供材料，完整历史继承须另核对宿主能力与重复输入开销 |

历史摘要不能取得新授权，旧状态不能替代当前事实；完整目标持续保存与在当前请求中投影必要信息分别处理。首尾保留解决第一条路径的局部证据问题，不单独解决所有遗忘或防偏航问题。后两条路径的评估见[工作机制研究](../reference/codex-workflow-alignment-20261009.md)，本项不扩展到它们的实现。

## 已确认先落文档的局部范围：长日志首尾保留

实施前沿测试/故障日志从原生工具结果、回执采集到检查输入核对实际受测版本，确认已定位两处投影及上游可见内容。优先使用已有 `root_verifications.output` 等可明确识别的执行输出；新增目标字段必须有实际调用来源，不仅凭任意字符串看起来像日志就套用。

对选定的日志字段：

1. 未超过已有字段限额时保持原文；超过时确定性保留首部和尾部，最小方案使用均分的正文预算。
2. 中间明确标记省略，并携带处理前可见内容的长度与摘要；字符数与字节数分别明确单位，不能把上游已裁剪的片段标成完整原生输出。
3. 为标记预留空间，最终按既有字段限制及完整程序上下文字节上限核对，避免标记额外撑大输入；中文、Unicode 等文本裁剪后保持有效编码。
4. 保留原有来源、tool call ID、退出码及其来源、输入/产物版本匹配标记。已有截断事实继续显式表达；尾部文本不能替代结构化执行结果，也不能据日志总结推断成功。
5. 有更早裁剪时，在首次可控制的日志投影处保留首尾，再进入现有检查输入压缩流程；只改本项实际涉及的裁剪点，避免反复裁剪挤掉保留内容。

原始要求、有效修订、依据、权限声明、finding 和 Root 交付正文继续沿现有专门策略处理。本轮真实降级发现普通字段预算125字符小于日志省略标记；Ruby仅日志output采用最低500字符空间，原最高2000字符和整体65536bytes硬上限不增，其他字段继续降级，无法容纳则显式省略全记录。

此次不把通用 `bound_string` 的所有调用统一改成首尾模式，也不提高程序上下文总上限。

## 首项验收条件

| 场景 | 可观察结果 |
| --- | --- |
| 一次长测试输出的开头含执行信息，结尾含失败总结 | 实际送给检查者的程序上下文同时包含两端，并明确表示中间有省略 |
| 普通短输出 | 内容保持原文，来源与执行结果不变 |
| 多份日志使程序上下文进入降级 | 最终 JSON 可解析且不超过现有 64 KiB 上限；现有裁决事实保留与省略规则仍成立 |
| 日志来自已截断或旧版本回执 | 明示可见范围与既有截断/版本事实，不将旧回执或日志文字提升为当前通过证据 |

复用[现有上下文测试](../../tests/check_runner_context_test.rb)，只为日志尾部保留、总大小约束和证据归属的真实回归风险补少量场景。本轮实施先运行相关已有测试；真实路径使用隔离项目的代表性工具输出核对实际检查输入，区分确定性通过、真实读取事实与模型判断结果。历史文档阶段未新增测试或调用模型；本轮实际模型验收见[验收记录](../reference/codex-lessons-acceptance-20261009.md)。

## 后续待评估：模型容量感知

先取得实际请求构成和可核实的执行路由 context window，核算原文、依据、工具定义、程序上下文与输出预留；后续工具读取也需计入容量压力。模型目录的容量不直接当作实际路由限制，容量未知时保留现有确定性限制并明确未知。

只有这些事实足以说明当前固定字节限额的实际问题时，再决定是否调整预算。原始要求超容量时报告真实缺口，不能静默以生成摘要替代。不得为了容纳输入降低权限、独立性或整体要求覆盖门。

本项不新增模型摘要系统、token 预测平台或预算硬门，也不因为 Codex 有容量适配就默认把它列为下一批实施。现有字段投影足以解决日志信息丢失时，保留局部方案。

## 效果观察与范围控制

先验证选定日志的实际两端、来源、版本和既有大小约束，关键结果是检查输入保留了有用失败信息，且没有损坏裁决事实或增加误报。复用现有记录观察后续读取、判断和可得用量，不要求这个局部裁剪改动先完成一套经济对照或证明模型普遍可靠。

若要宣称减少漏检或节省资源，再对同类交付要求与同一检查范围比较实际结果、人工介入及可归属用量；没有比较就只报告实际事实。顶级模型、其他模型和现金分别记录；更短的输入不必然减少后续读取或返工，首尾信息更完整也不能自动证明费用下降。
