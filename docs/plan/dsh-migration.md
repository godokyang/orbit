## 1. 背景

Orbit 现在以 OMP 为唯一宿主（ADR-008），Loom 经可信节点消费 Orbit 的集成合同。当前有两个限制：

- **对外暴露面窄**：OMP 经受控任务、原生 ask、停止、恢复、检查和外部引用被驱动；OMP 的 RPC 本来就推送事件，缺的是 Orbit 没有把它们做成公开投影、节点也没有常驻读取。Loom 的展示层因此只能轮询状态与少量可见文本。
- **宿主只能承载执行，不能承载界面**：OMP 是 RPC agent，没有可挂界面的插件宿主。Loom 必须自带一套 Web。

用户希望有一个统一宿主：既能当日常开发工具，也能承载 Loom 的界面；桌面、Web 与将来的手机端都由宿主外壳提供。

## 2. Loom 与 Orbit 各自解决什么问题

迁移之前先要保住两套思想。它们回答的是不同问题；合并或者让其中一套退化成另一套的字段，都会同时丢掉授权口径和执行核验。

### 2.1 Loom：项目的事实与授权账本

**它要解决的问题**：AI 已经能写代码，但使用者仍然回答不了四个问题——该做什么、做到哪了、能不能交付、谁批准了什么。

- 执行任务多，不等于项目前进；
- 模型说完成，不等于可验收；
- 代码合了，不等于业务目标达成；
- 换个人、换个会话，就要重新讲一遍背景。

**它的答案**：把项目当对象管理，而不是把对话当对象。

1. **结构**：目标 → 里程碑 → 交付项 → 验收标准。每条叶子必须可验证、有来源、有优先级、有依赖。
2. **授权**：范围要人确认；批准绑定具体方案、标准和版本；聊天、提交反馈、代码存在、合入都不能替代批准。
3. **进度**：实现进度与有效验收进度分开算；分母是已确认范围的权重；分母没有就显示未知，不填猜测值。代码量、提交数、任务条数和模型中间百分比都不算进度。
4. **完成**：实际成果 + 必要自检 + 逐标准的有效独立验收 + 约定交付事实。模型自述、Orbit 结束、Git 合入、测试通过，都不能单独等于业务完成。
5. **证据**：绑定目标/成果版本与真实来源；版本一变，旧结论要判有效性，不能自动沿用。
6. **人的位置**：只在关键点介入——批范围/方案、重要设计取舍、不可逆动作（发布、合入主线、删除数据、产生费用）、AI 判断不了的标准、返工后仍无法继续。
7. **持续复用**：同一项目后续工作复用已有目标、决定、交付项和有效证据，不要求使用者重讲背景。

**它刻意不做的事**：不跑模型、不持模型密钥、不执行 AI 循环，所有 AI 工作统一交给执行主体。这条边界不是能力不足，是证明结构：业务权威若与执行主体同体，“模型自述不算完成”就无法被证明。

**一句话**：Loom 回答“该不该做、算不算数”。

#### 不同的人看到什么

同一套界面，不同默认视角。不是三套产品，是三种第一屏。

| 视角 | 第一眼要看到 | 主要动作 | 不该被什么淹没 |
| --- | --- | --- | --- |
| 老板 | 目标日期、能不能按时、风险与卡点、等他拍板的事 | 看结论、处理决定 | 分支、日志、diff、任务条数 |
| 项目经理 | 今天该推什么、谁在等谁、范围变化影响哪些交付、阶段门卡在哪 | 调整范围、跟进需求与卡点 | 单个任务的实现细节 |
| 程序员 | 当前在做什么、卡在哪、证据和运行记录在哪 | 提缺陷、修复、看技术详情 | 项目层面的汇总与汇报 |
| 接入者 | 导入、环境、权限、验证条件是否齐 | 接入、补条件、处理卡住 | 业务取舍 |

原则：默认用业务语言；技术细节一步可展开；权限决定能看到哪些项目和数据。这几类人共用一套事实，只是默认视图不同——老板看到的是“能不能交付”，项目经理看到的是“该推哪一步”，程序员看到的是“现在卡在哪”。

### 2.2 Orbit：执行侧的监督与核验

**它要解决的问题**：coding agent 能干活，但不可靠。

1. 干到一半停了，不催就不动；
2. 说“做完了”，其实没验；
3. 用户纠正了几次，它还在按最早的做；
4. 全程一个贵模型，又慢又贵。

**它的答案**：在宿主 agent 外面加一层“受控任务 + 独立核验”，但把判断权留给 agent。

1. **单入口**：使用者只跟 Root 说话。Root 负责理解、分工、集成、纠偏和争议处理；成员不能再派成员，团队保持一层。
2. **程序只做事实**：保存用户原文与有效修订、拍工作区快照、向检查者提供真实材料入口、记录实际派发/模型/失败、执行停止并确认。程序不代替 agent 做技术判断，也不把未知自动解释成失败或必须由用户处理。
3. **独立检查**：检查者在另一个只读会话里，读固定快照和登记的材料，按用户要求逐项查证。它区分“尚未检查 / 缺必要证据 / 已发现缺陷”，不混着报。
4. **结论可沿用也可撤销**：同一要求前提未变时，已有有效结论可以沿用；出现新反证或证据失效则撤销。输入或产物变化后，旧结论只供检查者判断适用性，不自动授予当前版本完成资格。
5. **完成与停止分开**：`complete` 要求独立检查通过且实际执行确认停止；停止未确认就是 `stop_unconfirmed`，不冒充完成。
6. **JEV 判断**：入口、观察、分工、成员选型和检查选型由 JEV 按用途分别判断；执行者和检查者各有候选池；Root 始终使用启动会话的模型，保证集成一致性。见下文“JEV 不只是选模型”。
7. **事实留痕**：逐次记录实际模型、调用、失败、检查结果和停止状态；失败留证但不做成永久黑名单，也不从一次失败推断所有任务。

**它刻意不做的事**：不判断业务优先级、不确认范围、不替使用者做产品取舍。这些归 Loom。

**一句话**：Orbit 回答“真的做完了吗、做对没有、谁做的、停了吗”。

#### JEV 不只是选模型

JEV 是 Orbit 的外部判断服务（TypeSafe System One），按用途提不同问题；每类问题有独立的输入、问题集版本和校准门。

| 用途 | 问什么 | 输出怎么用 |
| --- | --- | --- |
| 入口 | 这条新请求要不要建立受控任务？ | 看执行授权、交接价值、监督价值三个概率；过阈值才建任务。明确讨论和概念问答不建 |
| 观察 | 任务卡住了吗？偏题了吗？ | 首次约 5 秒、之后每 5 分钟；看最近 20 条完整操作；可触发过程检查 |
| 分工 | 这个已声明的工作单元值得派吗？派给谁？ | 给 Root 提示，不自动派发 |
| 成员选型 | 哪个执行型号适合这个工作单元？ | 从执行者池选，按目标、要求、依赖和候选能力组织输入 |
| 检查选型 | 哪个检查型号适合这次终检？ | 从检查者池选，结合精确证据与目录先验；未放行只给事实和池序 |
| 材料组织 | 选型材料太长怎么办？ | 只为选型请求压缩，保留必保信息；缓存绑定原文版本 |

边界比“会选模型”更重要：

- 概率只用于**安排已有检查或提供选型依据**，不是问题证据、完成结论或停止授权。
- **不判断成果就绪**。这个职责被明确交还给 Root 和独立检查，JEV 不触发产物检查。
- 不自动派发成员，只给提示，Root 决定是否派。
- 失败返回 `unavailable`，不用部分答案触发动作；失败不当作低分。
- 判断 provider 与执行/检查模型是两件事，不能混用；判断用量与执行用量分别记账。
- 观察不因状态相同永久跳过，但检查在途时跳过、不补发。
- 用户的新指令、提问和纠正原文必须进 JEV；未登记为修订不能成为不传正文的理由。

这块在迁移里最容易丢：大家只记得“JEV 会选模型”，忘了它同时是入口门、卡点哨兵和分工参谋。只搬选型，等于把它的其他职责留在 OMP 上。

#### 入口门：为什么不是每条消息都建任务

Orbit 的流程是一套**长任务运行时**：建任务、拍快照、派执行成员、独立检查、每 5 分钟观察、确认停止。它有固定的启动成本，只有跑得久、步骤多的任务才摊得平。

问一句“1+1 等于几”，模型直接回答就行；启动 Orbit 流程却要拍快照、派检查、盯停止，开销远大于收益。所以入口门的第一作用是**算账**：这条消息值不值得进受控流程。

在这个基础上，它还要解决另外三件事：

1. **分清“说话”和“做事”**：提问、讨论方案、解释代码不建任务。建了就要派检查、拍快照、每 5 分钟观察，成本花在没有交付物的问题上。
2. **授权语义**：“帮我看看”不等于“授权你改并交付”。受控任务意味着记录、派发和完成门；误判就是把聊天当授权。
3. **状态诚实**：自动判断失败时明确标“本次未受 Orbit 监督”；显式要求受控时失败关闭。不沉默地假装被管。

注意“划算”不等于“短”。一行但高风险的改动（发版、删数据）仍然值得监督；很长但没交付物的讨论仍然不值得建任务。所以门判的是执行授权、交接价值、监督价值三个概率，不是消息长度。

**为什么用模型判断而不是规则**：规则会误伤（含“代码”的提问被当成任务），也会漏判（“把这个修了”很短但是任务）。所以用模型加阈值，只读当前用户原文，判断失败不重试，非 Git 工作区或截断请求不付费判断。阈值是执行授权 0.85、交接价值/监督价值 0.65，组合规则为“授权且两类价值任一过门”，并经过真实样本与 holdout 校准。

两个常被忽略的理由：

- **数据质量**：什么消息都建任务，账本里全是假任务；用这种账本做选型，学到的是噪声。任务边界干净是数据飞轮的第一步。
- **误判代价不对称**：误建任务可以停，成本可见；漏建是沉默的失守，用户以为被管了其实没有。所以显式要求必须诚实失败，自动候选可以降级但必须标注。

职责分离：入口只判“要不要建立受控边界”；建立之后，过程交给观察，结果交给独立检查。入口如果持续判断，会和观察重复、互相打架。

**迁移的问题**：DSH 的会话由外壳创建，没有 `before_provider_request` 这个同名钩子；但有 `agent/pre-step`，可以在拟进入步骤前拒绝或替换消息。迁移前必须先定“谁拥有入口判断”——会话创建时、第一条用户消息时，还是 orbit-core 显式开启。选错会让“自动接管”退化回“用户每次说请使用 Orbit”，或者粒度太粗：一个会话里先聊天后做事。

### 2.3 为什么必须是两个东西

| 问题 | 归谁 |
| --- | --- |
| 该做什么、范围多大、谁批准 | Loom |
| 做完没有、做对没有、用什么模型、停没停 | Orbit |
| 算不算项目进度 | Loom（消费 Orbit 的回执） |

两个原则：

1. **一个事实一个权威**：业务事实归 Loom，执行事实归 Orbit。Orbit 的 `complete` 不直接转成 Loom 完成。
2. **业务权威不能与执行主体同体**：所以 Loom 不跑模型，Orbit 不做业务判断。

这两条也是迁移的验收标准：换宿主可以，但不能把两套思想合并，也不能让其中一套退化成另一套的字段。

### 2.4 迁移要保住的清单

| 来自 | 必须保住 |
| --- | --- |
| Loom | 授权绑定版本；实现与验收分开计；证据可追溯、失效可判；人的介入点；业务权威独立于执行主体 |
| Orbit | 单入口；程序只记事实；独立只读检查；逐条结论；完成与停止分开；JEV 的入口、观察、分工与选型；事实留痕 |

DSH 提供的是承载这两套思想的新宿主，不是替代它们的新思想。任何一步迁移如果让上表中的某项失效，就等于换了产品，而不是换了底座。

## 3. 讨论中确认的事实

### 3.1 OMP 与 DSH 在 agent 层同类

两者都是成熟 coding agent，都跑同一批模型。差别不在 agent 能力，而在**宿主对外暴露什么**：

- OMP 经 Orbit 的窄合同被驱动；
- DSH 暴露 ACP/SDK 协议、事件溯源的会话与投影、客户端插件系统与多个外壳。

因此“换 DSH”不是“换个更强的 agent”，是“换一个愿意把内部事件和界面插槽给你的宿主”。

### 3.2 Loom 真正缺的是宿主暴露面

- DSH 会话是只追加的事件日志（`dsh-session`），`dsh-session-projection` 把派生状态以“快照 + 变更流”发给客户端。
- 客户端插件可占据 `main` 键位插槽（`ctx.layout.selectPanel`）；插件管理器本身就是默认组合里的全屏页。
- host 插件可注册 HTTP 路由、类型化 RPC、KV 存储，并订阅 `session/*` 事件。
- 分发：第三方插件是 npm 包，`dsh plugin add` 后在 profile 启用；host 代码在宿主进程内运行。

### 3.3 DSH 的多模型

- `dsh-llm-deepseek` 直连 DeepSeek；`dsh-llm-pi-ai` 可接 pi-ai 目录、OpenAI/Anthropic、任意 OpenAI 兼容网关和自托管端点。
- 每个路由可配 `baseURL`、`api`、`models`、`modelOverrides`、`compat`、reasoning、图片预算与重试；凭据以引用解析，不写进配置。
- 会话级 `/model` 与 reasoning effort；模型目录驱动 GUI。
- 子 agent 可逐次指定 `provider` / `model` / `reasoning_effort`；`modelSelectionSettings` 可把精确路由白名单记入会话并继承。
- **限制**：ACP、Codex、Claude Code 后端拒绝逐子 agent 模型选择（`agentOptions`）；本地 spawn/fork 与 DSH SDK 支持。

结论：**接入能力比 Orbit 现有模型池更宽**；缺的是角色化选型策略与质量证据。两者不是同一层：DSH 提供接入与路由，Orbit 提供角色池加 JEV 选型。早先把它们并列比较，对象不对等。

### 3.4 DSH 的子 agent

- `spawn`（不继承上下文）/ `fork`（继承）/ 外部 ACP。
- 深度上限（默认 1 层）、冷恢复、父子消息、中断、列举。
- 实验性 agent team：Lead + 具名 teammate + 持久任务板 + inbox。
- workflow 扇出（`agent()` / `parallel()` / `pipeline()`），结果可用 schema 校验。
- 缺的不是 subagent 机制，而是“验收 AI”这个角色及其保证：独立只读、固定快照、逐条覆盖、问题回送、完成与停止门。

### 3.5 DSH 不提供的东西

- **没有 Temporal 那种外层持久执行**：jobs 随 harness 关闭结束，schedule 只向会话投提醒，workflow 随进程结束。持久编排与关系存储仍留在 Loom。
- **`dsh-goal` 不是编排**：目标可跨重启与 fork 保留，但它只存状态、不调度工作，不能替代 Temporal。
- **没有手机外壳**：现有外壳为 desktop、web、headless、SDK/ACP。
- **客户端没有 URL 路由**：打包产物中未发现路由库；面板切换靠本地状态。
- **客户端 API 处于 `0.2.1-rc.2`**：与宿主 release 绑定，有 `engines.dsh` 兼容检查，跨 release 需重建。

> 以上能力来自对 DSH 打包产物（295 个包）README 的静态核对，未运行其 API。落地前需真实探针。

## 4. 结论

### 4.1 目标形态

```text
可信节点（本地 Mac）
└── DSH
    ├── orbit-core   （agent 侧）：任务、要求版本、快照、独立检查、完成门、选型、账本
    ├── loom-ui      （客户端插件）：项目工作台、进度、决定
    └── loom-bridge  （host 插件）：调 Loom 后端
        │ 出站连接
Loom 后端（Python/Postgres/Temporal）：项目、批准、证据、进度
```

### 4.2 分工

| 部分 | 职责 | 约束 |
| --- | --- | --- |
| orbit-core | 存准要求与修订、拍快照、安排独立检查、判完成、选型、记账 | **零 Loom 依赖**，可独立作为开发工具运行 |
| loom-ui | 项目工作台、进度、决定、证据展示 | 只展示，不判完成 |
| loom-bridge | 调 Loom 后端 API | 不持业务事实 |
| Loom 后端 | 项目、批准、范围、证据、进度 | 业务权威不变 |

### 4.3 两个门

沿用 2.3 的分法：orbit-core 判本次交付是否完成、是否经独立核验、是否真的停止；Loom 判是否属于批准的范围、是否计入项目进度。现行合同已经是这个分法（Orbit 的 `complete` 不直接转 Loom 完成）。

### 4.4 双用途是硬约束

Orbit 还要作为独立开发工具日常使用。因此**完成门与模型选型必须住在 agent 侧**，Loom 只消费。否则独立使用时没有门、日常开发产生的数据也进不了账本，飞轮不成立。

## 5. 讨论中修正过的判断

### 5.1 不是“只把 Loom 做成界面插件”

最初设想只替换 Loom 的界面层。核对后：只做界面不解决事件暴露，仍需轮询；需要宿主同时承载 agent 侧与界面侧。业务权威仍留在 Loom。

### 5.2 完成门不能放 Loom

若完成门只在 Loom，独立开发没有门，且两边判定会分叉。完成门留在 orbit-core，Loom 消费回执并做自己的业务门。

### 5.3 选型不能等账本成熟

最初计划“先攒账本、再谈选型”，结果是长期只用贵模型，账本也只有一个模型的记录。改为**选型第一天在线**（L0/L1），第 2–4 周进入 L2 统计。

### 5.4 不是等价迁移

没有可移植的代码边界，只有可参照的规则与理由。宿主原语几乎不对应：

| 本仓依赖的 | DSH 里对应什么 |
| --- | --- |
| OMP 原生 `task/hub` 派发与会话隔离 Agent 定义 | subagent / 实验性 agent team（语义不同） |
| 向 provider 请求载荷的特定位置注入指引 | 另一套 system prompt 组装与 persona |
| `ctx.models` 目录与凭据解析 | `dsh-llm` 目录 + pi-ai 路由 |
| OMP 会话文件、扩展 API、只读会话 | DSH 会话日志、子 agent、只读沙箱 |

规模参考：本仓 `main` 跟踪 84 个 Ruby 文件、43,150 行（`git ls-files`）；163 是含未跟踪文件的全部文件数，不是规模口径。检查与选型相关 14 个文件约 7,900 行。Orbit 自身标准是“确定性测试不能替代真实模型与控制验证”，所以搬过去要按新宿主重新跑真实验收，不能继承旧结论。

### 5.5 AI 重写改变的是“写”的成本

AI 能压缩翻译与补缺口的时间，但压缩不了三件事：

1. 逐条决定哪些保证在新宿主上仍然成立；
2. 产出真实端到端证据（真模型、真停止、长会话）；
3. 独立接受结论——用同一套模型自证移植正确，正是 Orbit/Loom 要防的循环。

等价性用**差分对比**证明：同一批任务，两套检查各跑一遍，对比结论与覆盖项，不靠读代码。

## 6. 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 只把 Loom 做成 DSH 界面插件，执行体仍是 Orbit/OMP | 不解决事件暴露，仍靠轮询；统一只到外观 |
| 把 Loom 业务底座搬进 DSH host | 关系数据、持久编排、权限边界都不匹配；业务权威与 agent 同进程，边界只能靠纪律 |
| 完整等价迁移 Orbit | 需重跑全部真实验收，与上游分叉；成本与风险最高 |
| 写死模型映射 | 模型迭代快，映射很快变成负资产 |

---

## 7. 选型：JEV 加角色池，不是轮换

2026-10-16 的裁决已经定了选型方式：执行者和检查者各有候选池，由 JEV 在“池 ∩ 当前目录”里做任务适配判断；Root 始终用启动会话的模型；不引入品牌、强弱、价格等级或自动升级偏好；池序是用户偏好，不构成质量或费用优势。

因此早先写的 L0/L1“轮换、便宜优先、失败升级”不成立：它用程序规则替代 JEV，并引入了价格与强弱偏好，违反该裁决。**选型从第一天就是 JEV，不是轮换。**

成熟度体现在证据，而不是策略档次：

| 阶段 | 选型依据 | 何时可用 |
| --- | --- | --- |
| 基线 | 池序加目录先验；没有质量证据时明确降级 | 第一天 |
| 精确证据 | 真实样本、任务适配判断、实际型号记录 | 有用量后 |
| 费用排序 | 只有可信本路由资源与可归属用量可比时才比较 | 有可比数据后 |
| 换判断 provider | 新增或替换判断服务须显式选择并逐问题校准 | 单独决定 |

要点：

- **真值来自独立检查**，不是模型自述；没有检查者，账本记的是自述。
- **按整项任务成本记账**，不按单次调用；便宜模型多返工两次可能更贵。
- 新模型通过用户候选池进入，不由程序随机试。
- 证据按时间衰减；未知不读为免费。
- 没有质量证据时按池序降级并明说，不假装已验证。

## 8. 里程碑

JEV 不是“以后再加”：入口判断、观察和选型都依赖它。没有它，M1 就没有自动入口和成员选型。

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| M1 | orbit-core 骨架：任务、要求版本、快照、独立检查、逐条结论、完成门、账本；**入口判断、观察、成员与检查选型的 JEV 通路**；同时定下对外可读的事实形状 | 一个真实任务从头到尾跑通；选型有实际型号记录 |
| M2 | 日常开发用起来；精确证据积累，任务适配判断可用 | 连续用一周不别扭；账本有样本 |
| M3 | Loom 只读接入：同一任务在 Loom 里能看到状态与逐条结论 | 形状对得上，不用改 orbit-core |
| M4 | Loom 业务接入：批准、进度、完成回执 | 两个门各判各的，不打架 |
| 并行 | 换判断 provider、费用可比排序 | 不阻塞 M1–M4 |

M3 不等待 M2 的体验打磨：只要 M1 的对外事实形状稳定就可接入，越晚改形状越贵。

## 9. 风险与未验证

1. **停止语义（最高风险）**：OMP 按进程组收束；DSH 是会话与子 agent。能否做到“确认真的没有东西在运行”要单独验证。
2. **JEV 重校准**：观察形状（原生调用元数据、窗口、去重键）不同，策略可搬，事实要重攒。
3. **独立性等级**：检查者与执行者同进程同账号时，独立性靠“新上下文 + 只读 + 不给执行方的话”保证；要达到进程隔离级别需另起进程。
4. **入口判断的落点**：DSH 有 `agent/pre-step`，可在拟进入步骤前拒绝或替换消息；需验证它能否在首条消息前拿到原文与稳定 id，以及“会话已建立但尚未判定”的窗口怎么覆盖。
5. **客户端 API 不稳**：`0.2.1-rc.2`、与宿主 release 绑定、跨 release 需重建。
6. **无 URL 路由**：面板切换靠本地状态，深链与浏览器后退会退化。
7. **无手机外壳**：手机端要单独做响应式或等上游。
8. 以上全部**未做真实探针**。

## 10. 未决事项

1. orbit-core 是完整搬还是先搬子集（双用途倾向完整，但可先骨架）。
2. 检查者的独立性要做到哪一档：同进程只读，还是另起进程。
3. Loom 界面是否必须进 DSH，还是先留在自有 Web、DSH 只做 agent 侧。
4. 入口判断挂在 `agent/pre-step` 的哪一步；是否还需要额外的会话创建钩子。这决定“自动接管”能否保留。
5. 差分对比的任务集与比较维度。
6. 迁移期间新旧并存、发布与回退方式。
