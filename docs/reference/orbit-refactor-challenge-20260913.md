## 值得补实的五项

### 1. 检查者必须拿到完整原文和实际版本

**已核实：**[task_records](../../lib/orbit/v2/cli/document_factory.rb:176) 只取 `acceptance` 的第一项，`source_requirements` 是固定说明。[证据入口](../../lib/orbit/v2/cli.rb:600) 使用提案提供的路径；[repository_snapshot](../../lib/orbit/v2/cli/document_factory.rb:1005) 有 Git 时读取 HEAD，非 Git 回退只散列路径名称。现有路径不能证明检查者看到了完整验收条件和本次未提交内容。

**失败风险：**用户要求 A、B，Root 整理稿或入口只留下 A，检查者再独立也可能一致通过；检查旧快照也可能误报遗漏或漏掉新改动。

**Root 建议：**原文和有效决定由输入入口直接保存，Root 的解释另存；检查能读取并关联当前实际内容，包括未提交改动。先补清输入和观察边界，不以增加 reviewer 数量弥补共同的错误依据。

### 2. 持续检查需要独立运行主体，不能只有命令和规则

**已核实：**[dispatch](../../lib/orbit/v2/cli.rb:472) 目前只建立执行记录；[LeadControl](../../lib/orbit/v2/lead_control.rb:81) 中到期触发遇到 active attempt 会返回冻结决策。[ADR-006](../adr/006-serialized-lead-orchestration-control-loop.md:49) 仍要求每 Task 最多一个 non-terminal Attempt。本地 provider 的[信任限制](../plan/debt-ledger.md#1-本地-provider-信任降级阶段-d-裁决2026-08-17) 也未解除。

**失败风险：**如果没有持续运行的程序负责时间和事件，Root 不调用 Orbit 时，检查根本不会发生。若绕开合同在另一处派检查，又可能形成两套执行状态。

**Root 建议：**实施前明确谁启动 Agent、谁到点唤起检查、谁采集结果和确认停止；这些能力必须能独立于 Feedback 运行。决定运行中检查是否允许读取固定快照并与写入并行，再修订相应串行语义。程序可以随一次任务持续运行，不必由此推导出庞大的常驻服务平台。

缺少实现是接线前提，不单独证明新方向错误。返回 `frozen` 也不证明真实进程已经停止；原始 Grok 回报把二者接近等同的表述不能作为运行事实采纳。

### 3. 停止范围必须对应实际可控制的执行单位

**已核实：**Zeen 快照的[权限回调](zeen-orbit-handoff-20260913/snapshot/services/feedback-agent/src/team/acp-drive.ts:87) 按角色和工具类型判断，[stopTree](zeen-orbit-handoff-20260913/snapshot/services/feedback-agent/src/team/proc.ts:107) 停止进程组；它们不能直接证明可按任意业务意图精确截断工具动作。

**失败风险：**同一会话混做必要功能 A 和应停止的优化 B。只阻止下一次派发挡不住当前动作；停整个会话则 A 也会暂停。

**Root 建议：**停止以能够实际控制的会话、进程或已隔离工作为单位。混在一起的工作可能需要一起暂停，已经隔离的独立工作继续。不要要求程序理解每条 shell 的业务目的，也不要用完成门代替实际停止。这不增加 Root 自动替换或运行故障恢复。

### 4. 资源边界要能观测，检查和裁定也要计入

**已核实：**[BudgetProjection](../../lib/orbit/v2/budget_projection.rb:44) 的指标是测试数量与行数；[budget_fuse](../../lib/orbit/v2/lead_control.rb:714) 检查的也是测试预算。尚不能用这些机制声称供应商额度受控。

**失败风险（未实测）：**任务卡住时反复读取相同材料、调用检查和裁定，监督成本增长却没有改善交付。“有新证据”也可能仅是无价值测试或微小产物变化。

**Root 建议：**在最小实现设计中明确一个实际可执行的资源边界，并记录检查、裁定和执行的累计投入。可得 token、调用次数、运行窗口各按自己的单位表达；不可见套餐额度继续标未知。用户授权的调用或时间上限本身可以生效，不等于把它伪装成 token。

目前没有证据证明最佳检查频率或第三方裁定的净收益。保留已经确认的连续观察与按需裁定方向，通过实际行为验证其成本和效果，不预先承诺一定节省额度。

### 5. 最小验收应更贴近用户实际遭遇的失败

原定两条路径只能证明所覆盖的遗漏检测与停止行为，不证明所有漂移都能纠正。一次成功也不能推翻模型可能共享盲点的风险。

**Root 建议，待讨论：**保持两条验收主线，不建大型基准。第一条从真实输入开始，让 Root 整理稿漏掉一项，并保留未提交产物，验证独立检查仍能发现；停止路径除明确边界外，考虑用“需求已满足却继续加无必要测试”的情形验证语义止损。还需用小范围接线检查确认：Root 没有提交产物时，到期检查确实能发生；停止请求确实作用于相应执行单位。具体实验组合与资源仍需冻结，不能为了审查不断扩大验收。

## 不直接采纳的替代方案

- **退回只有终态后检查。** 旧串行合同冲突必须处理，但旧合同不是否定新方向的理由；仅等 Root 结束会重新漏掉用户要求的持续观察。
- **工作区 digest 没变就永不调用检查者。** 可以复用已知结论，但缺少变化本身可能是卡点。不能用去重重新堵住无产物时的独立诊断。
- **删除裁定者，让检查者拥有最终否决权。** 这未解决检查者误判导致任务被拖住的问题；现有“必要时独立裁定”的净收益应验证，不因可能多一次调用直接取消。
- **固定第三次重新设门，或把引用字段齐全当作问题成立。** 这不能替代用户已确认的“先证明问题属于当前交付，再看是否值得继续”；结构完整不证明语义正确。
- **假定不同供应商必然独立，或要求模型猜出未表达的真实意图。** 模型来源不同不保证没有共同盲点；原文确有歧义时应查已有决定，仍无法确定则问用户，不能把猜测包装成纠偏成功。

### Root 核查：值得补清的三个接缝

1. **原始执行指令的原样传递。** 现有 skill 确实让 Agent 编写 task 定义；新稿要求保存原文，但还没有指定原文如何绑定到触发消息。缺口是接入方式，不是需要接管需求讨论。建议优先使用通道可提供的本次执行消息，skill 原样转交而非重写成计划；执行中的明确修改同理。只取本任务执行指令，不收整段需求讨论，不加用户二次填表或每次确认。通道无法直接取原消息时如实说明来源能力，不把 Agent 摘要宣称为程序已核验的原文。OMP 所称“原始指令实为转述”是风险推断，尚未实现的新通道不能据此断言必然失真。
2. **检查依据应包含双方共同适用的项目规则。** 新稿已经说在目标项目遵守其规则，但具体投递不应依赖检查会话偶然位于正确目录。建议让执行者和检查者取得本任务相关、同一有效版本的项目规则，并区分产品／工程要求与 Orbit 运行控制。针对 Zeen，用户本轮明确的预估非硬门、不投票、不替换 Root 等决定不能被旧参考流程恢复；这也不是授权 Orbit 全面覆盖目标项目的安全边界或必过检查。项目事实按项目来源，控制策略按本次有效授权；只处理实际冲突，不全量引入 Zeen 规范。
3. **只读检查与执行验证的边界。** 静态阅读实际源码本身可以发现问题，不等于只看 Root 自报；因此不采纳“只读就只能看声明”的二分。但测试、构建确实可能写缓存、产物或共享数据。建议默认检查固定产物及已有验证结果；确需补执行验证时，使用独立临时副本和任务资源，或在不与写入冲突的时段验证，不在 Root 正在改的工作区并行运行会改变它的命令。隔离和补验按实际风险需要，不给每次只读检查强制建 worktree。

这些是待纳入实现设计的建议，未因此更改已确认产品边界或自动增加验收场景。

### 不直接采纳的扩展与不同意见

- **保留实现类任务的 assurance-only 自动冻结作为通用保险丝。** 已读 `LeadControl.stop_loss`：其按终态的 delivery／assurance 分类冻结。Grok 的担心有价值，但“需要补关键验证、实现字节未变”也可能是正常交付进展；分类本身不能证明浪费。新稿已要求检查者判断无必要工作，并不将所有“做多了”都降为偏好。`stop_loss` 的具体替换在计划中本来就是待审建议；不因本轮投票将其保留或删除，更不能先删旧门而不接通新的观察与纠正。
- **增加 Orbit 进程故障体系和杀进程验收。** 这是独立于 Root 故障的运行风险，记录其影响：监督进程异常退出可能使定时检查中断。但“被杀的进程给自己记标记并通知 Root”不能覆盖不可捕获的退出；要实现需明确另一个观察者，不能一句话当作免费能力。本轮不自动加入恢复／监督体系，也不将故障注入设为第三条必验。完成结论仍须来自有效检查，缺检查不能伪称已完成监督。
- **要求用户修改需求必须改走 Orbit 入口，或交付时统一补确认。** 不直接采纳。用户在当前 Root 会话说话的使用方式保持不变，先解决接入层传递，不把程序缺口变成用户新增操作。
- **新增多个真实实验。** 四者建议均保留为候选，不机械叠加。输入原样传入和途中更新适合在接入阶段核对；检查权限在实际会执行的路径验证；现有两条验收主线不因本轮意见自动扩张。

### 一个值得保留的验证建议
