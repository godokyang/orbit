### 当前机制与判断边界

当前 [check_runner.rb](../../../lib/orbit/check_runner.rb:1023) 已要求逐项枚举原始要求、修订和依据，没读或证据不足应标 unverified。因此不能建议“补一句要求逐项验收”，仿佛现在没有。当前 [requirement_coverage.rb](../../../lib/orbit/requirement_coverage.rb:105) 检查枚举声明和条目状态，语义是否充分仍依赖检查者判断；结构合法不等于内容判断正确。

这次 21 项低于 64 项上限，没有证据表明是上限迫使遗漏；也不能说只是看不到图片。已确认的是要求与证据的对应判断失败，尚不能确定模型为何忽略具体条款。后续可讨论如何让检查围绕原条款和直接证据作判断，不能以新增 Loom/UI 专用判据替代通用能力，也不默认要求重复执行全部测试。

## EXP-12：申诉裁定被持续作废

### 日志能还原的循环

C 第 1 次检查认为成员不能读 `prototype/`、`docs/`，要求 Root 扩大范围。Root 申诉指出实际被拒的是 `skill://` 资源，相关项目资料已经允许读取。

随后第 3—24 次检查都是 `adjudicator`。22 次结果的 `resolved_ids` 都包含 `block-read-outside-scope`，理由均否定原意见的依据。但 22 次全部 `stale=true`，原因是检查期间 artifact、host 等发生变化。最后 `state.dispute` 仍在，`decisions` 长度为 0。共 24 次检查中 23 次过期，仅第 1 次形成正式纠正。

这些裁定不全只看申诉，也有当前工作判断。但后续以 `jev_process`、`member_block_stall` 触发的过程检查，同样被选成申诉裁定者，反复处理这条未结束的申诉。

当前代码能解释上述过程：

1. [task_runtime.rb:2624](../../../lib/orbit/task_runtime.rb:2624)：只要存在 `state.dispute`，下一次检查角色就是 adjudicator。
2. [task_runtime.rb:3109](../../../lib/orbit/task_runtime.rb:3109)：检查结束时，比较代码、输入、宿主活动及申诉是否变化。
3. [task_runtime.rb:3164](../../../lib/orbit/task_runtime.rb:3164)：过期分支不会保留 adjudicator 的普通待复核线索；保存后直接返回。
4. [task_runtime.rb:3271](../../../lib/orbit/task_runtime.rb:3271)：采纳裁定、记录 decisions、清除 dispute 在上述返回之后，因此没有执行。

结果是：Root 继续工作 → 裁定期间内容变化 → 裁定不被采纳 → 申诉仍在 → 下次又裁同一申诉。这里已经能定位程序原因，不需要先假定 JEV 判断错了。

### 已发生的投入与限制

22 次裁定的起止时间累计 4,191 秒，即 69 分 51 秒。SDK usage 合计：非缓存输入 2,790,818 tokens、缓存读取 13,940,736 tokens、输出 500,260 tokens；legacy 总计 17,231,814 tokens。缓存读取与非缓存输入不能按同一价格折算，不能把这段累计时长当成十二小时中完全串行浪费的时间。

C 另有 474 次 JEV 记录。JEV 调用次数不能当作有效纠偏次数；也不能因有 22 次独立裁定就说申诉已经解决。最终停止记录确认 Root 与 11 名成员结束、相关工具与异步活动结算，这证明停止完成，不证明九项交付完成。

2026-10-16 用户已确认：程序将裁定、依据及期间变化交给 Root，由 Root 通过 Orbit 工具决定采纳或说明原因要求补查。程序不因代码或对话变化自动作废，也不因等待 Root 处理反复裁同一条申诉；其他工作与正常检查继续。完整方案维护在[已确认改动方案](agreed-change-plan.md#exp-12-已确认裁定交给-root-处理程序不自动作废)，尚未实施。

## EXP-13：对话证据路径错误

A、B、C、D 的 `connection.thread_id` 都指向 L1，但 `root_session_file` 均指向旧会话：

`/Users/yangke/.omp/agent/sessions/-Personal-omen-loom/2026-10-14T05-45-09-947Z_01a138f1-723b-70f3-8b0d-0bbbdd3f5476.jsonl`

该文件只有 480 行，结束于 `2026-10-14T06:28:06.947Z`，早于本轮任务。原要求 `104b8de4`、复核要求 `5547f8df`、用户确认 `6dbec2a9`、停止要求 `4c5da936` 都不在其中；它们实际位于 L1 第 7、5864、5883、13280 行。A 第 31 次和 C 第 8 次检查的 `prompt.txt` 也携带这个旧路径。

当前 [omp-host.mjs:2127](../../../plugins/omp-host.mjs:2127) 的 `sessionFileFor` 按会话 ID 找 Registry 条目后，直接取条目的 `sessionFile`。本地无模型探针从源码提取该函数，提供“Registry 路径旧、活动 sessionManager 路径新”的对象，函数仍返回旧路径；本机安装版 0.8.11 对应函数与工作区相同。日志已证明实际路径错指；探针证明当前函数不会纠正这种不一致，初次追查未查明 Registry 在哪一步留下旧值；后续已用实际 OMP 18.9.0 复现新建和切换时登记地址不更新，完整证据见[根因追查](exp-13-session-path-cause.md)。

还验证了实际下游影响：[task_evidence.rb:524](../../../lib/orbit/task_evidence.rb:524) 优先选记录中存在的路径，随后检查文件头是否匹配会话 ID。用 C 的真实状态调用这段只读逻辑，返回 `unverified`，原因为会话头与 ID 不符。它安全地拒绝复制错误对话，但此分支没有继续按正确 ID 找实际文件，因此会漏掉可取得的 Root 原生对话。

不能据此断言每个检查者都实际打开了旧文件，或所有误判都由此导致。例如 C 第 18 次裁定声称没有得到启动确认，但 L1 第 5883 行确实存在“确认”；这说明检查依据与真实对话不一致，尚不能把原因唯一归到错路径。需要一并核对已有 EXP-02／06 的输入与读取问题。

后续已定位取值错误：活动会话地址已更新，Orbit 却读取登记表中未更新的地址。修复候选改为从活动会话读取实际地址；此前“对不上再找”只涉及历史记录补救，不能替代根因修复。详见[根因追查与原生探针](exp-13-session-path-cause.md)，尚未采纳或实施。
