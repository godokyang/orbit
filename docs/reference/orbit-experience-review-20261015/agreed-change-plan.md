## 目标与职责

Orbit 帮助 Agent 尽量完整、便宜、自动地完成任务，减少用户催促、转述和纠偏。Root 决定实现、分工、纠偏、争议处理及是否需要用户介入；成员自主实施，检查者自主取证。程序准确记录和传递事实、执行决定，落实用户明确授权与停止要求。完成标准来自用户原始要求及有效修订。

Root 交代问题、背景、任务要求和验收条件；成员自行调查、选择修改文件和实现方法；交付后 Root 核对结果，决定接受、返修或拒收。用户明确的约束持续有效。

后续从本文进入修改：产品规则改运行合同，决定理由改 ADR，代码与验证状态改交接；本目录保留问题证据与实施定位。评价口径按 [ADR-009 的整项任务成本](../../adr/009-user-selected-model-pool.md#2026-10-16-补充以整项任务评估成本与自动完成效果)，同时观察完整交付、返工、重复调用、等待与用户介入，不以少传 token 或选低价模型单独证明收益。

### EXP-11 的具体调查

1. 从原始要求与引用原型列出实际遗漏的义务，对照第 30、31 次检查的真实读取、coverage 和证据。确定是条款未进入输入、已读未检查，还是证据被错误推广；不能仅以条目数量少判漏项。
2. 核对第 30 次未核实项在第 31 次如何变成已核实，以及已有错误通过是否被沿用。区分程序没有提供历史详情与模型没有调查可读材料，不从“可能锚定”直接判因。
3. 对照后来发现缺陷的检查，比较原要求、受检文件、实际输入和取证动作；能解释差异的事实保留，模型内部判断原因未知就明确未知。
4. 核对 Root 是否因检查要求追加了无必要验证。已有 UC-01 记录不支持“第 14 次检查强制追加烟测”；其他片段按时间与实际消息分别调查，不先认定一个通用原因。

调查结果用于提出最小调整，不能预先换成强制逐字引用、固定必读文件、增加检查轮数或升级模型的方案。需要真实模型比较时另按实施授权安排，不把静态分析写成效果已改善。

### 本轮不采纳的替代方案

不恢复固定文件／目录白名单，不恢复所有视觉项一律读图，不改为程序自动采纳裁定，不新增 coverage 逐字引用义务，也不默认新增“多久没有 verified”展示或硬门。它们没有被当前证据证明能解决对应问题。裁定仍由 Root 处理，是否补查依据具体缺口与证据判断。

后续[研究判断](decision-followup-research-20261016.md)及[对 Loom 的影响](loom-change-impact-20261016.md)单独保存，不因本节已经确认而自动生效。已查明 Loom 的原生问答链存在，旧 `needs_user` 续接仍有硬编码拒绝，严格模型执行路径关闭 JEV；具体联动建议见影响报告。

## EXP-02 补充确认：告诉检查者记录在哪里，由它自主读取

2026-10-16 确认。EXP-11 追查发现，上一轮逐项检查结果已经保存在任务目录，下一轮没有直接获得详细内容。此处并入既定开放只读取证方案，不新增一套历史结果传递机制。

启动独立检查者时，程序提供自己实际使用的任务记录目录，并说明现有文件的用途：

| 位置（相对于实际任务目录） | 内容 |
| --- | --- |
| `state.json` | 历次检查结果、已记录的问题和裁定 |
| `requirement-coverage.json` | 已保存的逐项检查结论、证据与对应版本 |
| `checks/` | 各次检查保存的输入、输出及会话等原始材料；可用内容以实际文件为准 |

目录从运行时持有的 `TaskRecord.path` 取得，与实际写入记录使用同一来源，不由 Root 或检查者猜测。当前代码已使用该路径保存状态并建立 `checks/<编号>/`；需要补的是向检查者提供这个入口及用途说明，并开放相关只读访问。路径说明须完整可用；文件实际缺失时如实说明，不编造原件。

检查者自行按需读取历次结果、逐项结论、证据和未核实原因，判断哪些可沿用、需要补查或应被推翻。不默认把全部历史内容重复放进每次输入，不另建记录副本，不增加固定必读文件名单或检查次数。验收关注能否从给定入口读到上一轮具体未核实项及原始依据，而不只是看到检查编号和状态。

这项补充解决记录可取得、位置可找到的问题。EXP-11 中原型与页面代码已经可读却未检查的事实仍保留，不能把开放读取当作漏判已修复；后续按上文具体调查和已知失败样本核对。EXP-13 的原生对话路径错指是另一处问题，不因任务记录目录正确而自动解决。

方案已确认，尚未实施。证据与当前代码位置见 [EXP-11 检查调用追查](exp-11-review-trace.md)。

## EXP-05 已确认的日志范围

本节确认诊断记录的补充；输入完整性方向及观察顺序见下一节。判断口径、触发策略、纠偏与恢复机制的具体调整仍待证据支持。记录齐全不等于监控效果已经修复。

| 记录对象 | 必须保留的事实 |
| --- | --- |
| 实际请求 | 最终发送给供应商的完整 JEV 输入及问题文本，包含当次要求、有效修订、依据、近期观察和成员状态等实际字段；保存发送版本，不另造一份日志摘要冒充输入 |
| 身份与时间 | 任务与调用标识、请求和响应时间、请求模型与实际返回模型、问题／输入投影／程序决策版本，以及输入和受观察状态的对应关系 |
| 裁剪过程 | 被省略或截断的来源、裁剪前后长度、原始记录位置；可以定位宿主投影与 JEV 输入构造中哪一层丢失事实 |
| 结果与程序动作 | 成功、失败或不可用状态，供应商返回分数及实际用量；程序为何触发、未触发或暂缓检查，以及关联检查编号。实际返回内容可留原件；供应商未提供解释时记未提供，不编造模型理由 |
| 监督与成员生命周期 | 监督中断、恢复尝试及结果、当前任务绑定变化；成员退出、终态通知尝试和送达结果，以及 Root 后续接管或处置的可观测动作。停因或处置不可得时保留未知 |

完整输入和结果可放在任务目录的独立文件，`events.jsonl` 使用同一 `call_id` 引用，避免重复嵌入大段正文。每次实际调用均可关联；不把无新事实的每次循环都写成一份重复快照。最终发送内容只指 Orbit 可观测的请求，不声称掌握供应商内部追加的上下文。

按现有记录补缺和建立关联：已有调用标识、分数／用量、纠正送达／失败、成员状态及续接事件继续复用，不另建平行日志系统。监督和成员的记录要求不表示当前没有相关机制；能力与实际缺口见[现有能力核对](user-correction-monitoring-audit.md#现有能力核对与建议收缩)。

验收使用现有日志中的不同失败路径：UC-01 能回查完成状态和烟测失败是否进入 JEV；UC-05/06 能区分成员退出与监督空档。新增日志不能补造旧任务已经丢失的输入。来源见[UC-01 根因追查](user-correction-monitoring-audit.md)和[其他五个片段复核](other-round-root-cause-review.md)。

## EXP-05 已确认的输入方向与观察顺序

沿用成员自主实施、检查者自主取证、完整申诉及取消固定容量上限的方向：增强 Agent 获取相关信息和自行判断的能力，减少缺乏实际依据的程序限制。

1. **先补日志、观察真实调用。** 已回放确认信息损失及未触发检查，但尚不能确定 JEV 具体评分原因。先保留实际输入、输出和程序处理依据，不把裁剪、问题文本和阈值一起改动后再猜原因。
2. **输入方案优先评估取消人为截断。** 当前原要求 4,000 字符、单条修订 1,200 字符、近期观察总计 5,000 字符及每条 1,800 字符等限制，不默认保留。此前提出的分配摘要预算、首尾裁剪等方案未获采纳，不作为既定实施方案。
3. **区分 JEV 与独立检查者。** 当前 JEV 是无自主补读工具的单次判断请求，相关输入尽量完整提供，仅附路径不能替代内容；独立检查者沿用 EXP-02 的开放只读取证，取得必要上下文及原件入口后自主调查。
4. **按任务关联选择材料，不按小字符上限切断正文。** 取消人为截断不意味着每次重复发送整个项目历史。具体材料选择方式仍待核对，不把裁剪换成同样会静默遗漏关键证据的限制。
5. **实际接口容量不足时明确处理。** 记录真实容量问题，不静默删掉内容后当作充分证据继续判断；具体处理方式待实施前核实实际约束，不新增假设性容量机制。

以上确认的是日志优先的顺序和减少人为截断的方向，不代表已经实施全面取消限制。取消后的判断效果、误报／漏报与调用量须实际观察；是否调整问题、阈值及其他现有机制，依据新证据再决定。

## EXP-06 已确认：用户的新话也要给 JEV 看

当前程序已经读到用户新消息的正文，但未登记为任务修改的消息只留下消息 ID，没有把正文传给 JEV。JEV 因而可能看见 Agent 根据新话采取了行动，却仍只拿旧要求判断。具体评分是否因此出错，仍需完整日志核实。

已确认的修改如下：

- 用户最新的指令、提问和纠正，以及理解这次行动所需的前后新消息，原文传给 JEV；不能只等 Root 登记修改或在回答中复述后才看见。
- 原任务要求和已登记修改继续保留。用户新消息注明来源、先后关系及是否已登记修改，供 JEV 结合上下文判断 Agent 当前行动是否合理。
- 让 JEV 看见新消息，不代表每句话都自动修改旧任务，也不因为插问就自动取消任务、关闭监控或认定 Agent 跑偏。
- 复用宿主已有的消息读取能力，补上正文传递，并接入 EXP-05 的实际请求日志；不用另造一套消息来源，也不要求用户重复解释已说过的话。

例如用户先要求修代码，又问“你觉得 Orbit 好不好用”，JEV 应同时看到这两项要求，再判断 Agent 回答评价是否合理。输入确实包含新消息可通过记录核对；模型是否减少误判须另作实际验证。

修改定位：`plugins/omp-host.mjs` 的 `messages`、`lib/orbit/task_runtime.rb` 的 `collect_amendments`／`assess_jev`、`lib/orbit/jev_advisor.rb` 的 `observation`。本项不同时决定删减 Root 的旧目标上下文；原分析和检查记录见 [EXP-06](evidence-review.md#exp-06)。

## EXP-07 已确认：暂不调整，保留核查

当前已有原任务与修订的上下文提供、活动成员修订传递，以及条件满足时提醒 Root 继续执行的机制。用户确认本项暂不改代码、不新增机制；先实施前面已同意的日志和用户新消息传递，再观察用户纠正后是否实际继续执行。保留问题，不标为已解决。

## EXP-08 已确认：保存成员退出状态，不沿用旧 running

当前源码已复现成员中止并移除后，状态读取仍返回缓存的 `running`，运行时继续将成员保留为未结束。本机安装的 0.8.11 相关代码与工作区相同；复现过程及其范围见[当前版本复现](other-round-root-cause-review.md#exp-08-当前版本复现退出后仍返回旧的-running-状态)。

已确认修复方向：处理宿主已有的成员状态变化和移除事件，及时保存最后状态。登记消失而最终状态无法确认时明确返回未知，不能把旧 `running` 当作当前仍在执行。复用现有状态读取和通知能力核对 Root 是否取得变化，不新增统一等待时限。

验收覆盖已复现的顺序：成员先被观察为运行中，在下一次读取前中止并移除；随后 Orbit 不再返回旧运行状态，运行时和 Root 可取得真实终态或明确的未知状态。成员状态已保存不等于 Root 已收到通知，需分别核对。本项讨论已确认，代码尚未实施，也未验证修复效果。

## EXP-09 已确认：由 Root 判断是否需要用户处理

2026-10-16 确认。当前 `needs_user` 既可来自独立检查结果，也可由程序在成员无法接收修订、用户消息读取失败等情况下直接设置并停止任务；续接入口又只接受 `paused`。当前代码及验证证据见[EXP-09 核对](other-round-root-cause-review.md#exp-09-当前版本核对needs_user-停止后没有续接入口)。

已确认的调整是：**检查者和程序提供事实，由 Root 判断是否需要用户介入；不再仅凭 `needs_user` 自动停止任务或拒绝续接。**

| 情况 | 调整后的行为 |
| --- | --- |
| 检查者认为缺少信息或决定 | 告诉 Root 缺什么、为什么需要；Root 判断能否自行查明，还是必须问用户。检查者的 `needs_user` 不直接触发停止 |
| 成员结束、消息发送或读取失败等技术问题 | 报告实际错误和已知状态；Root 判断接手、换成员、重试或询问用户。程序不把技术问题直接等同于必须由用户处理 |
| Root 确实需要用户回答 | 使用现有提问能力，保留原任务和有效要求；其他不受影响且能继续的部分继续执行，不因提问就结束整项任务 |
| 用户答复到达 | Root 判断信息是否足够；足够则沿原要求继续，不足则具体追问。程序不根据状态标签阻止执行 |
| 既有任务已经停为 `needs_user` | 允许已确认停止的任务复用现有续接能力，保留原要求及有效修订，不要求用户重述任务；不自动唤醒旧成员 |

用户明确要求停止仍须立即执行。实际运行故障、停止状态和监督是否可用必须如实记录与报告，不能因为交给 Root 判断就假装程序仍在正常监督。此次决定调整的是用户介入与续接的判断，不取消独立检查和真实完成要求。

复用现有提问、通知、状态读取和续接能力，不新增审批流程。后续实施同步检查结果处理、程序直接设置 `needs_user` 的路径、Root 提示、CLI 续接校验及运行合同、ADR、集成能力声明；核对已有字段与调用方，不能只放开续接却保留上游自动停止。

验收围绕检查者报缺口、程序报技术问题、Root 提问后收到答复、旧 `needs_user` 任务续接四种行为，分别核对信息是否送达、Root 的选择及实际后续动作；用户明确停止与真实故障报告继续有效。当前仅确认方案并落文档，尚未改代码或验证新行为。

## EXP-10 已确认：暂不单独调整汇报机制

2026-10-16 确认。当前材料尚未证明一个独立的“程序生成错误汇报”缺陷。先落实前面已确认的证据、监控与状态处理方向，再观察 Root 的实际汇报与交付；不为本项新增固定汇报格式、频率或重复检查流程。暂不改动不等于体验问题已经解决。

## EXP-12 已确认：裁定交给 Root 处理，程序不自动作废

2026-10-16 确认。Loom 同一申诉已有 22 次裁定支持撤销原意见，但程序因检查期间代码或对话变化而不采纳，申诉持续保留并反复触发裁定。原因与代码位置见 [EXP-12 追查](loom-experience-review-20261016.md#exp-12申诉裁定被持续作废)。

已确认流程：**裁定返回 → 将结论、依据及期间变化交给 Root → Root 提交处理决定 → 程序记录并执行。**

| 修改点 | 确认后的行为 |
| --- | --- |
| 不自动作废裁定 | 程序如实记录检查期间代码、对话、要求或申诉的变化，供 Root 判断是否影响结论；不再仅因这些变化跳过裁定处理，也不自动认定结果仍适用 |
| 将结果送给 Root | 通过现有消息能力提供对应申诉、检查编号、裁定结论、依据及期间变化；保留原始结果和记录入口 |
| 补上 Root 的处理能力 | 在现有 Orbit 工具中补充提交裁定处理决定的能力。Root 可以明确采纳某次裁定，或说明缺失证据与原因、要求补查。它是 Root Agent 调用的工具能力，不要求用户额外点击确认 |
| 结束重复裁定 | 裁定返回后保留为待 Root 处理，不因为申诉尚未结束就把后续检查一律变成对该申诉的再次裁定；其他工作与正常检查继续。只有 Root 明确要求补查，才再次裁这条申诉 |
| 执行 Root 决定 | 采纳后结束对应申诉，并按裁定更新相关问题；支持申诉时关闭被撤销的问题，维持原意见时保留需要处理的问题。要求补查时保留原结果、Root 的理由及新证据，不覆盖历史 |

Root 的处理须指明对应申诉和裁定，程序准确记录处理对象、决定和结果。具体工具动作名称与字段在实施时确定，不提前宣称现有工具已支持。复用现有任务记录、通知和检查调度；不能只放开过期分支，却仍让未处理申诉占据所有后续检查。

验收围绕已发生的行为：裁定期间 Root 继续修改代码或推进对话，结果仍可送达 Root；Root 采纳后申诉结束、对应问题按结论更新；Root 指明新证据要求补查时才再次裁定；等待 Root 处理期间，同一申诉不被自动重复裁定，其他工作与检查仍可推进。

本项调整申诉处理权，不把采纳裁定等同于整个任务完成；最终独立检查和真实停止要求仍保留。方案已确认并落文档，尚未修改产品代码或验证新行为。EXP-13 路径修复已纳入实施。
