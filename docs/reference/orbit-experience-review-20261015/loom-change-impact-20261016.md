## 结论

总体方向适用于 Loom，但不能把“放开 Agent 能力”实施成“改掉 Loom 正在依赖的状态、授权和证据含义”。最明确的联动改动是旧 `needs_user` 任务的续接。正常提问已有通道，无需再造等待状态。JEV 的改善不覆盖当前严格模型执行路径，因为该路径关闭了 JEV。

本轮读取 Orbit 当前工作区及同级 Loom 工作区。Loom HEAD 为 `289532c`，`executor.py` 等文件含未提交修改；下述行号定位读取时的实际文件，不声称这些内容均已提交、安装或上线。未修改 Loom，未控制其进程，未运行手机问答或付费模型实验。

## 逐项影响与建议

| 调整 | Loom 当前依赖与影响 | 判断 |
| --- | --- | --- |
| 成员自行选择文件 | Loom 在任务要求中写入批准的 `allowed_paths`；这是整个任务的范围。Orbit 当前还要求 Root 给成员预列文件，是另一层限制 | 取消 Orbit 的成员名单；继续遵守用户批准的任务范围。不能宣称此次调整会同时取消 Loom 的范围约定 |
| 检查者开放读取 | 有利于回查完整会话、旧检查和真实工具结果，但读取后的内容会发送给检查模型 | 保留 Loom 已选模型及已有资料授权。来源和受检版本要可辨认；不新增每次读文件审批，也不把只读等同于可发给任意供应商 |
| Root 决定何时提问 | Loom 已接原生 `ask`、问题上传、手机答复与 `answer_ask`；仅运行中的任务可以接收该答复 | 正常提问沿用此链，任务保持真实运行状态。不要把 `needs_user` 从“已停止”偷偷改成“等待回答” |
| 旧 `needs_user` 任务续接 | Loom 先看 Orbit 的能力声明，之后仍硬编码只接受 `paused` | Orbit 支持旧任务续接时，Loom 必须同步调整这一判断；仅修改 Orbit 不足以打通。继续核对实际停止、原会话、任务归属和已有模型授权 |
| 用户历史消息读取缺口 | Orbit 当前找不到上一条消息的位置就可能停止为 `needs_user`；Loom 随后进入结束处理，原生答复发送也会被状态检查挡住 | 找不到旧消息不等于 Root 收不到新消息。记录具体缺口、恢复补读并交 Root 判断；不能以此直接认定整体失控 |
| JEV 完整日志和用户原话 | Loom 当前执行器传 `allowed_models`；Orbit 在此模式将 advisor 置空，Loom 又校验 `auxiliary_judgments=disabled` | 继续改通用 JEV，但不能承诺它改善这条 Loom 执行路径。若需要在严格模式启用 JEV，须另定授权模型与双方合同，不能顺手开启 |
| 裁定交 Root，取消自动重复裁定 | 可消除已定位的申诉反复过期循环；Loom 另依赖最终检查的 `current`、成果指纹及逐标准记录 | 只取消程序自动作废裁定的处理。不得连带把旧成果的最终通过记录改为当前有效，也不得把 Root 采纳裁定写成独立终检已完成 |
| 取消场景专用验收、覆盖 64 项上限 | Loom 按标准 `ref` 映射 coverage，不依赖本次删除的 Git 专用判据；其映射遍历条目，没有这里讨论的 64 项限制 | 保留既有 `ref`、版本和 coverage 字段含义。Orbit 不再追加场景义务，但仍检查用户要求；不替 Loom 决定合入或业务验收 |
| 修复成员编辑、退出状态及会话路径 | 可减少编辑拒绝、等待已退出成员、错读会话；Loom 的问答与 Root 报告取证也依赖真实会话文件 | 编辑与退出修复按已确认方案实施。建议采纳 EXP-13 的活动会话路径修复；只修正确来源，不把旧任务绑定改指新聊天 |
| EXP-11 检查误报完成 | Loom 的逐标准映射能校验身份、版本和结构，不能仅凭 evidence 非空判断功能真的存在 | 作为重要效果问题继续调查。开放工具不能算修复完成；优先用已知遗漏验证取证是否有效，不先增加固定检查轮次或升级模型 |

## 关键源码证据

以下 Loom 路径相对于同级 `../loom/`，只作为本机取证定位，不是本仓开发规范。

1. **正常问答已经存在。** `services/node/src/loom_node/orbit/session.py:218` 启用原生问答，`:240` 接收问答事件，`:262` 回答。`execution/executor.py:704` 的 `_live_question_step` 由多个执行阶段调用，`:767` 上传 `run_question`，`:940–962` 确认任务仍运行后调用 `answer_ask`。`:2006` 在启动前启用通道。`execution/question_flow.py` 区分答案已送达与模型实际采纳。以上证明代码已接，不证明本轮手机实测通过。
2. **旧任务续接确实仍受阻。** `orbit/adapter.py:497` 检查 `needs_user` 是否在能力声明中；紧接着 `:500` 的 `current != "paused"` 仍拒绝它。`execution/executor.py:680` 把 `needs_user` 与 `failed` 送往终态处理。Orbit 的现行[集成合同](../../../contracts/integration.md)也将其定义为终态，`attention.needs_user` 不是原生问答信号。建议保留旧状态含义，通过能力声明扩充可续接来源并联动适配，避免改坏老调用方。
3. **严格模型路径没有 JEV。** `execution/executor.py:2022` 启动时传入模型名单，`orbit/authorization.py:92–107` 同时核对名单和 `auxiliary_judgments="disabled"`。Orbit [task_runtime.rb:93](../../../lib/orbit/task_runtime.rb:93)在存在名单时清空 advisor。此前 Loom 开发会话的 474 次 JEV 是另一种运行记录，不能据此认定 Loom 产品当前严格执行路径也有同样的 JEV 监督。
4. **消息缺口不是失联证明。** Orbit [plugin_connection.rb:156](../../../lib/orbit/plugin_connection.rb:156)已经取回消息列表，却找不到 `after_id` 时返回 `boundary_not_visible`。[task_runtime.rb:2501](../../../lib/orbit/task_runtime.rb:2501)除待投递外将缺口直接转为 `needs_user` 停止。此条件只证明旧定位点不可见，未证明新的消息投递、Root 接收或停止控制均失效。真正控制失败仍须如实记录，不能伪造停止成功。
5. **任务范围仍来自 Loom。** `execution/executor.py:179–222` 将批准要求和允许修改路径传给 Root；`execution/workspace.py:45` 起核对冻结目标。成员自主选文件不替代用户已批准的范围，后续实现不应凭此取消 Loom 的范围核对。
6. **最终验收与裁定不同。** `verification/coverage.py:45` 按 `ref` 或原标准编号映射，检查 `current`、`complete`、唯一条目及证据；`:133` 的收集过程核对前后公开状态和实际成果。它明确返回 `business_accepted=False`。`execution/executor.py:1881–1911` 还校验缓存与当前成果、检查一致。Root 处理申诉不能使这些事实自动变真。
7. **路径修复对 Loom 有价值，但不等于全部恢复。** `execution/executor.py:2060` 优先读取原生会话路径；`:2306` 的补取路径使用 Orbit `root_session_file`，随后检查会话身份与原始提示，已有绑定则不会跟随新消息改写。EXP-13 修复能提供正确来源；旧错误记录不能直接改挂，需按各任务实际身份补证。[原生复现](exp-13-session-path-cause.md)已证明活动路径可正确取得，修复仍未实施。
