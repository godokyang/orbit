## UC-02：不是没有规则，而是没有按规则选择验收前置

S4:14 的开发规范回执已经包含可创建可丢弃 fixture 的规则。S4:106 的测试规范回执明确要求先用 hardcode 构造关键状态，不以登录、多账号或完整服务链路作为视觉对照前置。S4:3324 再次读到了相同规则。

但 S4:3639 仍把真实记忆数据、分享服务等列为 UI 验收未完成的前置。用户在 S4:3640 要求重新看文档，Root 于 S4:3655 明确承认混淆了 UI 验收和业务闭环。随后原任务清单及文档被改正。

因此，执行端的原因可定位为**验收层次和依赖选择错误，已读取规则未落实**，不能简单归为文档缺失或用户没有讲清楚。会话曾读取规则并不证明它在之后每次模型请求中都完整保留，也不能判断模型是遗忘还是错误解释。

监督侧有一条输入配置线索：S4:97 于 10 月 7 日 18:58:12 返回任务状态 `running`，`basis=[]`，当时 checks 为 0。Root 读过项目规范，不等于它们自动进入 Orbit 的任务依据；不过这一开工状态不足以证明后续检查完全没有读取规范。S4:2956 的通知主要指出整体验收未完成及答复不归属，没有指出不必要的真实数据前置。完整检查输入已不可得，不能继续推断成某个固定截断或阈值问题。

## UC-03：纠正送到了，但没有落实为后续动作

S4:3667 发出 amend；S4:3673 的原生 Orbit 通知完整包含允许 UI fixture 的修订。这里可以排除“纠正没有传入”的解释。

接下来 Root 修改 TODO、实施记录与 baseline，跑文档检查，将“更正口径”标为完成。S4:3691 的内部 TODO 显示 0 open、4 blocked，其中仍保留此前设备超时和等待终检等阻断。S4:3692 于 08:15:39 报告口径已更正、设备仍阻断，随后结束答复。08:18:41 用户再次催促；Root 才读取设备恢复技能，并在 S4:3700 承认停在口径修正，接着执行设备恢复与 fixture 准备。

执行断点是：**任务口径变更后，没有重新判断哪些阻断已解除、哪些可执行工作应恢复**。更新文档和成功 amend 只证明信息变更，不证明原任务继续推进。原有设备故障是真的，不能把它说成虚构阻断；错误在于它被沿用为停下整轮工作的理由，用户随后不得不再次推动。

当前源码已有 `continue_unfinished_task`，但它有检查种类、归属、idle、成员结算等条件，且并非历史安装身份的证明。本例不能用当前函数存在来宣称当时自动恢复应该或确实发生，也不能直接裁定是某个条件挡住了唤醒。

两次 `wait` 实际占用约 38 分 48 秒；这是具体等待时间，不把成员退出后整个约 55 分钟都算作空耗。`wait` 没有指定成员 ID，返回“可能仍在运行”也不是该 iOS 成员存活的证明。直到用户催促，Root 才用 `agent://` 读输出；随后 `proc://…/kill` 返回不存在，向成员发消息又被宿主明确拒绝唤醒。

通知为何缺失仍需保留不确定性。历史 `dbd93aa:plugins/omp-host.mjs` 的 `stop` 与当前实现都会压住所属后台工作的自动结果、清理排队的 `async-result`，以防停止后又被结果唤醒。这提供了一条代码上存在的解释，但旧任务目录已不存在，缺停止调用和当时队列记录，不能直接认定这次就是该路径清掉了通知。成员退出时间也早于日志中用户“停”的文字消息，不能把文字消息时间当作最初停止原因。

当前源码已经有两项相关处理：`apply_native_member_observation!` 会将 `aborted` 记为失败；`continuationBlock` 明确说明旧成员已停止，要求通过 `resume_from` 恢复监督，并且不要等待或唤醒旧成员。Git 显示后者在 `d947af6`（2026-10-09）加入，晚于本次 10 月 8 日故障。历史参照 `dbd93aa` 仅用于核对当时已有代码路径，不冒充该会话精确安装身份。

因此本次已定位到的实际错误是：**Root 在没有恢复监督、没有核对成员状态时继续等待，并且忽略了第一次等待超时后的查状态提示。** 当前版本是否仍会发生，需要核对现有续接提示是否实际送达、恢复是否成功、Root 是否读取成员真实状态；不能仅凭旧样本认定还缺一套退出识别功能。EXP-05 已同意的日志应覆盖上述事实；本轮没有修改运行逻辑或新增固定接管时限。

### EXP-08 当前版本复现：退出后仍返回旧的 running 状态

**当前源码存在可复现的状态更新漏洞。** 这不是从 10 月 8 日记录推断：本轮使用当前 `plugins/omp-host.mjs`、真实本地控制 socket 和现有 `omp_native_gate_test.mjs` 的宿主替身，直接验证成员状态读取。没有调用模型或改动产品代码。

复现顺序：

1. 登记正在运行的成员，读取一次 `member_state`，缓存 `running`。
2. 成员变为 `aborted`，发送 SDK 的 `status_changed` 事件。
3. 移除成员登记，发送 SDK 的 `removed` 事件。
4. 再通过控制 socket 读取 `member_state`。

返回结果为：

```json
{"before":"running","actualFinalStatus":"aborted","returnedStatus":"running","attached":false,"retained":true}
```

原因已定位：`subscribeRegistryGate` 的监听回调在事件不是 `registered` 时直接返回，忽略 `status_changed` 和 `removed`。`captureMemberSnapshot` 因此没有保存此次最终状态。随后 `memberDispatch` 在登记已经消失时回用旧快照，并将其中的 `running` 原样作为 `registry_status` 返回。附带的 `retained_snapshot=true` 和 `session_attached=false` 没有让运行时纠正这个旧状态。

本机 SDK `src/registry/agent-registry.ts` 的 `setStatus`、`unregister` 已核对实际发出上述事件。宿主探针最初用非 SDK 事件名查到相同行为，随后改用上述真实事件名重新运行，结果一致；结论依据后一次。临时探针复用既有测试，在完成后删除，没有增加永久测试或新依赖。

再用 `omp_native_member_test.rb` 的宿主替身，将相同的 `registry_status=running`、`session_attached=false`、`retained_snapshot=true` 交给当前 `TaskRuntime.tick`，结果为：

```json
{"saved_status":"registered","saved_registry_status":"running","members_settled":false,"root_messages":[]}
```

这证明运行时会保留成员未结束，且本条状态观察路径没有主动通知 Root。此探针没有启用 JEV，也没有模拟 OMP 独立的结果自动通知；不能据此断言所有实际任务都必然无人提醒。它证明的是：**如果退出发生在两次读取之间，程序已有的状态观察不能可靠识别退出；其他通知没有送达时，这条路径不能补救。** 旧 UC-05 是否正好走到这个漏洞，仍不能倒推。

`orbit version --json` 确认本机安装为 0.8.11、来源 `7a9ca1b81f5e9dfeec17431d18cbc23b497ef49a`。安装目录 `273c361688cd3c39ecc88ca2` 与工作区的快照函数、登记事件过滤片段、成员状态／结果读取实现逐段比较完全相同。因此安装版也包含该代码缺陷；实际探针运行的是工作区源码，不冒充已安装进程的模型实测。带探针的宿主门禁测试及既有原生成员协调测试通过，说明原有通过结果没有覆盖这个缺口。

建议修复方向：使用宿主已经提供的成员状态变化和移除事件，及时保存最后状态；登记消失而最终状态未知时明确返回未知，不能把旧 `running` 当作当前仍在执行。复用现有状态读取和通知能力核对 Root 是否取得变化，不增加统一等待时限。本项缺陷与修复方向已获用户确认，汇总于[已确认改动方案](agreed-change-plan.md)；当前仅落文档，尚未实施代码修改。

后续用户在 S1:2348 要求只测 Android；:2653 明确 iOS 不测、E1 仍继续。Root 虽未继续运行 iOS 应用测试，却仍围绕 E1 runner 签名推进，最后在 :2875 承认误将其作为 Android 前置，:2917 才移除依赖。

区间 S1:2348—2917 中未发现新的 Orbit start/amend 工具调用。三次关键用户消息的 `.orbit/entry/*.json` 均为 `uncertain/root_decides`。这与此前重启失败共同表明：**可见恢复链未建立，不能把该段归入“有监控但没识别”的样本**。入口没有自动启动不等于系统裁定无需监督，而是把是否恢复的决定留给 Root，Root 没有完成恢复。

执行端也须保留用户要求的细节：第二次消息仍保留 E1，因此不能把所有签名调查都叫作违令。明确错误是没有把独立事项和 Android 收口依赖分开，用户不得不再次纠正。

## EXP-09 当前版本核对：needs_user 停止后没有续接入口

当前代码支持已确认停止的普通暂停任务续接，不能把 UC-05/06 的旧恢复失败概括为当前完全没有恢复能力。但另有一个明确的现行限制：任务因需要用户处理而停止为 `needs_user` 后，即使用户补充信息并要求继续，`resume_from` 仍拒绝。

依据与验证：

- `lib/orbit/task_runtime.rb` 接到检查结果 `verdict=needs_user` 时，调用 `stop` 并保存该状态；它不是所有原生提问的通用状态，普通 `ask` 不因此一律停止。
- `lib/orbit/cli.rb` 的 `resume_from` 校验只接受同项目、同 Root、确认停止的 `paused`，明确排除 `needs_user`。本机已安装 0.8.11 的这一段校验与工作区逐字相同。
- `contracts/task-runtime.md`、集成合同与 `docs/plan/debt-ledger.md` 一致记录这个限制。它是已知产品能力缺口，不是代码偏离当前合同。
- 本轮运行 `ruby --disable-gems tests/integration_contract_test.rb` 通过。已有测试使用真实 CLI、运行时与任务存储，分别证明 `paused` 停止后可续接，以及确认停止的 `needs_user` 被拒绝。测试中的 OMP 会话和检查者是替身，不代表真实模型已验证恢复效果。

因此，“需要用户处理 → 用户补充信息 → 沿原要求继续”缺少受支持的直接续接路径。普通新建任务仍可用，不能夸大为程序彻底不能执行；但那不是自动带回旧要求和修订的原任务续接。

进一步核对发现，`needs_user` 不只来自检查者：程序在成员结束而无法接收修订、用户新消息无法读取、旧成员记录不受支持时，也会调用 `stop(..., status: "needs_user")`。这些技术问题是否必须交给用户，当前并未先由 Root 判断。

2026-10-16 用户已确认：检查者和程序提供缺口、错误与状态事实，由 Root 判断自行解决、接手或询问用户；不再仅凭 `needs_user` 自动停止任务。用户答复后由 Root 判断是否足够并继续，既有已确认停止的 `needs_user` 也可沿用现有续接能力。完整方案统一维护在[已确认改动方案](agreed-change-plan.md)，代码尚未实施；上述测试仍只证明修改前的行为。

## 对后续讨论的影响

应分别核查四种能力，不能用一个分数门槛统包：

1. **规则落实与目标判断**：已读到的规则是否约束当前动作；相关但不必要的前置是否在拖延交付。
2. **纠正后的继续执行**：修订是否真的改变依赖、解除阻断并恢复行动；amend、改文档和汇报都不是完成信号。
3. **成员终态与接管**：成员退出、失败、句柄消失能否及时被 Root 识别并处理，避免等待已停止成员。
4. **监督连续性**：用户中断后继续、任务结束后续做、重启失败时，实际执行与活动监督是否重新对齐。

UC-01 已有当前安装版的确定性回放；本页五项已有更具体的执行和恢复原因，但旧 JEV 输入／分数／检查结果仍有缺口。修复后应按这些不同路径验证效果，不能只重跑提交推送案例便宣称整个监控纠偏能力正常。
