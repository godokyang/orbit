## 2. 结论摘要

1. **程序缺陷类诊断可靠，应尽快修，不必等职责调整。** EXP-08、EXP-13、EXP-12 的循环机制都已在代码层核实。EXP-01 的编辑阻断有一个更具体的原因：0.8.5 起的安装回归（见 5.1），可以单独修。
2. **多数方向合理。** 开放取证、完整申诉、取消“远端头 = 本地 HEAD”判据、向 JEV 传用户原话、先补日志、按整项任务看成本，这些都合理。但开放读取缺少数据边界，实施前需要补上。
3. **主要问题是不对称。** 程序侧约束现在就全部移除，而材料中记录的 Agent 判断失败（Root 偏离、检查者误报完成、纠正后不继续）都放到“继续观察”。ADR-011 用作兜底的“Root 事后核对、独立检查”，正是材料里失效过的两个环节。再加上不设硬门、取消自动 `needs_user`，Loom 那种十二小时不收敛的情况，仍然只能靠用户叫停。
4. **EXP-01 矫枉过正。** 主要证据是一个 fail-closed 的安装回归，决定却移除了整套文件名单。由该名单派生的命令沙箱、`.git/.orbit` 保护、断网和凭据剥离如何处理，决定里没有说明；连 Zeen 评价本身也写着“权限不能放松”。
5. **几项实施前必须先定的问题没有写进决定：** 开放读取的敏感数据边界、观察失效时的行为、外部集成方的“等待用户”信号、并行成员的写冲突。

## 4. 核心问题：约束移除与判断纠正不对称

**事实（材料所述）：** 材料中有明确行为证据的失败，大多发生在 Agent 判断层，而不是程序约束层：

- UC-01：Root 追加了不必要的烟测，Root 自己承认。
- UC-02：已读到的 fixture 规则没有落实。
- UC-03：收到修订后停在“口径已改”，没有继续执行。
- UC-04：自行改换了规定工具。
- UC-05：成员已退出，Root 仍在等待，并忽略了等待超时的提示。
- UC-06：误加了前置依赖。
- Loom 22:06：Root 承认重复截图和核验挤占了页面交付。
- EXP-11：检查者没有读原型和相关页面，就给出 complete 和 21 项全部 verified。
- 第一轮把 A 判为完成的，也包括 Root 自己的核对。

**决定的处理方式：** 程序侧约束（EXP-01/03/09/12）现在全部改为由 Agent 判断。Agent 侧失败的对应项则分别是：

- EXP-05：先补日志。
- EXP-07、EXP-10：暂不调整。
- EXP-11：漏判“保留观察”。

ADR-011 承认的代价写的是“通过完整证据、Root 事后核对和独立检查来发现与纠正”，可材料里恰恰是这两个环节失效过。

**推论（推测）：** 这三项叠加起来：

- 不新增预算、次数或时长硬门（ADR-009 补充节）；
- 取消自动 `needs_user` 停止；
- 争议由 Root 处理。

叠加之后，Loom 任务 C 那种运行 12.5 小时、474 次 JEV、22 次裁定（**材料所述**）的不收敛模式，除了 EXP-12 的循环被修掉以外，没有任何新机制能让它比用户更早停下或被发现。这正是产品宣称要减少的成本。

**ADR-011 的论证也有一处跳跃。** 它说这些限制“增加了往返，却没有阻止独立检查漏掉可读材料并误报完成”。成员文件名单、申诉截断和检查者漏读原型是不同环节；前者没能阻止后者，不构成取消前者的理由。取消约束的真正理由是它们的成本（往返、误报、反复申诉），这一点材料有证据支持，应该这样表述。

**建议（不是硬门）：**

1. 在 ADR-011 中写明：信任从程序约束转到 Agent 判断之后，什么让“不收敛”对用户可见。例如在状态里展示自最近一次新增 verified 要求以来的耗时、调用量和用户介入次数，只展示不阻断。这与 ADR-009“分别呈现、不制造综合分”的口径一致。
2. 回答一个优先级问题：EXP-11（误报完成，直接违背产品核心承诺）为什么是“保留观察”，而 EXP-01（摩擦成本）是全面采纳？至少应把 EXP-11 的下一步写成具体调查项（见 5.2）。
3. 有一个值得用日志检验的假设（**推测**）：Root 的过度验证，部分可能是 Orbit 自己的证据规则诱发的。比如 UI 必须读图（CR-03）、产物一变就作废测试回执（CR-04）、unverified 项阻止完成。如果成立，EXP-03 的调整也会减少 Root 偏离。检验方法：核对 Root 追加的验证是否紧跟在检查者的 unverified 项之后。

## 5. 逐项意见

### 5.1 EXP-01：取消成员文件名单——证据主要是回归，决定超出了证据

**已核实：编辑阻断是 0.8.5 起的安装回归。**

- [work-unit-scope.mjs:212–220](../../../plugins/work-unit-scope.mjs:212) 只从 `runners/omp-reviewer/node_modules/@oh-my-pi/pi-natives/native/index.js` 加载 `editInspect`，失败返回 null。
- [:241–242](../../../plugins/work-unit-scope.mjs:241) 拿到 null 就不产生目标路径，[:543](../../../plugins/work-unit-scope.mjs:543) 随即拒绝该 edit。
- `aa089bb`（fix: reuse local OMP，0.8.5，10 月 11 日）之后，[runners/omp-reviewer/package.json](../../../runners/omp-reviewer/package.json) 已没有任何依赖。[manage-install.rb:27](../../../scripts/manage-install.rb:27) 把 `runners/omp-reviewer/node_modules` 列为待清理的旧目录。
- 加载器来自更早的 `715e579`；`aa089bb` 删除了它依赖的三项 SDK 包。[omp-host.mjs:3685](../../../plugins/omp-host.mjs:3685) 对每次成员 `edit` 都接入这个投影。因此从 0.8.5 起的新安装中，只要宿主 SDK 提供 `EditTool`（常规情况），成员的每次 `edit` 都会被拒；开发工作区若残留旧依赖，就会掩盖这一点。
- Zeen 的 12 次 edit 阻断、Loom“edit 无完整目标路径”与此吻合（吻合是**推测**，阻断记录本身为**材料所述**）。

[evidence-review](evidence-review.md#exp-01) 明确写着“本决定替代此前仅修复编辑解析依赖的建议”。也就是说，这个回归在 ADR-011 实施前会一直存在，而 ADR-011 的实施量要大得多。**建议立即单独修复**（从宿主 SDK 解析 `editInspect`，或在装配时提供），与是否保留名单无关。

**决定没有覆盖的部分（已核实）：**

- 名单不只控制文件读写。成员 bash 的 Seatbelt 配置由同一份名单派生，见 [work-unit-scope.mjs:371–396](../../../plugins/work-unit-scope.mjs:371)：写集合、`.git` 与 `.orbit` 的读写拒绝、不放开网络，以及 [:530–532](../../../plugins/work-unit-scope.mjs:530) 剥离继承的凭据环境。
- [resolveUnitScope](../../../plugins/work-unit-scope.mjs:258) 没有缺省值，名单为空时 [:521](../../../plugins/work-unit-scope.mjs:521) 拒绝一切工具。所以“取消名单”在实现上必须选一个默认范围，而合同目标规则只写了“用户明确约束与宿主实际权限继续适用”。如果沙箱随名单一起消失，成员就能联网、带凭据执行、写 `.git`，也能写检查者今后要读作证据的 `.orbit` 记录（关联 5.2）。
- `allowed_commands` 的逐字精确匹配，才是 UC-05 的直接阻断：复合 Git 命令被拒、沙箱拒读 Xcode 依赖（**材料所述**）。决定对此没有表态。
- **用户反馈与决定方向不一致。** [文档对照评估](zeen-orbit-document-assessment-20261015.md)写的是“权限不能放松，但工具应该可靠理解它允许的正常操作”，以及“不是要求削弱验收或权限”。用户（人）有权作出不同决定，但 ADR-011 应写明这里偏离了反馈，并说明理由。

**并行写冲突（已核实未发现相关机制）：** 在 `work_unit.rb`、`work-unit-scope.mjs`、`omp-host.mjs` 中没有找到跨单元路径不相交检查，只有“同一单元不能同时派给多个成员”。原先 Root 至少要声明路径；取消名单后，并行成员在同一工作树里的冲突更难看见，而决定又排除了工作树隔离和自动重置。

**建议：**

1. 先修回归。
2. 把“取消逐文件名单”和“保留执行边界”分开：默认范围取 `artifact_root`，减去 `.git/.orbit`；沙箱、断网、凭据剥离和推送／发布等外部副作用边界保留。
3. `allowed_commands` 单独评估。
4. 记录各成员实际写入的路径，供 Root 事后核对时发现冲突。

### 5.2 EXP-02／04／11：开放只读取证——方向对，缺数据边界和版本边界

- **敏感数据（已核实）：** 现行快照只收 `git ls-files -c -o --exclude-standard` 的结果（[workspace_snapshot.rb:146](../../../lib/orbit/workspace_snapshot.rb:146)），排除 Git 忽略文件；材料还说明快照排除了 `.git`、`.orbit`。目标规则允许检查者读“相关项目文件、任务记录、原生会话”，这会把 `.env`、本地凭据和完整的用户对话交给检查模型。检查模型来自用户的模型池，可以是与 Root 不同的第三方供应商；材料记录 Loom 第 31 次检查用的是 `opencode-go/deepseek-v4.1-flash`（**材料所述**）。决定对此没有任何边界说明。
- **版本：** 目标规则要求检查者“注明版本与来源”，这依赖模型自觉。更稳的做法是：项目文件仍从快照读（快照本来就代表受检版本）；只对快照外的证据位置开放读取，即任务目录、经核实的 Root 会话文件、显式声明的证据路径；同时沿用忽略规则，并记录实际读了什么。
- **锚定：** EXP-11 追查指出，第 30 次检查同样错误地把界面迁移判为 verified（**材料所述**）。让下一轮读取历史 coverage，可能把错误的通过结论延续下去，材料自己也承认了这一点。开放读取解决了“取不到”，没有解决“取到了却不查”。对 EXP-11 的具体调查可以从这里入手：为什么 9 条完成标准被合并成 1 个 coverage 条目，证据却只有依赖和两张无关截图（**材料所述**）？可选的通用做法是要求每个 coverage 条目逐字引用其来源条款。这样合并会变得可见，又不用程序理解业务。是否有效属于**推测**，需要验证。

### 5.3 EXP-03：场景判据——移除规则正确，连事实一起删除过头

- **Git：** 取消就绪判据正确，但目标规则同时删除了远端事实采集。只读检查者没有 shell，`GitRemoteEvidence` 是它独立看到远端状态的唯一来源；有了它，还可以用“交付提交是否是远端的祖先”这样的事实代替头相等。材料内部也有前后不一致：[evidence-review](evidence-review.md#exp-03) 写“不据此自动删除全部场景相关采集能力”，[已确认方案](agreed-change-plan.md)写“删除……专用采集和判定链”。**建议：** 保留事实，删除规则和关键词推断出的义务。
- **UI 图片规则**（[check_runner.rb:1039–1044](../../../lib/orbit/check_runner.rb:1039)）：方案的验收写“视觉呈现、交互、状态变化各有适当证据”，这个方向可以接受。但措辞是“删除所有……一概规定”，容易实施成只删不补。9 月 28 日反馈（“审过材料不等于用过产品”）和 EXP-11 都说明视觉证据是薄弱处。**建议收窄而不是删除：** 关于视觉呈现的结论仍需要视觉证据，否则标 unverified；交互和状态用执行证据。
- **测试回执相关性：** 允许检查者判断版本变化是否影响某次测试，可以减少重跑，但更依赖检查者的判断，而 EXP-11 显示这正是宽松的地方。前提是程序真的提供回执版本与当前快照之间的变更文件清单（方案中的“版本差异”）。这一点应写进验收，而不是交给提示词。

### 5.4 EXP-09：取消自动 needs_user——方向对，两个前置问题没定

**已核实：** 程序直接停为 `needs_user` 的位置有四处：

- [task_runtime.rb:1320](../../../lib/orbit/task_runtime.rb:1320)：成员结束而无法接收修订；
- [:2493](../../../lib/orbit/task_runtime.rb:2493)：旧成员记录无迁移路径；
- [:2512](../../../lib/orbit/task_runtime.rb:2512)：无法观察用户修改；
- [:3305–3306](../../../lib/orbit/task_runtime.rb:3305)：检查者 verdict。

前两处和第四处交给 Root 判断是合理的。

1. **观察失效（:2512）是安全停止，不是“需要用户”。** Orbit 看不到用户消息时，就无法登记修订、无法转达给成员，也可能漏掉文字形式的“停”。目标规则只写了“不能假称继续监督”，没有规定此时运行时是继续让成员执行，还是暂停。实施前必须定下来。
2. **外部集成方会失去信号。** [集成合同](../../../contracts/integration.md) 中，`attention.needs_user` 是外部调用方唯一的“用户相关”信号，而且定义为“已停止终态，不表示等待原生答复”。取消自动 `needs_user` 后，Root 改用原生提问，Loom 手机端这类外部调用方就看不到“有问题在等用户回答”。debt-ledger 正是因为这个场景才记录了 `needs_user` 不可续接。该能力在 1.3 的码表是冻结的，补充需要走次版本。这是功能缺口，不只是兼容写法的问题。外部调用方能否看到原生 `ask`，**缺证**。

### 5.5 EXP-12：裁定交给 Root——诊断成立，补救可以更小

现有设计其实已经支持按版本绑定的裁定：[:3272–3274](../../../lib/orbit/task_runtime.rb:3272) 的注释说明裁定记录的是所裁版本，“later checks can tell reopened evidence”。所以有一个更小的修法与现行语义一致：

1. 裁定只在申诉本身、输入或工作区变化时作废；产物或宿主变化时照常采纳，并按所裁版本绑定，后续检查凭新证据仍可重开。
2. 不再让申诉存在期间的所有检查（包括 JEV 触发的过程检查）都变成裁定（[:2624](../../../lib/orbit/task_runtime.rb:2624)）。

这样就能结束 22 次裁定的循环，不需要新增 Root 工具动作和待处理状态。

已确认方案让 Root 采纳裁定或要求补查。Root 是申诉的一方，而且每次裁定都多一个往返。如果保留这个方案，建议：

- 要求补查必须引用新证据，不能只附理由；
- 把待处理和补查次数显示出来；
- Root 不能借“补查”反复推迟一项维持原意见的裁定。

### 5.6 EXP-05／06：JEV 输入

- **调用频率是更大的杠杆。** 按材料数字推算（**推测**），Zeen 任务 341 次 JEV、7,343,707 input tokens，平均每次约 2.15 万。取消截断会推高单次成本，而每个任务三四百次的调用频率才是主要变量。材料的“现有能力核对”已撤回了几项新增提议，这里不重复提出，只建议日志落地后先统计签名变化来源，再决定输入与频率孰先。
- **外发范围扩大。** 用户新消息原文将外发到 TypeSafe（独立第三方）。合同保留了项目级关闭外发，实施时应在 `orbit jev setup` 或状态中说明外发范围变大了。

## 6. 文档与流程

- **合同可读性变差。** 合同（111 KB，随 npm 包发布，见 `package.json` 的 `files`）在约二十处插入“当前实现／待替换／待取消”标注（按关键词统计得 22 处）。Zeen 文档评估批评的正是“读者要不断分辨现行规则、历史解释和待实现”。目标规则已集中在一节和 ADR-011，正文各段只需一个指针，逐段插注可以去掉。实现完成后，再一次性改写正文。
- **AGENTS.md 未指向 ADR-011。** `11fb125` 的 AGENTS.md 仍写“产品语义由 `contracts/task-runtime.md` 与 ADR-008/009 定义”，没有提到 ADR-011。按 AGENTS.md 进入的开发 Agent 可能漏掉这个替代关系。
- **README 写的是目标职责。** 面向用户的职责表已改成目标职责，附了“尚未全部实现”的说明。可以接受，但安装版的行为在相当长时间内会与表格不符。
- **材料内部漂移。** 除 5.3 的 Git 采集外，EXP-01 从“修复解析依赖”变成“取消名单”，原建议的去向只在 evidence-review 里一句话交代。已确认方案最好列出被替代的原建议，免得实施时只看到新方向、漏掉回归修复。

## 7. 建议顺序

1. 不依赖 ADR-011 的缺陷修复：EXP-01 编辑解析回归、EXP-08、EXP-13，以及 EXP-12 的最小修法（5.5）。修复后先在真实安装上复核阻断是否消失，再评估名单本身还剩多少摩擦。
2. 实施 ADR-011 的 EXP-01、EXP-02、EXP-09 之前，先在 ADR 或合同中定下：成员默认范围与沙箱、命令边界；检查者读取的数据边界与版本来源；观察失效时的行为；外部“等待用户”信号。
3. 把 EXP-11 从“保留观察”改为具体调查项，与 EXP-05 的日志一起推进。
4. 补一个“不收敛可见”的展示项（第 4 节），并纳入 ADR-009 的效果评价。
5. 文档整理放在实现之后。

## 8. 仍缺的证据

- 原始日志、会话与安装目录本机都不可得，第 4、5 节中所有统计、会话行号和模型身份都只能按材料引用。
- 编辑回归与 Zeen 12 次阻断的对应关系：代码路径已核实，现场逐条对应**缺证**。
- 检查者 verdict 为 `needs_user` 的实际频率、外部调用方能否看到原生 `ask`：**缺证**。
- Root 过度验证是否由 Orbit 证据规则诱发（第 4 节假设）：**缺证**，需要日志检验。
- 取消名单后的实际收益：材料中能区分“回归造成的阻断”和“名单本身造成的阻断”的样本很少。Loom 中的 grep／write 越界和 `skill://` 拒绝属于后者（**材料所述**），数量不足以估计净收益。
