## 总体判断

**Orbit 的目标不是单纯“多派几个 Agent”，而是让多模型交付可控、可核验、可追溯。这个方向成立；但目前“证明任务受控”的复杂度，明显侵占了“把用户任务完成”的精力。**

相比第一份，我对它的设计完整性评价提高了，对它的实际交付效率评价没有提高。

## 一、读文档后修正的判断

| 第一份的体感 | 文档事实 | 修正后的判断 |
| --- | --- | --- |
| Orbit 更像监督系统 | 产品明确定位为任务协作、独立检查、纠偏与停止确认，Root 仍负责交付 | 不是定位偏了，而是监督成本与交付收益还没平衡好 |
| 缺少轻量路径 | README 明确允许短任务直接完成；分工也不是强制 | 不能说没有轻量设计；问题是实际执行没有充分采用。我拖慢提交也有明确责任 |
| 已澄清问题反复出现 | 已有 finding 去重、关闭和争议裁定；但不同 ID 的语义重复不自动合并 | 不是完全没做去重，而是去重依赖检查者稳定命名，闭环仍脆弱 |

## 二、真正值得保留的优点

### 1. 把“Agent 说完成了”变成可以核对的交付

Orbit 区分了：

- 成员提交结果与 Root 接受结果；
- 测试通过与用户要求全部覆盖；
- 检查通过与当前版本仍然有效；
- 请求停止与相关执行真正停止。

**这是实质价值，不只是管理形式。** 本次语音环境未打通、录音计时缺画面、原 run 缺终态，都没有被“其他测试通过”抹掉。

但要准确归功：这些边界也来自用户要求和项目规范，不能把全部严谨性都算作 Orbit 的功劳。

### 2. 分工保留单一交付负责人

文档坚持：Root 理解任务、决定派发、集成和验收；成员只做有界工作；检查者独立只读。没有让几个 Agent 互相交接后无人负责最终结果。

这比“自动组队、自动讨论、自动宣布共识”的设计更可靠。来源：[ADR-008](../../adr/008-omp-native-collaboration-base.md#已确认的决定)。

### 3. 模型选择没有伪装成精确科学

文档明确承认：

- 可选模型不等于实际可调用；
- 模型基准不等于本任务表现；
- 目录价格不等于实际渠道费用；
- 未知消耗不等于零；
- 推荐不等于真实采用，更不等于成功。

**这种诚实值得保留。** 但选型记录足够严谨，不代表选型系统已经产生净收益。来源：[ADR-009](../../adr/009-user-selected-model-pool.md)。

### 4. 故障记录与实际安装状态分得清楚

交接文档会明确写“源码修复”“仅隔离安装”“未更新全局安装”“该真实分支未再次触发”。这让后续定位有依据，不至于用“已经修过”否定用户遇到的问题。

这也是我读文档后提高评价的一点。来源：[当前交接](../../plan/handoff.md)。

## 三、最主要的缺点

### 1. 安全约束很完整，但执行顺畅性不足

**我的判断：Orbit 目前更擅长回答“为什么还不能完成”，不够擅长回答“怎样以最少动作满足完成条件”。**

本次正常补丁遇到权限路径识别问题，随后又进入范围解释、历史核对、争议和再次检查。最终 Root 不仅承担产品实现，还承担了监督系统的诊断。

权限不能放松，但工具应该可靠理解它允许的正常操作。无法理解时，应一次明确说明不支持的调用形式和安全接管方式，而不是让成员与 Root 多轮碰壁。

### 2. 纠正机制有去重，但还缺少可靠的收敛

合同按 finding ID 和多项证据绑定去重；不同 ID 的同义问题，依赖检查者自行复用旧 ID。

这意味着：**同一个争议，换个表达就可能再次占用执行资源。** 当前限制也明确承认这一点。

不建议直接让另一个模型“智能合并所有相似问题”。更稳妥的方向是：允许明确关联“这是旧问题的重复项”，保留反证、裁定和重新打开的具体依据，避免每次从头辩论。来源：[运行合同](../../../contracts/task-runtime.md#程序与模型)。

### 3. 内部协议的复杂度泄露到了日常使用

状态、通知、工作单元、模型证据、检查版本、完成通知、停止确认，各自都有合理性；组合起来却要求 Root 记住大量操作细节。

**就在本次独立评价问题中，旧聊天 Goal 的完整要求和依据仍被再次注入。** 这不证明 Orbit 把评价错误地当作旧任务修订，但说明：任务归属即使在逻辑上分开，信息呈现仍然可能干扰当前工作。

用户需要的通常只是：

> 当前结果是什么；还缺什么；谁继续做；下一步是什么。

这些内容应该由系统从权威记录中可靠整理，而不是让 Root 每次重新解释整套协议。

### 4. 产品承诺与收益证据之间还有明显距离

README 的目标是节省顶级模型额度，减少用户催促、转述和核对。限制清单同时承认：

- 整次任务费用可能未知；
- 独立检查投入较高；
- 有负收益对照；
- 效果尚不能推广。

因此目前我会把它定位为：

**有明确控制价值、收益仍待验证的工程工具，而不是已经证明能提效降本的成熟助手。**

本次用户仍然要问进度、问阻断、问未完成项，并提醒“提交怎么这么久”。不论具体责任在 Orbit 还是 Root，端到端体验都没有实现“明显减少用户操心”。来源：[产品目标](../../../README.md)、[收益与限制](../../plan/debt-ledger.md)。

### 5. 文档本身也反映了维护复杂度

当前合同和 ADR 中混有大量历史故障、版本差异、接线细节和补充决定。它们有追溯价值，但读者要判断“现在究竟按什么规则做”，需要不断分辨：

- 现行规则；
- 历史解释；
- 源码修复；
- 安装状态；
- 有界实测；
- 尚未验证的分支。

**文档很认真，但不够容易执行。** 这与运行时频繁需要解释状态的体验是一致的。建议保留证据，但让现行操作规则更短、历史依据单独可查，而不是继续追加长段约束。

## 四、最值得优先改善的顺序

| 优先级 | 改善方向 | 应看到的用户变化 |
| --- | --- | --- |
| 第一 | 正常工具调用与权限声明可靠对接 | 成员不再因已允许操作的解析问题反复失败，Root 不必替工具解释权限 |
| 第二 | 纠正闭环真正收敛 | 已处理问题不会换个编号重新出现；重开必须指出新证据 |
| 第三 | 每次阻断提供明确、可执行的下一步 | 不再只看到“继续、未就绪、等待”，而能知道具体缺口与负责人 |
| 第四 | 大 Goal 与小操作、独立问答分清 | 提交推送不重复展开整套验收；独立问题不被旧任务材料淹没 |
| 第五 | 用整体结果衡量收益 | 比较总耗时、Root 返工、检查开销、用户介入次数，而不是成员数或调用数 |

这些是改进建议，不是要求削弱验收或权限，也不是建议再加一层检查者。

## 最终评价

**我会继续用 Orbit 做长任务、多人协作和高风险交付；不会把它默认用于所有小操作。**

它最有价值的是：**让未完成、未验证、未停止的事实不能被轻易掩盖。**

它最需要解决的是：**当事实已经清楚时，系统能否停止重复证明，迅速推动下一步。**

第一份我说它“像监督系统”；读完文档后的判断是：

> **它已经有一套相当完整的监督设计，但距离“替用户省心的交付系统”，还差稳定的协作接入、可收敛的纠正流程和足够轻的日常操作。**
