# 用户主动纠偏与 Orbit 监控链复核

采集日期：2026-10-15。状态：事实补证，EXP-05 方案尚未定案。Zeen 已有明确用户主动纠偏及可对照的监控记录，本次未扩展读取 Loom。只读核查既有日志和代码，未重新运行任务或修改产品实现。

## 结论

用户主动纠偏真实存在，且不只是状态询问。最完整的当前版本样本中，JEV 持续判断，但未在用户介入前触发针对执行拖延的过程检查；用户介入后 Root 明确承认追加无必要验证并改变行为。历史样本还显示：验收前置解释错误、收到修订后未继续执行、绕过指定工具、无产出成员接管迟缓。

因此 EXP-05 应同时讨论监控漏纠偏、用户纠正后的执行闭环及检查结果过期。仅把它定义为检查太频繁、过期结果太多，会漏掉最重要的一类失败：没有启动相关过程检查，用户却已经承担了纠偏。

## 判定方法与边界

不把所有提问计为不满意。优先选有明确纠正或催促，并可对照前后行为、工具回执及 Agent 承认问题的片段。每项区分：用户发现、系统先前是否已发现、通知是否送达、Root 是否实际改变行动。

原生会话定位沿用[用户消息索引](user-message-index.md)的 S1、S4、S5。表内时间为 UTC，北京时间加 8 小时。历史任务目录缺失时，仅证明原生记录可见的现象，不把没有看到消息当作全程没有监控，也不将历史失败全部归因于当前版本。

## UC-01 根因追查：输入丢失、判断口径与触发断点

继续追查后，已能定位确定性的输入损失和调度断点。整体链路是：Root 在必要合并及主要验证之后继续追加烟测；观察投影丢失完成状态和烟测失败；JEV 返回的风险分未满足过程检查门槛；独立过程检查未启动，最后由用户促成收敛。

这里区分确定性代码行为与语义判断的推断。尚不能从供应商返回的分数逆推出模型内部理由，也未证明修改某一处便足以修复整条链。

### 1. 用户新要求已经传入，不能归因为漏读“提交 + 推送”

任务 `amendments/1.txt` 的完整内容就是“提交 + 推送”。它于 10:47:08 登记，只有这一项 amendment，未触及 JEV 每项 1,200 字符或总计 8,000 字符的限制。11:00 后的漏检发生在修订登记之后。此前约三分半的登记延迟是另一事实，不能解释本段漏检。

第 14 次检查要求继续完成已授权交付，没有新增 finding，也没有要求先排查这次导航烟测。当前证据不支持把 Root 后来的额外烟测归因为该检查强制追加的步骤。

### 2. 观察按长度裁剪，完成状态和失败事实确实会丢失

核对安装目录 `/Users/yangke/.local/share/orbit/orbit/releases/273c361688cd3c39ecc88ca2`。其中 `jev_advisor.rb` 与当前源码完全相同。`omp-host.mjs` 的历史边界与当前源码不同，因此以下回放使用安装版；相关工具输出裁剪与 JEV 预算规则在两版中相同。安装版 `task_runtime.rb` 的过程触发条件也与当前源码相同。

回放直接抽取安装版 `state()` 及 `toolCallSummaries()`，从 S5 原生记录按 `parentId` 还原对应时刻的分支，再调用安装版 Ruby `JevAdvisor.observation_tail`。只重建近期观察投影；没有调用模型，没有恢复当时完整 HTTP 请求、Git 状态或进程瞬时状态。表中时刻附近原生分支稳定，但这仍是日志回放，不是保存下来的请求原件。

具体机制见 [宿主观察投影](../../../plugins/omp-host.mjs:2208)与 [JEV 近期观察裁剪](../../../lib/orbit/jev_advisor.rb:285)：宿主对工具输出保留前 2,000 字符，JEV 再按最新优先、每条最多 1,800 字符和总计 5,000 字符取尾部。选择依据是位置与长度，没有优先保留当前目标、已完成事实、剩余阻断和关键失败。

另一个放大因素：该 eval 调用本身 `isError=false`，因为包装执行成功地打印了子进程失败结果；宿主将其投影为 `completed`。这不等于烟测成功，但烟测失败正文又被截掉，监控因而更难区分“工具调用返回了”和“目标操作成功了”。不能用解析任意输出中的 error 单词替代真实子操作结果。

工具调用摘要只携带名字、声明意图，以及 read/write/edit 的文件路径；bash 命令和 eval 代码不进入摘要。JEV 的观察也不包含 Root 原始验证回执。JEV 本身是一次判断请求，没有独立检查者的 read/grep/glob 补读流程。因此较早回执仍在磁盘，并不代表触发独立检查之前的这一层能补回它们。

### 3. 判断口径未明确覆盖“相关但不再必要的工作”

[JEV 问题](../../../lib/orbit/jev_advisor.rb:24)主要判断两件事：是否无法取得有用进展，以及近期工作是否与最新要求无关或相反。问题还明确提醒普通调查和测试可能相关，单次失败不代表卡住。

这些提醒有合理用途，但没有明确要求核对：已满足哪些交付条件、当前新增动作是否为剩余交付所必需、是否自行增加了前置条件。UC-01 中，烟测仍与修改的代码有关，Agent 也在持续调用工具，实际偏离发生在交付优先级和额外验证范围上。

这是由问题文本和案例支持的设计缺口判断；不能声称供应商明确“因为测试相关而打低分”，因为返回结果没有这项解释。

### 4. 怀疑未达到门槛，独立检查没有机会核实

[过程检查触发](../../../lib/orbit/task_runtime.rb:775)要求最大风险分单次达到 0.85，或连续两次达到 0.65。实际 11:01、11:03 的最大分分别为 0.62、0.63，均将连续计数归零。用户介入后的 0.66 仅计一次，随后 0.52 又归零。

因此本例的直接调度原因已经明确：没有达到进入独立过程检查的条件。它不是独立检查者检查后判错，也不是结果过期或纠偏消息未送达。不能把这些分数说成“证明无问题”，也不能未经效果验证就认定降低到某个新阈值是正确修复。

stuck/off_track 的否定条件都同时包含“证据不足”。本层没有将证据不足单独交给补读取证的机制，独立过程检查仍依赖风险分跨过门槛。输入缺失与低分不升级因而可能互相放大；该机制可从代码确认，其在单次模型评分中的贡献无法单独量化。

### 5. 验证与诊断缺口

现有单测用预设风险分验证调度，例如 0.95 会启动过程检查；这能验证接线，不能证明真实模型能识别本例这种范围扩张。[欠账记录](../../plan/debt-ledger.md:16)仍明确保留“非 stale process finding→纠正→恢复组合未实测”。入口模型放行或成员选择的校准记录也不能代替这条监控链的效果证据。

events 保存分数、用量和 call ID，但没有保存这些调用逐次完整输入或判定理由。这是定位模型判断原因的诊断缺口，不是本次漏检的直接触发原因。本次回放已确认输入投影问题；尚未证明改输入、改问题或改调度中任一单项能够独立解决漏检。

### 待讨论的修复方向

后续已确认先补日志、观察真实调用，输入方案优先评估取消人为截断；具体方案以[已确认改动方案](agreed-change-plan.md#exp-05-已确认的输入方向与观察顺序)为准。下述早期候选不构成立即修改判断或触发机制的决定。

优先让监控保留最新目标、关键完成事实、剩余阻断及实际操作结果，提供回查相关原始证据的路径；判断应明确覆盖额外前置、反复验证和相关支线拖延主交付。证据不足应能进入有针对性的取证，不能只靠提高风险分才有机会核实。

触发策略应基于本例与正常合并、必要测试等对照案例再评估，不能只为命中这一条日志修改阈值。随后验证真实“发现→独立核实→纠正→恢复”链路。以上为本轮建议，尚未采纳，也未修改产品代码或现行合同。

目前可以直接支持的增量是：已确认的诊断记录补缺，以及已复现的观察投影信息损失需要处理。其余项先核对现有机制在实际版本和案例中的失效位置，不作为七项新增功能进入实施。以下是效果评估的分类，不代表相应机制当前不存在。

应把下面几种状态分开评估，不能用“调用了多少次”代替纠偏效果：

1. 尚未识别到用户后来明确指出的问题，如 UC-01。
2. 检查发现问题，但返回时被判过期，未形成当前纠正。
3. 接收了用户纠正，但执行未恢复，如 UC-03。
4. 成员无产出或监督绑定断开，接管没有及时发生，如 UC-05。
5. 系统正式纠正了错误方向，反而制造额外申诉，如前述历史 scope 与推送误报。

EXP-05 的优先目标应是减少用户被迫介入，判断系统能否先发现、给出适当纠正、并看到实际恢复；成本在同一条链路上评估。目前不采纳直接降低分数阈值、延长固定间隔或自动接受全部过期结果的方案，具体方案继续讨论。
