# Zeen 多任务复核：用户介入与监督是否有效

采集日期：2026-10-15。状态：待讨论，不构成修复决定。本文补充[单任务代码与日志复核](evidence-review.md)，纠正其样本过窄的问题。当前任务状态读取至 `2026-10-15T12:03:26Z`；旧文的统计截止点保持不变。下文时间均为 UTC，北京时间加 8 小时。

## 结论与范围

单看 10 月 15 日聊天任务，会低估用户承担的纠偏工作。跨会话反复出现的是：任务范围与验收口径需要用户重申；局部阻断导致整项停工；内部检查状态占据汇报；成员缺少产出时没有及时接管；局部完成与总目标完成被混淆。这些是使用链路上的真实失败，不能用“Orbit 保存了记录、发出了检查”抵消。

但“所有用户介入都代表不满意”不宜作为统计规则。授权、范围调整、主动提供信息和普通询问都可能是正常协作。应优先复核明确纠正、同义重复、催促、以及 Agent 承认前述做法不对的消息，再看前后工具行为。用户询问进度也可能意味着信息不清楚，而非完全没有汇报。

## 纠偏、卡住、协作和停止分别有没有工作

### 纠偏：有真实价值，但“发现、登记、执行、复核”经常不同步

9 月 28 日首轮反馈记录独立检查找出颜色守卫遗漏 `#fff`、登录页文档与实际入口不符。原生 S1:16507 后确有重新启动与多轮检查调用；原始反馈说明第 4 轮完成。当前旧任务目录已缺，本文保留该历史评价的证据级别，不把它重新包装为本次已逐项复跑的代码验收。

10 月 8 日 UI fixture 纠正有原生 amend 通知，是“要求传入 Orbit”的直接证据。但随后仍须用户要求继续，说明监督接受修订与执行恢复不是同一事实。

10 月 15 日的作用可以追到后续行动：过程检查 #1/#4/#6 的历史阻断提示后，Root 分别补充具体可读路径、禁止成员继续尝试宽泛路径、要求失败后返补丁；#7 后 Root 收回和结算相关单元。这支持局部纠偏有效，但 Root 部分集成工作原本已在做，不能全归功于提醒。相反，#11/#12 又把历史 scope 问题当成当前问题，#13 才裁定关闭；#18 推送误报由 #20 推翻。详见旧文 EXP-02/03/05。

评价应记录谁先发现、用了几次用户重申、修改是否传到成员、再次检查是否以新要求为准。仅统计 correction_sent 数量会把反复误报也算作价值。

### 卡住：会保留阻断，不等于能及时解除阻断

两类失败需分开：一类是确实缺设备、权限或正式材料；另一类是方法不当、误加前置、重复检查、没有接管无产出的成员。前者不能随意放行；后者应有继续推进的动作。9 月 28 日录屏、10 月 8 日 fixture 和 iOS 交接都显示，用户在承担判断“还有没有路可走”的工作。

10 月 15 日提交片段提供更直接的当前版本证据：用户 10:43:30 授权提交推送；10:51:20 首次 push 被远端拒绝，之后 rebase 合理。11:00 后又加导航烟测，11:04:59 用户投诉；11:05:21 Root 承认多做不必要烟测，11:05:43 成功推送。此前 15 次 JEV 成功判断的 stuck 最高 0.63、off_track 最高 0.61；投诉后一次为 0.66/0.64。未见投诉前针对该验证拖延的有效纠偏。

这证明该片段没有及时收敛，不证明“耗时长必定卡住”，也不支持仅降低全局阈值。当前 `jev_advisor.rb` 的题义已经禁止仅凭时间判断卡住；需要评估其可见观察是否包含重复失败、没有新增证据、用户此前纠正及当前真正剩余动作。

### 停止与恢复：成功屏障和恢复故障必须同时报告

10 月 8 日出现了三条独立错误：

1. S4:5870：对 task 返回的成员句柄调用 `proc://.../kill`，得到 `Background job or service not found`。
2. S4:5873：随后 `agent://...` 要求停止，得到成员已被 Orbit 停止、拒绝重新唤醒。这个拒绝是保护行为；前一条 kill 失败不能推出成员仍在运行。
3. S4:5882：提交旧单元 failed 结果时得到 `Task does not belong to the current Root on this host`；5887 context 的 `task_directory=null`，5889 改走 takeover 启动后续监督。

因此“Root 已说接管”不足以证明旧成员已停、旧任务已结算、新任务绑定已恢复。该历史片段证明链路不顺，但旧运行版本和全部停止回执不足，不能断言当前 0.8.11 仍能复现同一故障。

反面也有充分的正例：当前 8 个任务中，7 个已结束执行的记录均有 `confirmed=true`、`active_tools_after=0`、`async_jobs_settled=true`；其中 2 complete、5 paused。9 月 28 日 Java 清理的原生 status 也有同样的真实停止字段。它们说明停止屏障确实工作过，不能因为整体体验不好就说“停止功能没用”。仍 running 的聊天任务没有停止确认，不能按对话结束追认为完成。

## 对核心设计的重新评价

Orbit 让 Root 负责交付，成员有范围，独立检查负责核验，程序掌握最终完成与停止。这种职责区分有价值：拒收猜测、保留未验项、真实停止字段都能从记录看见。问题在于各层都可能完成自己的局部动作，而用户的总目标仍没有向前推进。

| 原观点或容易形成的结论 | 本次修正 |
| --- | --- |
| 主要是提示太多、检查太慢 | 不够。还包括目标保持、纠正后的行动、工具与环境选择、恢复绑定及交接接管 |
| 用户介入说明 Orbit 全部没工作 | 不成立。用户调整范围属正常协作；多处范围修订、拒收和停止屏障有直接正证据 |
| 能指出缺少条件就证明卡住判断成功 | 只证明识别缺口。还应核对是否误加条件、是否有可继续部分、是否给出可执行恢复路径 |
| 多 Agent 被启动就证明协作有效 | 不成立。需要可验收产物、及时传回阻断、Root 集成、真实结算，以及对关键路径的贡献 |
| complete 能代表整个长期目标完成 | 只能绑定当次原要求及有效修订。Java 清理案例说明消费状态的一方也会错误外推 |
| 增加检查频率能解决用户不满意 | 未证明。误报、旧证据、归属缺失和高成本验证可能随频率增加而放大 |

当前代码接缝进一步限制了归因：

- `plugins/omp-host.mjs:1565` 已明确要求用户纠正先 amend，并传给活动成员；进度询问不应替换原目标。历史失败提示应验证这条约束是否真正落实，不能说代码完全没有设计该能力。
- `plugins/omp-host.mjs:2266` 输出用户消息归属；`lib/orbit/jev_advisor.rb:205` 的 host 投影只保留 status／turn／active_tools 等字段，未带 `last_turn_task_attributed`。该断层与旧文 EXP-06 一致，不能仅靠把完整目标重复注入解决独立问答和进度询问的区分。
- `contracts/task-runtime.md` 的修订、成员结算、覆盖与完成条款区分输入有效、业务接受、执行终结及完成。历史上的局部 complete 外推，不应通过放松这些门修复；需要正确关联用户目标与当前受检范围。
- 工作区 `task_runtime.rb`、`requirement_coverage.rb` 已有其他未提交修改，本次没有改动它们，也没有把当前源码等同于历史运行安装。
