# Orbit 使用体验：合同、日志与代码复核

日期：2026-10-15。来源：本次 Orbit 仓库会话的只读分析，由用户要求保存。返回[讨论与修改入口](README.md)。

评估对象是 Zeen 使用方的[原始体感](zeen-orbit-experience-assessment-20261015.md)和[文档对照评价](zeen-orbit-document-assessment-20261015.md)。本文保存当次结论与证据边界，不构成已采纳的产品决定或实施授权。

## 总体判断

原评价的总体方向成立，但归因还不够准确。“监督成本侵占交付精力”有日志支持。更深的问题是：部分执行工具接线失效，检查证据在传递中失真，个别完成判据偏离用户要求。这些问题会让 Root 花时间纠正 Orbit 自身。

Orbit 保留目标、独立核验和确认停止的设计有价值。本次应先处理执行接线、证据保真和验收判据，再判断监督投入是否带来了足够收益。不能仅靠增加检查、调整提示文案或合并 finding ID 解决这些问题。

## 成立的判断

### 目标、授权和完成边界有价值

“成员返回结果”“Root 接受结果”“完整验收通过”“实际停止”是不同事实。语音环境、录音计时画面、原 run 终态尚缺证据时，不能因其他测试通过就宣布完成。这符合[运行合同的完成语义](../../../contracts/task-runtime.md#观察与完成)。

不过，Root 已主动报告了多项缺口。保留这些缺口是正确行为，不能全部归功于独立检查者发现了产品缺陷。

### 协作与纠正成本偏高

任务有 5 个工作单元，多项最终由 Root 集成或接管；成员记录有 12 次 `edit` 路径提取阻断；21 次检查中包含 3 次争议裁定。原本用于减少 Root 负担的机制，确实增加了工具诊断和解释成本。

这些数据证明发生了投入，不证明全部投入无价值，也不能直接换算为净延误。

### 尚未证明普遍提效降本

本次没有同条件的直接执行对照，费用也不完整。但日志已有调用数、token、检查时长和接管情况。应区分“可测量的投入”和“尚未证明的净收益”，不能把所有收益问题都归为未知。

模型建议、实际派发、成员交付、Root 接管和最终验收也须分开。工作单元被接受，不等于成员独立完成了整条行为，更不能自动证明节省了顶级模型额度。

## 需要修正的判断

## 原评价遗漏或解释不足的问题

<a id="exp-01"></a>
### EXP-01：成员编辑工具与安装依赖不一致

**已核对事实：** `plugins/work-unit-scope.mjs` 的 `loadEditInspect` 仍从包内旧路径加载：

```text
runners/omp-reviewer/node_modules/@oh-my-pi/pi-natives/native/index.js
```

实际运行的安装目录中该文件不存在，开发工作区中却存在。加载失败返回空值；`createEditProjection` 无法获得检查函数时不产生目标路径，成员路径门会拒绝无法提取完整目标的编辑请求。现场有 12 次对应的 `edit` 阻断。安装版与工作区的这一模块内容一致。

**判断：** 已发现具体的安装接线缺口，可以解释此类编辑失败。不能主要归责于 Root 未写好权限声明。开发工作区的残留依赖还可能掩盖安装后的不可用行为。

**验证边界：** 本次核对文件、控制流和原始阻断记录，没有重新启动真实成员逐调用重放，不能声称其他 scope 拒绝都由此造成。`local://`、`xd://` 越界写入与未声明工具的拒绝须分别判断。

**后续讨论决定：** 用户认为 Root 预先限定成员修改文件会增加调查和授权成本，并限制成员解决问题；已确认取消默认文件限制的方向，由成员根据任务自主决定修改文件，Root 在交付后核对。改错后继续纠正，不增加自动重置，也不为此引入工作树隔离机制。用户明确的任务要求仍需遵守。本决定替代此前仅修复编辑解析依赖的建议；现行合同和产品代码尚未据此修改，安装缺口的历史事实仍保留。

源码入口：[编辑解析加载与权限门](../../../plugins/work-unit-scope.mjs)、[宿主调用接缝](../../../plugins/omp-host.mjs)、[安装管理](../../../scripts/manage-install.rb)。日志入口：任务 `collaboration.jsonl` 的 `work_unit_tool_blocked`、`state.json.member_blocks`、`work-units.json`。

### EXP-02：裁定证据在压缩后失真

**已核对事实：** 第 12 次裁定实际收到的 `checks/12/prompt.txt` 中，1446 字的申诉只剩 62 字前缀和长度／摘要标记。两名成员发生的两次 write 阻断，明细只保留最后一名成员，计数仍为 2。部分权限列表也被压缩。

原始 `state.json` 的该类阻断保留两名成员与两个工作单元。第 12 次裁定却引用压缩后的单成员列表进行归因，之后需要再次申诉。第 13 次裁定才明确指出聚合记录不能证明同一声明错误，也不能把历史 `stalled=true` 当作当前仍在重派。

**代码依据：** `CheckRunner` 对程序上下文设置 65,536 字节预算；多轮降级后继续缩小字符串和列表上限。`dispute` 进入通用 `bound_value`；通用数组取尾部，未为所有关联统计提供逐字段省略说明。

**判断：** Root 看到完整记录，裁定者看到压缩记录，双方没有掌握相同事实。保存了原始证据，不等于检查者实际拿到了足以裁定的证据。模型也有未充分尊重缺证边界的责任；不能把全部问题解释为模型忘记旧结论。

**讨论方向（后续更新）：** 用户提出取消检查者只读工具的快照范围限制，让其主动获取相关原始材料；申诉不应被压到极小长度。后续修改方向为放开 `read/grep/glob` 的只读访问范围，并将申诉原文移出通用字符串减半截断，完整提供，单次输入放不下时分段读取。仍需区分本次受检版本与后来变化，不能将新版本事实追认为旧版本证据。此方向尚未修改合同或实现。

**压缩阈值补证：** 本次申诉为 1,446 字符、2,454 UTF-8 字节，低于初始普通字符串上限 2,000 字符。由于整份程序上下文受 65,536 字节预算约束，类别降级后仍超限时，`reduce_caps` 将普通字符串等上限依次减半至 1,000、500、250、125、62。申诉走通用 `bound_value`，本次实际保留 62 字符前缀及原始长度／哈希标记。不是模型上下文只容得下 62 字符，也不是该段申诉单独超限。按需读取可以减少首次输入，但工具返回仍消耗上下文和 token，不能预先承诺整个检查的净节省。

**讨论补证：检查者能否自行获取完整材料。** 原始要求、有效修订和指定依据已经由 `CheckRunner#build_prompt` 分段完整传入，不受程序上下文的 65,536 字节压缩预算影响；此前提出“需要完整保留这些内容”不应被理解为当前没有实现。被压缩的是申诉、执行与测试回执、成员记录、检查历史等程序上下文。合同要求缺证／压缩缺口保持 unverified，并未授权检查者从缺失材料推断事实。

检查者可以用 `read/grep/glob` 自行读取固定快照内的项目代码、文档和图片，但不能读取原始工作区、`.orbit` 运行记录、原生会话目录或 `/tmp` 材料；没有 shell、MCP 或向 Root 请求证据的工具。`yield` 用于提交结构化检查结论。快照收集排除 `.git`、`.orbit` 及 Git ignored 内容，工具还校验真实路径不得越出快照。第 12 次实际 `evidence.json.active_tools` 为 `glob,grep,read,yield`，且 `read_tool_is_confined` 为 true；其 `scope.json` 保存完整申诉，而 prompt 中仅有截断版本。原件保存在快照之外，日志中可回溯不等于检查者有权限补读。目前没有为这类被压缩的程序证据提供独立的完整原文读取入口。这是证据供给与权限之间的缺口，不能仅要求检查者“自己多查资料”。后续方案尚待讨论。

源码入口：[上下文压缩](../../../lib/orbit/check_runner.rb)。日志入口：`checks/12/prompt.txt`、`checks/12/evidence.json`、`checks/13/evidence.json`，与完整 `state.json` 对照。

### EXP-03：远端交付判据比用户要求更强

**已核对事实：** `root-verifications.jsonl` 中，11:05:43Z 的原生回执证明 rebase 和 push 成功，交付提交为 `a92e520c8e1b4227d9355137afcae034f1499126`。随后同事继续更新远端。11:28:43Z 的回执记录 `git merge-base --is-ancestor <交付提交> FETCH_HEAD` 成功，远端包含该提交。

第 18 次检查因远端分支头与本地 HEAD 不同而提出 `REMOTE-DELIVERY`。第 20 次裁定撤销“头不同即漏推送”的判断，但仍依提示要求保留 `delivery.ready=false`。第 21 次检查沿用了这一限制。

**代码依据：** `GitRemoteEvidence.capture` 只比较本地 HEAD 和远端分支头，相等记 `verified`，不同记 `mismatch`。`CheckRunner#delivery_rules_note` 要求存在推送义务时只能依据该事实，且只有 `verified` 才能 ready。安装版与工作区的这两个模块内容一致。

**判断：** 用户要求“提交＋推送”，没有要求共享分支头永久等于本地 HEAD。这里验证了更强的命题，制造了额外验收义务。程序应提供可核实的事实，不能通过事实检测悄悄替换用户要求。撤销 finding 也无法单独消除这条就绪限制。

**讨论更新：场景修补方案已撤回。** 用户明确拒绝围绕 Git 推送制定专用完成判据。此前提出“远端包含交付提交”以及“有推送成功回执即认可该项”的建议，不作为实施方案。需要解决通用边界：程序记录真实执行及证据来源、版本和归属；独立检查者依据用户原始要求、有效修订和实际证据判断是否满足交付，不由场景专用代码追加验收义务。命令成功仅是执行事实，不能通用地推出用户目标完成。后续应识别其他同类场景判据，区分事实采集与完成裁决；具体改动范围仍待讨论，不据此自动删除全部场景相关采集能力或修改代码。

**最新已确认方向：** 移除 Git 场景专用采集和验收链，按通用执行记录与用户要求判断；不再围绕远端包含提交另建专用放行规则。具体已同意范围见[改动方案](agreed-change-plan.md)，尚未实施。

源码入口：[远端证据](../../../lib/orbit/git_remote_evidence.rb)、[检查提示](../../../lib/orbit/check_runner.rb)。日志入口：上述原生回执与 `checks/18`、`checks/20`、`checks/21`。

### EXP-04：真机与测试证据没有形成稳定的交付链

**已核对事实：** 21 次检查的 `snapshot_image_reads` 全部为空。Root 保留了多张 `/tmp` 截图，但检查者只读固定快照；图片路径或文字描述不等于独立看过图片。

**代码依据：** 检查提示要求 UI 事实必须由实际读取的图片支持。`TaskRuntime#root_verifications_for` 另只取最近 32 条回执，并计算输入与产物版本是否匹配。检查提示不接受被截断或产物不匹配的回执作为执行成功的证明。

**判断：** 要区分真实场景未完成和证据未交给检查者。本次确有语音、原 run 与计时画面缺口，不能因证据交付有问题而抹去；其他已产生的截图和测试结果，也不能仅靠 Root 重述就成为当前独立验证。长任务还存在已做验证退出回执窗口或因后续产物变更而失去直接匹配的问题。

**讨论方向：** 让需要验收的证据可被检查者实际读取，并明确旧证据对哪些未变化行为仍然有效。避免要求 Root 反复口头证明，也不把历史验证冒充新版本全量验证。

**后续已确认：** 沿用 EXP-02/03 的开放只读取证和证据相关性方案，近期回执作为概况，较早记录可从完整原件回查。实施验收应确认检查者能找到并使用早于最近 32 条窗口的有效证据，不因退出窗口就重做验证，不另建专用证据系统。见[已确认方案](agreed-change-plan.md)，尚未实施。

源码入口：[回执投影](../../../lib/orbit/task_runtime.rb)、[视觉与执行证据要求](../../../lib/orbit/check_runner.rb)。日志入口：各 `checks/*/evidence.json` 的图片读取记录、`root-verifications.jsonl` 和补充体验记录中的截图清单。

### EXP-05：过程检查投入与有效产出需要单独衡量

| 当次统计 | 结果与边界 |
| --- | --- |
| 检查总数 | 21 次：11 次过程检查、7 次产物检查、3 次争议裁定 |
| 过程检查过期 | 11 次中 10 次过期；部分仍提供历史提示，不等于全部无价值 |
| Jev 过程判断 | 341 次成功回执；报告 input_tokens 合计 7,343,707，不能直接折算现金或与不同 token 字段无条件相加 |
| 检查累计运行时间 | 过程检查约 14.1 分钟、产物检查约 12.7 分钟、裁定约 9.3 分钟；与 Root 执行存在并行，不是净延误 |
| 自动重复检查抑制 | 13 条 `check_duplicate_skipped`，说明已有去重实际生效，不能说完全没有去重 |

**代码依据：** Jev 判断的签名包含 Root 回合、状态、活动工具、产物及成员事实；实际变化后仍有 60 秒冷却。过程检查保留 host 变化导致的过期判定；产物检查不因纯 host 变化失效。

**判断：** “状态变化”不一定意味着值得再支付一次判断成本。高过期比例反映观察变化、触发时点与结果有效期之间的冲突。没有同条件对照，不能把这些时长和 token 全部判为浪费，也不能据此声称普遍负收益。

**用户介入补证：** [监控链复核](user-correction-monitoring-audit.md)核对了六个明确用户纠偏片段。当前聊天任务在提交拖延被用户指出前有 15 次 JEV 判断、报告 383,701 input_tokens，却未触发针对该拖延的过程检查；Root 在用户投诉后承认追加不必要验证并收尾。这不是检查结果过期能解释的失败。历史样本还存在修订后不继续、工具偏离和成员接管迟缓。EXP-05 需从检查成本扩大到监控是否减少用户被迫纠偏，当前尚未定案。

**讨论方向：** 评估哪些事件能带来可行动的新结论，哪些只应更新状态，以及历史提示实际帮助关闭了什么问题。不能机械增加检查或仅按调用次数追求减少。

源码入口：[Jev 调度与过期处理](../../../lib/orbit/task_runtime.rb)、[观察键](../../../lib/orbit/observation_key.rb)、[过程问题定义](../../../lib/orbit/jev_advisor.rb)。日志入口：`events.jsonl`、`state.json.checks`、`resource-calls.json`。

### EXP-06：独立问答尚未在上下文和调度上充分隔离

**已核对事实：** 用户在 11:10:02Z 要求评价 Orbit，随后要求保存评价、处理其他目录和抓取代码。这些消息没有自动成为旧 Goal 修订。第 17 次过程检查明确说明：Root 正在回答独立评价，不能据此认定旧 Goal 偏航，但该检查已经发生。

**代码依据：** 宿主 `context` hook 对活动绑定任务每次请求追加完整目标，活动分支没有先判断本轮是否为独立问答；暂停分支另有关系限制。`JevAdvisor.observation` 的 host 投影不包含 `last_turn_task_attributed`。相关片段与实际安装版一致。

**判断：** 不能说独立问题已经被当作旧需求修订；语义上确实保留了区别。但旧目标仍可能占据独立问题的上下文，并触发不必要的过程核查。影响不仅是提示冗长，还包括判断消耗。

**讨论方向：** 明确保持原任务目标与正确服务当前独立问题之间的边界，并使过程观察使用一致的任务归属事实。不能因为新问题出现就丢失旧目标，也不能把新问题自动认定为偏航。
