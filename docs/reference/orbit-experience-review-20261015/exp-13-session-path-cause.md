# EXP-13：聊天切换后登记地址未更新，Orbit 读取了旧地址

日期：2026-10-16。状态：已查源码并用本机 OMP 18.9.0 实际复现；修复方案待确认，未修改产品或 OMP。接续 [Loom 记录错指问题](loom-experience-review-20261016.md#exp-13对话证据路径错误)。

## 结论

同一个 OMP 进程新建或切换聊天时，活动会话对象中的编号和文件路径会更新；AgentRegistry 登记条目中的 `sessionFile` 没有同步，仍是创建时的地址。Orbit 按活动会话编号找到登记条目，再取条目里保存的旧地址，于是出现“当前聊天编号 + 旧聊天文件”的组合。

现在不是只根据模拟对象猜测：已在本机实际 OMP 可执行文件中创建隔离会话，调用原生 `newSession()`、`switchSession()`，复现同样的不一致。没有调用模型，也没有向 Loom 的运行进程发送命令。

## 代码如何产生这个组合

核对的是官方发布的 [pi-coding-agent 18.9.0 源码包](https://registry.npmjs.org/@oh-my-pi/pi-coding-agent/-/pi-coding-agent-18.9.0.tgz)，下载内容 SHA-1 与 npm 发布元数据一致：`5c057d3483c5befcef2d159d25f15ea89b85ae5b`。本机可执行文件是 `/Users/yangke/.local/bin/omp`，历史检查记录报告宿主版本为 18.9.0；本次探针直接使用该可执行文件中的 SDK。

| 步骤 | 18.9.0 源码位置 | 发生的事 |
| --- | --- | --- |
| 创建会话 | `src/sdk.ts:4052–4058`、`:4954–4961` | 注册并绑定 Agent 时，将当时的 `sessionManager.getSessionFile()` 保存到登记条目的 `sessionFile` |
| 保存登记值 | `src/registry/agent-registry.ts:141–150`、`:285–299` | 文件地址是单独保存的字符串；`attachSession` 可以更新，但它不是随活动会话变化的取值函数 |
| 新建聊天 | `src/session/agent-session.ts:9837–9856` | 同一 AgentSession 调用 SessionManager 新建聊天，然后同步当前会话编号；此流程没有刷新 Registry 的文件地址 |
| 切换聊天 | `src/session/agent-session.ts:11477–11503` | SessionManager 改为目标文件，并同步编号；Registry 中的地址仍可停在原文件 |
| 活动对象提供正确地址 | `src/session/agent-session.ts:6689–6695` | `session.sessionFile` 直接返回当前 SessionManager 的文件地址；编号也是活动值 |
| Orbit 取值 | [omp-host.mjs:2127](../../../plugins/omp-host.mjs:2127) | 用 `ref.session.sessionId` 匹配当前编号，却返回 `ref.sessionFile`，将两个更新方式不同的值拼在一起 |
| Orbit 保存 | [task_runtime.rb:365](../../../lib/orbit/task_runtime.rb:365) | 保存宿主返回的地址，后续状态刷新仍会取得旧值；不是运行时只忘记刷新一次 |

因此问题有两层：OMP 登记地址没有随会话变化更新；Orbit 对活动会话取地址时，又选择了这份可能过期的登记值，而没有读取活动对象已有的正确值。

用 A、B 代指探针实际创建的两段聊天：

| 操作 | 当前编号 | 当前会话实际文件 | 登记表保存的文件 | Orbit 当前取法 |
| --- | --- | --- | --- | --- |
| 创建 A | A | A | A | A |

第一版探针在写出结果后调用 `process.exit`，被 OMP 的扩展加载保护拒绝。最终保存的是修正收尾方式后重跑的结果：由外部执行器在结果写出且私有会话销毁后结束该探针进程。没有绕过或修改 OMP 的加载保护。

## 与 Loom 现场的关系及限制

Loom 四个任务的当前编号为 `01a13b2f-3721-772d-bebb-434152583e34`，却保存了旧会话 `01a138f1-723b-70f3-8b0d-0bbbdd3f5476` 的文件。当前源码取值路径与探针产生错误的过程相同。

已定位并复现产生该错误的程序原因；历史日志没有保存用户当时具体按了哪次新建或恢复命令，不能声称已还原那个按键时刻。这个限制不影响确认当前实现会在原生会话切换中返回旧路径。

## 修复讨论应以此为依据

Orbit 针对活动会话，应从已经匹配到的活动会话对象取得实际文件地址，例如其公开 `sessionFile` 属性，而不是继续读取登记时保存的字符串。新建、切换后该公开属性已在原生探针中证明跟随更新；这是修正取值来源，不是拿错之后再遍历目录碰运气。

OMP 本身还存在登记信息未同步的问题；若要修上游，应同步会话变化时的登记路径。当前未获得修改或发布 OMP 的授权，本次仅查源码和隔离复现，未修改上游。

历史任务已经保存的错误路径，以及导出发现不匹配后不继续查找的问题，是后续历史记录处理；不能用它们替代上述产生新错误的原因修复。成员退出后只有保留记录的情况也不等同于活动 Root，会话来源应按真实状态核对，不把 Root 修复机械扩展到全部成员路径。

此前“先核对文件，不对再找”的建议仅是补救，不能当成完整根因修复。最新候选方向以本节为准，尚未采纳或实施；讨论状态见[总入口](README.md)。
