# 独立审核后续：仍需判断的四件事

日期：2026-10-16。范围：一手资料检索与本地源码只读核对。本文提供判断依据，不新增产品规则；下文标为“建议”的内容仍待确认。没有调用付费模型、修改产品代码或操作运行任务。返回[讨论入口](README.md)。

## 判断

| 问题 | 本轮判断 | 下一步 |
| --- | --- | --- |
| 开放历史记录能否解决漏判 | 能补信息缺口，不能保证判断正确；历史错误结论也可能影响后续判断 | 优先查当前要求与产物，用历史记录核对变化；用已知漏判样本比较，不加固定审查轮数 |
| 取消文件名单是否等于取消全部权限控制 | 不等于。成员选哪些文件、工具能否写入、数据发给谁，是不同问题 | 拆开处理既有约束，保留用户明确授权；不照搬别家默认沙箱 |
| JEV 应先减调用还是缩输入 | 现在不能确定哪个收益更大；当前已经有冷却和去重 | 先完整记录输入、变化、调用与后续纠偏，再比较成本和漏报 |
| 是否新增统一超时、重试次数或裁定上限 | 资料不能给出适用于 Orbit 的数值，也没有证据支持现在新增 | 先消除已确认的程序重复裁定；明确真实失联时的处理，不能把正常探索当失效 |

已确认的方向仍成立：成员自主实施、检查者自主取证、Root 处理裁定、程序如实提供事实。解除限制后的判断质量需要验证，不能用“权限已放开”作为 EXP-11 已解决的证明。

## 1. 独立检查：历史可以读，结论不能直接继承

**本地事实。** [EXP-11 追查](exp-11-review-trace.md)记录：第 31 次检查完整读到九项标准，但未读取原型和缺失功能页面，把不充分的证据用于整体通过；第 30 次也已误判同一界面迁移完成。当前提示已有逐要求核对、证据不足不能通过的要求。因此，继续补同义提示、逐字引用条款，都没有被证明能解决这次失败。该事实来自已保存的本地追查，本轮没有重跑模型。

**外部资料。** 2026 年的原始研究发现，提供先前评分或错误标签会改变后续模型评判；“忽略旧分数”提示的改善并不稳定。研究也明确：代码评审子类影响较弱且差异较大，数值实验只有 20 份固定文本，不能直接推广到 Orbit。[论文全文及限制](https://arxiv.org/html/2608.25869v1)。

Anthropic 的 Agent 评估指南区分最终环境结果与 Agent 的成功声明，建议检查实际轨迹，并用真实失败校准评估器。它支持检验“证据是否证明结果”，没有证明某个引用字段或固定工具顺序能够保证正确。[官方评估指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

**建议，待确认。** 优先考虑在同一次检查中引导检查者先根据当前要求与实际产物形成判断，再核对旧结论及其证据。历史保留可查，既有有效证据仍可复用，不增加一道必须完成的审查或屏蔽历史工具。实施前用 EXP-11 的已知遗漏作小范围对照：漏掉的页面是否真正被查到、错误通过是否减少、耗时和调用是否增加。对照结果若不支持改善，就不引入这项调整。

**不能得出的结论。** 本轮没有证明 EXP-11 的根因是锚定，也没有证明换模型、加评审席位、强制读图、逐字引用或固定拆条能解决它。引导检查顺序只是低复杂度候选，不能写成已验证修复。

## 2. 自主取证与数据外发：分清具体能力

**源码事实。** [成员工具实现](../../../plugins/work-unit-scope.mjs:371)把文件名单同时用于命令沙箱的读写范围，并拒绝 `.git/.orbit` 访问；[命令分支](../../../plugins/work-unit-scope.mjs:521)还绑定逐字命令名单、无网络沙箱和环境变量清除。这些能力当前确实绑在一起，删除名单时需要分别处理。

**外部资料。** Claude Code 官方文档分别描述文件读取、文件写入、网络和凭据设置，并明确 Bash 沙箱不覆盖全部文件工具、MCP 和 hooks。因此，“shell 已断网”不能证明所有读取结果都不会外发；另一产品的默认配置也不是 Orbit 必须采用的规则。[官方沙箱文档](https://code.claude.com/docs/en/sandboxing)。Anthropic 的工程说明把减少逐次权限弹窗与明确运行权限相结合，说明自主运行与用户授权可以同时成立。[官方工程说明](https://www.anthropic.com/engineering/claude-code-sandboxing)。

**判断。** 放开检查者相关只读工具是合理方向，但只读表示不修改文件；内容一旦送给检查模型，就已进入相应供应商的模型请求。这个事实不能用禁止 shell 联网来替代。用户已授权的任务资料和模型可以直接使用；实际不允许交给该供应商的资料不能因“只读”自动取得授权。无需每次读取都再问用户。

**建议，待确认具体实现。** 利用现有工具回执记录实际读取来源、所属任务、受检快照或活动版本，以及调用模型。能确定的版本由程序提供；对活动文件只能确认实际读取时的内容，不冒充固定快照。检查者自行判断证据是否仍适用。对运行记录的读取与修改也分开：允许查 `.orbit` 不等于允许改写它作为独立证据。这里不要求新建逐文件审批、固定目录白名单或第二套审计数据库。

文件名单取消后，命令精确匹配、网络和凭据处理究竟保留哪些，要按实际授权和需要分别决定。官方资料不能替我们决定一概断网、一概放开或默认只准 `artifact_root`；本轮不将任何一种写成已确认方案。

## 3. JEV：先补完整事实，再比较频率与输入

**源码事实。** [assess_jev](../../../lib/orbit/task_runtime.rb:738)已经按签名去重，并在调用后设置 60 秒冷却。签名含宿主回合、工具状态、产物摘要、输入摘要和成员状态。因此“增加去重”不是现有缺失；签名变化是否意味着对监督有用的信息变化，仍需核对。另一方面，[observation](../../../lib/orbit/jev_advisor.rb:193)仍裁剪指令、依据、修订和成员结果；JEV 的现有请求调用不提供检查者那样的读文件循环。

**外部资料。** Anthropic 的上下文工程说明支持保存原始材料，以路径和工具按需取回；同时指出按需探索有延迟和漏找信息的代价，过度压缩会丢失关键细节。它没有主张无条件把所有历史塞进每次请求。[官方上下文工程说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。早期原始研究也发现信息位置会影响长上下文检索；该结果不能量化当前 JEV 的退化程度。[Lost in the Middle](https://arxiv.org/abs/2307.03172)。

**判断。** 不人为砍掉重要信息，和不反复传整份旧历史，可以同时做到。检查者有工具，可以自主补读；现有 JEV 没有相同能力，单给路径不能代替它应看到的用户原话。先落实已确认的完整日志和用户消息输入，不能为了省 token 再把关键纠正缩掉。

**建议的分析顺序。** 用同一任务记录串起：调用因何触发、实际看见什么、比上次新增什么、给出什么判断、有没有派出检查或纠正、Root 后续是否改变动作。分别计算调用频率、单次输入、缓存用量（能取得时）、实际耗时及真实纠偏效果。先查纯重复和已知丢失信息，再决定是否调整触发；不要同时改频率、输入和阈值而失去比较依据。不能从调用总数直接断言“频率一定是更大的杠杆”。这些是分析办法，不是新增运行硬门或常驻面板。

## 4. 失去监督与重复裁定：故障事实要明确，停止条件不能瞎定

**源码事实。** [collect_amendments](../../../lib/orbit/task_runtime.rb:2501)对 `pending_delivery` 暂时返回，其他用户消息观察缺口直接停止为 `needs_user`。这是当前故障处理，不证明实际发生过用户停止指令丢失，也不能把所有读取失败都解释成整个宿主失控。[已确认 EXP-12](agreed-change-plan.md)已经要求把裁定交给 Root，并避免程序自动重复裁同一申诉。

**外部资料。** Anthropic 的 Agent 模式文章建议依赖环境真实反馈，并介绍最大迭代数等停止条件作为常见选择；它也明确这些模式不是强制模板，增加复杂度应有结果收益。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。这支持保留用户明确预算与停止条件，不能证明 Orbit 应默认增加某个时限或次数。

**建议，待确认。** 故障处理按实际还剩什么能力决定：

- 只是 JEV 请求失败、个别材料读不到，而 Root 仍能接收用户消息并控制成员：把具体缺口交给 Root，允许它恢复或继续不受影响的工作。
- 用户消息补读暂未完成：不能当作“没有新指令”，应保持待补读事实并继续恢复。
- 已确认 Root 与运行程序都不能接收停止/纠正，且无法可靠控制受影响执行：应尝试暂停受影响执行、如实记录暂停是否成功，不能继续宣称受监督运行。这应是控制故障处理，不是让用户回答一个并不存在的问题。故障恢复后的续接需沿真实状态处理，不默认要求人工重新批准。

最后一项需要补查宿主实际能力后才能制定触发条件；本轮没有证明当前某一条错误信息足以判断“全部失控”。后续[本地核对](loom-change-impact-20261016.md)查明：当前 `boundary_not_visible` 是已取得消息列表却找不到旧消息定位点，不足以证明新消息投递或停止控制失效。先写“观察失效就全部停”，会把原先的误停换个名字保留下来。

重复裁定优先落实已有决定：结果送达 Root，等待采纳或基于证据补查；正常工作与检查继续。是否存在 Root 反复要求补查、借此拖延的问题，需要修改后的真实轨迹；当前程序反复判过期的 22 次记录不能证明这种新的失败已经发生。本轮不建议提前新增统一次数上限。
