## 我觉得好用的地方

- **真能找出遗漏。** 颜色检查漏判和登录页文档写错，都是我靠自己收口时可能带过去的问题。Orbit 给出了具体位置和证据，我能据此修改，再让它复核。
- **缺前提时敢停。** 协议缺正式内容、Android 某些验收被设备条件挡住时，它没有把缺口包装成完成。这比一句笼统的“检查通过”有用。
- **有记录可追。** 原始要求、每次检查和纠正都能回看；这次文档任务前后矛盾，也正因为留了两份检查结果，才能指出矛盾发生在哪里。
- **单项检查能守住范围。** 关 Java 进程时，它审的是进程清理；文档任务的前两次检查也没有把旁边无关的工作区改动算成交付。

## 我用起来不顺的地方

- **“检查通过”与“整个任务完成”太容易混淆。** Java 清理通过并不是 UI 项目通过；文档任务两次自动检查给了“完成”意见，任务仍等正式终检。普通用户很难从一句状态提示里看清还差哪一道门。
- **检查可能前后打架。** 文档任务的手动终检把同一份已提交产物判成不存在；先前检查却逐个确认文件。这里不是我还没写文档，而是检查没有看对位置和任务历史。用户要自己找证据、发起申诉，信任会受影响。
- **流程开销可见，收益不总是可见。** 长任务里有频繁的周期性评估，终检也来回数轮。重要错误因此被拦住了，但简单的进程清理或短文档整理走同样重的流程，体感偏繁琐。
- **审过材料不等于用过产品。** 它能核对文档、代码和已有验收证据；但 Stitch 设计出图或文档检查完成，不能证明 46 张画面已在手机上逐页还原、实际可用。

## 四项能力，这次到底证明了什么

| 能力 | 这次的判断 |
| --- | --- |
| 多 Agent 协作 | 四个 Orbit 任务的 `state.json` 均为 `members: []`。有独立检查者，但没有执行成员并行开发或交接；本次**没有验证多 Agent 执行协作**，不能声称它提高了开发吞吐。 |
| 节约时间与 token | 没有同任务“不用 Orbit”的对照，也没有 Root 全程成本口径，**不能算节省率**。它拦下错误，可能减少返工；重复评估、反复检查与这次误判申诉也确实增加了等待和检查开销。 |
| 及时纠偏 | **有真实效果，但有误报。** 项目终检的两处问题被发现并修正；文档终检又出现“已交付却判未交付”。周期评估本身不等于已经主动纠偏，关键结论是在独立检查时产生的。 |
| 判断卡住 | **能识别明确的外部前提。** 协议文本、地址和设备验收条件缺失时，它没有自行降低验收要求。但这次没看到它主动派成员接手或解除阻碍，也不能把“等待检查”和“真的卡住”混为一谈。 |

## 如果我是普通用户，我希望下一步改善什么

1. 每次状态直接写清：“**这次检查的是哪件事、通过了哪些项、整个目标还差什么**”。单项完成、自动检查通过、正式终检通过和停止确认应明显不同。
2. 检查提交后的任务时，先读当前提交里的文件和之前的检查结果；不要只看未提交的差异，更不要凭猜的文件名判定文件不存在。同一产物出现相反结论，应先核对自身矛盾再让用户处理。
3. 只有确实能并行、能缩短关键路径时才建议多 Agent；没有成员就坦白说“这次只有独立检查”，别让“用了 Orbit”听起来像已经多人协作。
4. 把周期性提醒和重复检查控制在有价值的节点。省时间、省 token 应用真实任务作对照后再宣传，不从“检查次数多”或“模型比较便宜”倒推收益。
5. 对 UI 任务分清“材料核对”与“手机实际操作通过”。前者不能自动替代后者。

**总体感受：**我愿意在长任务收口时让 Orbit 再看一遍，因为它确实拦过我漏掉的问题；但就这次而言，我还不会说它证明了“多 Agent 更快、更省 token”。状态表达与前后矛盾的检查，比继续增加检查频率更值得先改。
