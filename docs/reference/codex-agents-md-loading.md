# Codex 中 `AGENTS.md` 的加载规则与编写方法

> 本文说明 Codex 如何发现、合并和应用 `AGENTS.md`，并给出一套适合团队长期维护的组织方式。产品行为以 [OpenAI 官方文档：Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md) 为准；本文依据 2026-08-12 可见文档整理。

## 1. 先记住这几个结论

- Codex 会在开始工作前自动发现规则文件，不需要在每条命令里重复要求“读取 `AGENTS.md`”。
- 全局规则来自 Codex home，默认位置是 `~/.codex/`。
- 项目规则从项目根目录开始，沿目录树逐级加载到**启动时的当前工作目录**。
- 同一目录最多加载一个规则文件，查找顺序是 `AGENTS.override.md`、`AGENTS.md`、自定义备用文件名。
- 不同目录中的规则会合并生效；越靠近当前工作目录的规则越晚加入指令链，发生冲突时也越具体。
- `AGENTS.override.md` 只替代**同一目录**中的普通规则文件，不会自动屏蔽全局规则或上级目录规则。
- 普通 Markdown 文档不会因为被 `AGENTS.md` 链接就自动加载；要实现按需加载，必须写清楚触发条件和读取动作。
- Codex 不会替你对重复规则做可靠的语义去重。重复内容会占用规则容量和模型上下文。

一句话概括：

> 全局 `AGENTS.md` 放少量跨项目通用原则；项目 `AGENTS.md` 放项目增量规则和上下文路由；复杂专项规范拆成独立文档，按任务类型加载。

## 2. Codex 如何发现规则文件

Codex 在每次运行开始时构建一次指令链。在 TUI 中，通常意味着每次启动新会话时重新发现规则。

### 2.1 全局规则

Codex 首先检查 Codex home。默认目录是 `~/.codex`；设置了 `CODEX_HOME` 时，则使用该变量指向的目录。

查找顺序如下：

1. `AGENTS.override.md`
2. `AGENTS.md`

Codex 只加载其中第一个非空文件。因此：

- `~/.codex/AGENTS.md` 适合存放稳定的个人或组织级默认规则；
- `~/.codex/AGENTS.override.md` 适合临时替换全局默认规则；
- 删除或重命名全局 override 后，普通 `AGENTS.md` 才会重新生效。

### 2.2 项目规则

全局规则之后，Codex 会确定项目根目录——通常是 Git 仓库根目录——再从项目根沿目录树向下检查到当前工作目录。

在路径上的每一级目录中，查找顺序都是：

1. `AGENTS.override.md`
2. `AGENTS.md`
3. `project_doc_fallback_filenames` 配置的备用文件名

每一级目录最多加载一个文件。如果找不到项目根，Codex 只检查当前工作目录。

假设目录结构如下：

```text
project/
├── AGENTS.md
├── services/
│   ├── AGENTS.md
│   └── payments/
│       ├── AGENTS.md
│       └── AGENTS.override.md
└── web/
    └── AGENTS.md
```

从 `project/services/payments` 启动 Codex 时，生效顺序为：

```text
~/.codex/AGENTS.md
        ↓
project/AGENTS.md
        ↓
project/services/AGENTS.md
        ↓
project/services/payments/AGENTS.override.md
```

此时：

- `payments/AGENTS.override.md` 生效；
- 同目录的 `payments/AGENTS.md` 被忽略；
- 项目根、`services/` 和全局规则仍然保留；
- `web/AGENTS.md` 不会加载，因为它不在“项目根 → 当前工作目录”的路径上。

这不是递归扫描。若从项目根启动 Codex，位于 `services/payments/` 的规则不会预先加载；只有工作目录位于该路径中时，它才进入初始指令链。

### 2.3 合并顺序与冲突处理

Codex 按“全局 → 项目根 → 更深目录 → 当前工作目录”的顺序拼接规则，越具体的文件越晚出现。

因此，推荐把规则理解为逐层收窄：

```text
Global defaults
    + Project-wide rules
        + Module-specific rules
            + Current-directory override
```

这里的“覆盖”不等于删除前面的文件，而是后面的具体规则在冲突处优先。没有冲突的内容仍会共同生效。

`AGENTS.md` 也不能覆盖更高优先级的平台或系统约束。工程上最好避免依赖隐含的冲突优先级：如果下层规则需要改变上层规则，应明确写出被替代的规则、适用范围和替代行为。

### 2.4 空文件、容量限制和备用文件名

Codex 会跳过空文件。所有项目级规则文件的合并内容还受 `project_doc_max_bytes` 限制，默认是 32 KiB；达到限制后，后续内容可能无法进入指令链。

可以在 `~/.codex/config.toml` 中调整容量或配置备用文件名：

```toml
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]
project_doc_max_bytes = 65536
```

配置后，每一级目录的查找顺序变为：

```text
AGENTS.override.md
→ AGENTS.md
→ TEAM_GUIDE.md
→ .agents.md
```

备用文件名不在配置中时，不会参与自动发现。修改配置后应重新启动 Codex 或执行一个新的命令。

## 3. 全局规则和项目规则如何分工

### 3.1 全局 `AGENTS.md`

只放真正适用于所有项目的稳定偏好，例如：

- 沟通语言和输出风格；
- 通用安全边界；
- 对破坏性操作的确认要求；
- 跨项目一致的工作习惯。

不要放：

- 某个仓库专属的构建命令；
- 某个技术栈专属的编码规则；
- 经常变化的项目目录和负责人信息；
- 大段可以在项目文档中按需查阅的背景材料。

### 3.2 项目根 `AGENTS.md`

项目根文件负责整个仓库都需要知道的增量信息，例如：

- 项目目标和边界；
- 核心目录结构；
- 标准构建、测试和检查命令；
- 修改范围、安全与兼容策略；
- 专项规则文档的触发条件。

项目级文件不会让全局文件停止加载。正常模型是：

```text
Global + Project + Module
```

而不是：

```text
Project replaces Global
```

因此，全局和项目文件不应重复抄写相同规则。

### 3.3 模块级 `AGENTS.md`

只有模块确实存在不同工作方式时才增加，例如：

- 前端和后端使用不同的测试命令；
- 支付模块有额外安全约束；
- 生成代码目录禁止手工编辑；
- 某个子项目采用独立的包管理器。

模块规则应只描述相对上级规则的新增项或差异项，不要复制项目根文件全文。

### 3.4 `AGENTS.override.md`

override 适合“同一目录只能选一套规则”的场景，例如：

- 临时实验；
- 特殊运行环境；
- 某模块需要完整替换同目录默认工作流。

如果只是增加两三条模块约束，优先使用下级目录中的普通 `AGENTS.md`；不要为了“优先级更高”而滥用 override。

## 4. 避免规则重复和上下文浪费

Codex 会拼接发现到的规则文件，不应假设它会先做语义去重。

不推荐：

```markdown
<!-- ~/.codex/AGENTS.md -->

- 简单优先
- 任务优先
- 控制修改范围
```

```markdown
<!-- project/AGENTS.md -->

- 简单优先
- 任务优先
- 控制修改范围
```

推荐：

```markdown
<!-- ~/.codex/AGENTS.md -->

- 优先完成用户当前目标。
- 执行破坏性操作前确认目标和影响范围。
```

```markdown
<!-- project/AGENTS.md -->

- 使用 `pnpm`，不要使用 `npm` 或 `yarn`。
- 修改公共 API 时同步更新 `docs/api/`。
- 涉及数据库迁移时，先读取 `docs/agent/database.md`。
```

判断一条规则应该放在哪里，可以问三个问题：

1. 它是否真的适用于所有项目？是，则考虑全局文件。
2. 它是否适用于整个仓库？是，则放项目根文件。
3. 它是否只影响某个模块？是，则放最靠近该模块的目录。

## 5. 把 `AGENTS.md` 设计成上下文路由器

大型项目不适合把所有工程规范都塞进一个 `AGENTS.md`。更稳妥的方式是让它保存少量常驻规则，同时根据任务类型路由到专项文档。

推荐目录：

```text
~/.codex/
└── AGENTS.md                  # 少量跨项目通用规则

project/
├── AGENTS.md                  # 项目规则 + 上下文路由
└── docs/
    └── agent/
        ├── testing.md
        ├── backend.md
        ├── frontend.md
        ├── database.md
        ├── security.md
        └── architecture.md
```

普通 Markdown 文件不属于 Codex 的自动发现链。只写一个链接，不代表文档内容会自动进入上下文。因此，路由规则必须同时说明：

- 什么情况下触发；
- 必须读取哪个文件；
- 在什么动作之前读取；
- 多条专项规则冲突时如何处理。

不够明确的写法：

```markdown
如果是测试任务，请阅读 `docs/agent/testing.md`。
```

更推荐：

```markdown
## 按需加载规则

在执行下列任一操作前，必须完整读取 `docs/agent/testing.md`：

- 新增或修改测试；
- 修复失败测试；
- 修改 fixture、mock 或 test utility；
- 调整测试框架或测试配置；
- 分析覆盖率；
- 重构测试代码。

在执行下列任一操作前，必须完整读取 `docs/agent/database.md`：

- 修改表结构、索引或迁移脚本；
- 修改持久化模型；
- 编写数据修复或回填脚本；
- 调整事务边界。
```

这样形成的流程是：

```text
启动 Codex
    ↓
自动加载 AGENTS.md 指令链
    ↓
识别当前任务涉及的行为
    ↓
按明确触发条件读取专项文档
    ↓
应用专项规则执行任务
```

### 路由规则的设计要求

- 使用可观察的动作描述触发条件，不要只写“复杂任务”“必要时”等模糊表述。
- 同一专项文档尽量只由一个清晰入口负责，避免循环引用和多层跳转。
- 路由到的文件应聚焦单一主题，不要变成另一个超大的规则总集。
- 路径必须从项目上下文中可解析，并在移动文件时同步更新。
- 如果“读取全文”是必要条件，应明确写出，不要只写“参考”。
- 对高风险任务，除了要求读取文档，还应写清楚停止条件或需要的确认。

## 6. 推荐模板

下面的项目根模板可以直接裁剪使用：

```markdown
# AGENTS.md

## 项目目标

- 用一到三条说明项目解决什么问题。
- 明确当前仓库不负责什么。

## 基础工作流

- 安装依赖：`pnpm install`
- 本地检查：`pnpm lint`
- 核心测试：`pnpm test`

## 修改边界

- 优先完成当前明确需求。
- 不主动重构无关模块。
- 新增依赖前先检查仓库现有能力。
- 可能影响现有调用方时，先说明兼容风险和影响范围。

## 按需加载规则

- 新增、修改或修复测试前，必须读取 `docs/agent/testing.md`。
- 修改数据库结构、迁移或持久化模型前，必须读取 `docs/agent/database.md`。
- 修改认证、授权、密钥或敏感数据处理前，必须读取 `docs/agent/security.md`。
- 调整跨模块边界或公共抽象前，必须读取 `docs/agent/architecture.md`。

## 完成标准

- 核心行为已经实现。
- 已运行与修改风险相匹配的检查。
- 未修改任务范围之外的文件。
- 未验证项和剩余风险已明确说明。
```

模板不是越完整越好。删除与项目无关的条目，比保留“可能以后有用”的规则更可靠。

## 7. 如何隔离全局规则

截至本文整理时，官方文档没有提供一个只对当前项目关闭全局 `AGENTS.md` 的独立配置项，例如：

```toml
inherit_global_agents = false # 当前不是官方支持的配置
```

确实需要完全独立的 Codex 配置时，可以切换 `CODEX_HOME`：

```bash
CODEX_HOME="$(pwd)/.codex-home" codex
```

这会切换整个 Codex home，而不只是 `AGENTS.md`。其中的配置、技能或其他依赖 Codex home 的内容也可能随之变化。因此，它更适合隔离的自动化账号、测试环境或明确管理的项目配置，不应作为日常去重手段。

## 8. 验证规则是否正确加载

不要仅凭文件存在就认为加载成功。可以在仓库根执行：

```bash
codex --ask-for-approval never "Summarize the current instructions."
```

验证子目录规则：

```bash
codex --cd services/payments \
  --ask-for-approval never \
  "List the instruction files you loaded, in precedence order."
```

重点检查：

- 全局和项目规则是否都被识别；
- 当前工作目录是否正确；
- 同目录的 override 是否替代了普通文件；
- 子目录规则是否只在对应路径中生效；
- 是否因容量限制发生截断；
- 修改规则后是否启动了新会话。

若结果与预期不符，可依次排查：

1. 当前目录和项目根是否正确；
2. 文件是否为空；
3. 上级目录或 Codex home 中是否存在意外的 `AGENTS.override.md`；
4. 备用文件名是否已加入 `project_doc_fallback_filenames`；
5. `CODEX_HOME` 是否指向了另一个目录；
6. 规则总大小是否超过 `project_doc_max_bytes`；
7. 是否仍在使用修改规则之前启动的旧会话。

## 9. 常见误区

### 误区一：项目规则会替代全局规则

不会。全局规则和项目路径上的规则通常会合并。只有同一目录内，`AGENTS.override.md` 才会替代普通 `AGENTS.md`。

### 误区二：Codex 会递归加载仓库里的所有 `AGENTS.md`

不会。它只检查“项目根 → 当前工作目录”这条路径，不扫描兄弟目录，也不预加载当前目录以下的所有规则。

### 误区三：链接了专项文档就等于加载了专项文档

不会自动加载。应把链接写成明确的行为指令，并给出可判断的触发条件。

### 误区四：规则写得越多越安全

规则过多会增加冲突、截断和注意力稀释风险。高价值、可执行、与作用域匹配的规则更有效。

### 误区五：上下级重复可以“加强记忆”

重复会消耗容量，也容易在未来形成多个不一致的事实来源。需要强调时，应说明风险和原因，而不是复制整段规则。

### 误区六：修改 `AGENTS.md` 后当前会话会立即重建指令链

Codex 通常在运行或 TUI 会话开始时发现规则。规则出现陈旧时，应从目标目录启动新会话，而不是假设当前会话已经重新加载。

## 10. 提交前检查清单

- [ ] 全局文件只包含真正跨项目通用的规则。
- [ ] 项目文件只描述项目增量，没有复制全局规则。
- [ ] 模块规则位于最小有效作用域内。
- [ ] override 的使用确实需要替代同目录规则。
- [ ] 每条按需加载规则都有明确、可观察的触发条件。
- [ ] 专项文档路径存在且没有循环路由。
- [ ] 规则使用可执行措辞，避免“尽量”“视情况”等无法验收的表达。
- [ ] 没有把可由 formatter、linter 或 CI 自动保证的细节全部塞进上下文。
- [ ] 合并后的规则大小没有超过配置上限。
- [ ] 已在项目根和关键子目录分别验证实际加载结果。

## 总结

合理的 `AGENTS.md` 体系同时解决三类问题：

1. **规则复用**：全局原则只维护一份；
2. **作用域管理**：项目和模块只增加必要差异；
3. **上下文控制**：专项规范按明确条件加载，减少常驻 token 消耗。

最终推荐结构仍然很简单：

> 少量全局默认规则 + 项目增量规则 + 模块差异规则 + 明确的按需上下文路由。
