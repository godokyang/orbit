## 当前重构方向（2026-09-13 讨论确认）

本节记录用户已确认的方向与最小验收，不代表能力已实现，也不签发产品合同变更或开工授权。后文 D1–D11 和旧阶段保留为既有依据；涉及差异时先修订对应 ADR／合同，再实施。后续沟通保持简短，重要问题逐项讨论，不重复确认已有决定。

### 目标与独立性

Orbit 帮助用户高质量完成需求、自我纠偏、减少人工介入并节约供应商额度。取舍看执行、监督、返工与人工介入的整体成本，不以保留旧架构或增加协议完整性为目标。

Orbit 是可独立用于任何项目的执行工具，不依赖 Feedback 或任何外部前置审批、后置验收流程。项目、需求、授权和运行环境可以直接提供。Feedback 是接入方：它拥有反馈业务中的讨论、授权与人工验收；Orbit 唯一负责授权内的执行调度和纠偏；执行服务负责实际 Agent 接入、工具执行及事实采集。这些执行能力必须能脱离 Zeen 使用，Feedback 专用字段与业务状态留在适配层。Orbit 执行完成不依赖 Feedback 接收结果；接入后的业务状态由 Feedback 映射，不能再独立维护一套成员调度与完成决策。Herdr 只作本地观察与介入入口。

### 运行方式（已确认）

受控任务从 Orbit 入口启动。每次任务由独立的 Orbit 运行进程陪同整个过程：启动并协调 Coding Agent、接收实际结果、到约定时间触发检查、处理纠正和停止，任务结束并完成必要收尾后退出。Root 忙于执行时，这个进程仍能接收事件和处理到期检查，不依赖 Root 主动调用。程序等待不调用模型；需要语义判断时才使用模型。

独立使用可由用户直接启动，也可由 Coding Agent 通过 skill 在已有执行授权内自主调用 Orbit；不要求用户另开终端手动启动。Skill 负责何时调用、如何传入需求与约束，持续运行、到期检查和执行控制仍由 Orbit 进程承担。讨论本身不授权开始执行。接入 Feedback 时由适配层调用同一执行入口，不重复建设业务调度。

用户选择的方向是：已有 Coding Agent 调用 skill 时，默认沿用当前会话担任 Root，保留现有上下文，通过通信与控制通道接入 Orbit。新建 Root 同样需要通道，不能只因参考代码已有创建路径就强制交接。此前“第一版新建任务专用 Root”的建议未获采纳。具体会话绑定、途中消息投递、状态观察和停止能力仍待核实；能发送消息不等于已经能可靠阻断执行，不宣称现有任意会话均已受控。若接入受限，应说明具体缺口，不静默改为新建 Root。

该选择不新增常驻监督模型、开机常驻平台、Root 自动替换或故障恢复；具体 Agent 接入、命令参数及停止能力仍待验证。选择理由：连续观察需要真实运行主体，同时按任务启动和退出避免将独立使用绑定到外部服务部署。参考调研见[同类项目运行方式](../reference/orbit-execution-host-research-20260913.md)，并非决定引入其依赖。

### 暂停粒度（已确认）

普通纠正先向 Root 发送消息，并核查调整结果。必须停止时，暂停承载受影响工作的 Agent 当前执行，保留会话与上下文，并确认相关后台命令实际停止；其他独立 Agent 的无关工作继续。若几条工作混在同一个 Agent 当前执行中，则一起暂停，不增加按语义切断单条支线的复杂机制。程序执行已有授权边界或有效纠正裁定对应的控制动作，不自行猜测工程语义或扩大暂停范围。该决定明确最小控制粒度，不代表现有接口已通过真实停止验收。

### 检查与执行的关系（已确认）

常规检查与执行可以同时进行：检查者只读一份固定的当前产物，不修改代码，Root 继续推进。检查发现问题后，先核对最新产物中是否仍存在，再落实纠正或暂停；不能仅凭旧版本的问题控制已变化的当前工作。交付前核对实际交付版本，不能直接沿用不再覆盖当前内容的旧结论。理由是减少等待，同时保证检查对象明确。该方向需要调整 ADR-006 的同 Task 串行语义；具体快照与绑定方式未定，当前运行时代码与合同尚未修改。

### 执行输入（已确认）

Orbit 在用户要求执行时接入，保存用户原始执行指令，例如“按照这份文档执行”或一段 prompt。自检与独立检查直接对照原始指令；指令引用文档时读取对应原文，Root 的计划或摘要不能替代它。执行中用户明确修改要求时，保留该修改指令作为后续检查依据。

需求讨论和确认由用户与当前 Agent 完成，Orbit 不接管讨论、不审查讨论是否充分、不收集整段历史聊天，也不要求用户另填需求表。此前提出由通道保存需求讨论的设想退出方案；这里保留的原始内容限于执行指令及其指定依据。

### 额度与时间（已确认）

以高质量完成需求为优先。任务开始时粗估供应商消耗与完成时间，作为计划参考；预估不是硬上限，超出本身不触发暂停、额外审批或降低验收。无法准确估计或观测的用量标明未知，不用耗时或测试规模冒充 token，也不因缺少准确数字阻塞执行。

完成后对照最初预估与实际可得消耗、耗时，简要分析偏差原因，例如需求变化、低估难度、返工、等待或检查开销，并据此改进下一次估算和执行方式。中途调整预测时保留最初预估，避免覆盖偏差；执行、检查与纠正的投入合计观察，不因拆分工作或更换会话清零。先复用任务记录形成轻量优化循环，不另建统计平台或强制复盘审批。

执行中仍及时纠正无效重复、过度测试和无关优化，不等任务结束才处理。只有用户另行明确指定的硬资源上限才作为资源停止条件；默认预估不产生这样的边界。

### 重构与兼容边界（已确认，2026-09-14）

本次重构不保留旧版兼容。按新方案确定不再需要的入口、别名、字段、协议分支和实现直接删除，相关调用、规范、示例与测试同步调整；不增加兼容适配层、双轨运行、旧格式解析或仅为续用旧数据而建立的迁移机制。既有调用不是保留淘汰设计的理由，实施时说明破坏性变化并更新本仓调用，不为同一兼容取舍重复请示。

复用以新方案仍需要的实际能力为依据，不以“旧代码已经存在”作为保留理由。删除的是淘汰能力及其负担，不扩大为清理用户项目数据、覆盖用户自定义规范或删除当前有价值的规范和交接资料。本轮仍只收敛方案，取得实施授权后再执行代码删除与合同修订。

### 第二轮评审收敛（已确认，2026-09-14）

用户同意补清三个接缝：原始执行消息原样传入，不用 Root 摘要替代；Root 与检查者取得同一有效版本的相关项目规则；检查需要运行测试时，不干扰正在执行的工作区。输入只覆盖本次执行指令与明确修改，不扩展到需求讨论；项目规则不恢复已被用户明确否定的时间硬门、多数裁定或 Root 自动替换。默认只读检查固定产物，确需补执行验证时使用隔离副本／资源或无写入冲突的时段，不强制每次建 worktree。

保留“检查者误报被推翻后可正常完成”的验证方向，优先复用相关确定性测试，不另开必需的真实实验。第二轮其他故障体系、固定止损门等扩展未采纳；详细依据见[第二轮评审记录](../reference/orbit-refactor-challenge-20260913.md#第二轮2026-09-14-最新收敛稿与角色模型建议)。

### 本轮只做的闭环

1. 保存原始执行指令及执行中的明确修改，按指令读取指定依据，防止计划或摘要替代用户目标。
2. 推进执行并自动收集实际结果，减少 Agent 手工维护引用、证据和协议记录。
3. 首个能看出方向的结果出现时，以及准备交付时，按需启动独立检查；很小的任务可合并为一次交付检查。检查直接看原始需求与实际结果，发现做偏、漏做或多做；不常驻、不逐步审查。
4. 问题交 Root 修正，独立核查修正后的实际结果；确认需求完成，或在明确授权／资源边界处停止。

独立检查由程序可靠触发，不依赖 Root 记得申请。程序负责投递、关联、动作权限和阻断控制，模型负责语义判断。有效阻断可以限制受影响动作或完成声明，不能默认停掉无关工作。

压力测试确认：另设连续的观察安排，避免 Root 迟迟不交首份结果而没有检查。到约定时间检查当前进展，任务仍在执行且允许继续时，根据检查结果安排下一次时间，如此持续到完成或停止；由 Orbit 在原授权内安排，并遵守用户另行明确指定的硬资源上限，不反复要求用户确认。观察间隔随工作情况调整，不把耗时本身判成失败；检查消耗计入原任务累计投入，不能借重新约定时间重置投入或反复拖延处理同一阻断。超出预估不自动停止，见「额度与时间」。

Root 与检查者分歧先补事实；仍影响交付时按需独立裁定。裁定者可以在既定需求和授权内推翻任一方，不按票数，也不要求双方同意。相同产物与依据下不重复重审，只有新证据或相关变化才重开。裁定不改变目标、验收或权限；普通工程偏好不升级为阻断，只有真实产品歧义或授权缺口才交用户。此处确认的是职责边界，具体实现尚未冻结。

压力测试确认：Root 多次未落实已经裁定的纠正时，停止受影响的工作、保留上下文，并向用户报告具体问题，接受必要人工介入；不无限提醒，不自动替换 Root。不为此另设统一重试次数。

### 机制取舍与暂缓事项

| 处理 | 当前结论 |
| --- | --- |
| 保留 | 原始要求、授权与版本关联；独立评审、纠正落实与真实结果验证；已有有效上下文和产物 |
| 简化 | 模型维护协议的劳动由程序承担；检查按需启动并复用仍有效的结论，不为形式增加团队或评审轮次 |
| 改变 | 测试数量／行数不再作为默认硬门；同失败第三次尝试不再默认要求额外授权；额度与时间采用预估、实际对比及偏差改进，预估不作为硬门 |
| 不新增 | Root 自动替换；Root 运行故障自动恢复；复杂风险评分或大规模基准平台 |
| 新增重点 | 不依赖 Root 申请的独立检查，以及发现偏差后实际修正、复核的最小闭环 |

Root 运行故障仅记录为暂缓事项，不设计、不实现、不纳入最小验收。理由是用户尚未遇到该问题，上下文保留时人工重启心智成本很低；复用已有记录和工作目录，不另建恢复体系。此前提出的自主替换 Root 方案退出当前范围。

压力测试确认两项产品改造方向：

- **测试规模**：测试数量／行数回归工程建议，不再作为默认要求人工批准的硬门。独立检查结合需求和实际影响判断是否过度测试；用户明确设定的资源上限仍须遵守，不把测试规模冒充供应商用量。
- **重复失败**：取消同失败第三次尝试必需额外授权的默认规则。继续前先判断：不解决这个问题，是否会导致本次需求无法完成，或留下与本次任务有关的已证实重要回归？只有确属当前交付必须解决的问题，才进一步判断新证据、解决方向和剩余资源；这些条件成立时在原授权内继续。仅为更完善、更漂亮或增加无真实风险依据的边界覆盖，记录后停止该支线并回到主任务。没有新依据、只是重复尝试时先诊断或调整路线。需要扩大授权，或无法自行推进时才交用户；更换 Agent、会话或工作拆分不能清零同一阻断的累计投入。

新加测试失败本身不证明它是交付阻断，先核查测试必要性；既有必过检查不能随意绕过。独立检查同时判断当前工作是否值得继续，发现测试或优化持续增加却没有推进需求时，及时停止无必要的支线，不等资源耗尽。不能仅凭“有新证据”授权无限打磨；此判断属于模型的语义职责，不以测试数量、代码行数替代。

以上是已确认的改造方向，尚未修改代码或签发 ADR／合同修订；实施前对齐 ADR-006 及相关合同，现行运行时仍按旧合同执行。cross-control 残留、规则快照和命令形态的改造仍是候选，尚未逐项批准删除或替换。

### 最小验收

先在普通项目独立验收，再验证 Feedback 适配；不以 Zeen 业务流程作为独立验收前置。

- **发现遗漏并交付**：需求含两项明确行为，预置只覆盖一项的中间产物，Root 未主动申请检查。程序触发独立检查，真实 Agent 根据原始需求发现遗漏，Root 组织补齐，验证和独立复核对应最终产物；无需用户提醒即可交付并完成必要收尾。
- **该停时能停**：触及事先明确的授权边界或用户明确指定的硬资源上限后，停止相关执行和新增消耗，核实实际停止，保留产物并说明具体缺口；不能仅凭停止请求声称已经停止。额度与时间预估不是该场景的停止条件。

确定性测试验证程序接线与边界；真实模型路径验证能否识别并纠正偏差，两者分开报告。真实实验前冻结任务、供应商和停止条件，记录额度与时间预估；用户明确指定硬资源上限时一并遵守，不强制将预估设为上限。额度不可见就标未知，不用耗时或测试行数冒充 token。两条路径通过不直接证明普遍节约额度，实际收益另看可得消耗、返工和人工介入；完成后进行预估与实际对比，沿用「额度与时间」的轻量优化循环。

本轮只收敛方案，不实现、不启动 Goal、不运行真实模型实验、不提交推送，也不机械续做阶段 H。后续先明确最小闭环对应的 ADR／合同差异与接入边界，取得实施授权后再开发。

### 最终使用过程

用户给出执行指令 → 当前 Coding Agent 通过 skill 启动 Orbit 并继续担任 Root → Orbit 保存原始指令、粗估时间与消耗 → Root 推进任务，Orbit 到期或收到代表性结果时安排独立检查 → 修正并复核实际产物 → 交付、必要收尾、对比预估与实际。

模型承担需求理解、工程取舍、检查及必要裁定；程序承担消息和时间触发、实际状态与产物采集、记录关联、已确定动作的执行。等待不调用模型，检查不要求 Root 停工；暂停按上节已定粒度执行。用户可直接使用同一入口，Feedback 仅映射输入与输出。

- **只用已有 Codex 套餐**：当前 Astra Root；常规执行可用 Terra；独立检查与必要裁定用 Astra 的独立会话。小任务可由 Root 直接实现，不强制额外执行席位。实际模型以账号可用范围为准。
- **复用多个已有供应商**：当前 Astra Root；执行选已接入工具中的 GLM-5.3，明确的小任务可用 DeepSeek-V4.1-Flash；独立检查先用 Astra，其他合适检查模型在实际任务中验证后调整；必要裁定再启用独立强模型会话。OMP／OpenCode 等属于 Coding Agent 工具，与模型名称分别说明，不能把示例写成已完成接入清单。

四种职责不要求四个常驻席位或四种不同模型。检查独立性还依赖直接读取原始依据和实际产物，不共享执行者的结论作为唯一前提；相同模型的独立会话也不能证明推理错误完全独立。模型选择随真实任务的完成质量、漏检与误报、返工、耗时和可得消耗调整，使用既有收尾记录，不另开大规模模型评测，不自动启用未授权供应商或最高推理档。

### 最小实施顺序（待实施授权）

1. **定稿本次合同差异和接入验证范围。** 按上述已确认决定修订相关权威，不重写整套合同。暂定优先验证已有 Codex Root 的原生接入；其他供应商按实际需要接入，不承诺第一轮全覆盖，不改变用户供应商授权。
2. **先打通现有会话的通信和暂停。** 在明确指定的执行会话中验证消息到达、状态与结果回传、当前执行及关联后台动作停止、上下文保留。验证无需复杂需求；若接口不足，报告具体缺口，不静默改成新 Root，也不假装受控继续后面的实测。
3. **做一条完整执行与纠正链。** 原始指令 → Orbit 任务进程 → 当前 Root → 真实产物 → 独立检查 → 修正复核 → 完成。接上约定时间检查、自动记录、实际产物绑定和新取舍；不先完成全部底层整理再接真实执行。
4. **跑两条最小验收并收尾。** 沿用上节“发现遗漏并交付”和“该停时能停”，不新增一套阶段门；同次任务记录预估和实际偏差。通过后整理实际支持范围、skill 操作方式及受替代路径，未通过则只处理阻断该路径的问题。
5. **再验证 Feedback 适配。** 使用同一执行入口检查输入和结果映射，不增第二调度循环。真实修改 Zeen 与联调需要对应授权；在此之前可以完成 Orbit 独立验收，不把外部接入作为前置。

### 验证范围与停止加码的条件

真实路径 A 用两项明确要求，检查实际未提交的中间产物中预置的一项遗漏，Root 不主动申请检查；到约定时间触发检查并安排下一次观察，发现后补齐，复核最终产物。同一条路径覆盖输入完整性、途中触发及版本对应，不另开大量合成任务。真实路径 B 使用事先明确的停止指令或授权边界，确认相关执行与后台动作停止、上下文和产物保留；不以超出粗估作为失败条件。

程序接线、旧硬门变更及版本／停止边界用相关确定性测试验证，优先复用 `contract_test.rb` 的现有 projection/control/store 测试，更新已改变的旧断言，不绕过 validator 让测试通过。真实 Agent 路径另报模型实际表现；测试替身不能替代消息投递、纠偏和停止验证。既有有效测试通过后，只因新修改或具体未解决风险追加验证，不追求覆盖率或全供应商矩阵。

最终审阅材料只需：实际完成的行为、两条路径的结果、支持的接入范围、已删除能力与破坏性变化、未决项，以及预估和实际偏差。两条路径成功不证明普遍节省额度；后续从真实任务反馈改进，不增加常驻评审席位或复盘审批。

## 0. 目标定义

产品目标（owner 2026-08-17 确认）：

> **Orbit 是一个能在合理范围内自动实现需求代码的控制流。目前所有的控制都是为了这个目的；事实可追溯、不可抵赖等是附属好处，不是目标。**

这个定位改变了完成度的算法：evidence/gate 那条脊柱是**基础设施**，控制循环才是**产品**。

### 验收（两个场景，缺一不可）

**场景 A（能跑完）**：给一个真实的小需求，Orbit 无人值守运行，产出通过独立评审的代码，以 `completed` 停止。

**场景 B（能停住）**：给一个会漂移或超预算的需求，Orbit **在边界处停下**，以 `frozen` 或 `needs_user` 停止，并说明缺什么。

场景 B 比 A 更重要。愿景不是"能自动化"，而是"能在**合理范围内**自动化"——边界才是产品。只有 A 通过而 B 不通过，等于造了一个跑得更快的失控循环。

## 2. 关键设计判断（讨论结论，作为计划前提）

**Orbit 不能让 AI 在循环中持续守规则。** 它在 agent 外层，够不到内循环。它能做且只能做三件事：

1. **投递**：attempt 开始时交付 bounded context（含钉死的规则）；
2. **让 attempt 短到规则不失效**：这是 bounded work unit 的第二个理由——规则第 1 轮注入、第 40 轮已被稀释（ADR-003 引的多轮下降与 Lost in the Middle）。**规则的生效方式是每次 attempt 重新投递，不是持续约束**；
3. **事后独立复核**：评审者与实现者对同一份规则字节。合同机制是 `closure_basis_digest` 冻结 `assigned_rule_resolution_ref`（`contract.yaml:937` 的 `closure_basis_freezes` 五元组之一，`effective_verification_plan_digest` 是同组的另一元素而非绑规则的那个）。评审者自己的 attempt 仍有独立 rule resolution，可用 `baseline` 列入同一批规则、`supplements` 叠加评审规则——`RELATION_PRECEDENCE`（`rule_resolution.rb:14-18`）支持这个形状。

**控制代码不判断"符不符合规范"。** ADR-003 决策九：机械规则只管 refs/digest/lineage/cardinality/budget 记账；语义判断属 Lead，verdict 属独立评审。原文："软判断不得伪装成 validator correctness。"

**推论：循环的质量上限由评审 agent 的判断力决定，而规范文件是评审者的判据。** 所以 `references/` 是产品的有效载荷，控制代码是运货车。**规则不到位时先做 runner，等于自动化地产出不受约束的工作。**

**规则是项目里的真实文件。** `rule_resolution` 存 path + content_sha256，用 `project_root/path` 的真实字节重算比对。后果：改规则文件会让使用它的新 dispatch fail closed——**改规则是有版本的事件，不是静默编辑**；且任务化切分能让规则演进只影响相关 attempt。

## 3. 计划

五个阶段，按依赖排序。每阶段先设计后实施，沿用既有 Gate 模式。

### 阶段 G：规则库最小可用集

**为什么排第一**：它是有效载荷；且规则会被 sha256 钉进每次 dispatch，切错了比代码写错贵。

#### 裁决 1（2026-08-17）：规则文件装进用户项目，随项目版本化

依据是既有合同已经做过这个选择。`rule_resolution.rb` 的 `canonicalize_path!` 叠了三条约束：路径必须是项目相对 POSIX 路径（禁 `..`、禁绝对路径）；要过 `File.realpath` 解析符号链接；解析后必须仍在 `project_root` 内（L142）。digest 重算也从 `File.join(project_root, path)` 读真实字节（L59）。

因此：

- **装进项目**：原生可用，零产品改动。
- **留在 skill 目录**：当前合同直接拒绝——skill 路径无法表达成项目相对路径，符号链接会被 `realpath` 解析后落在 root 外而被拒。走通需要放宽这条路径契约，而它同时是防逃逸边界，属安全相关的产品变更。
- **hybrid**：基线部分撞同一堵墙，另加来源解析歧义（同一 `rule_id` 两来源谁赢、digest 记谁的）。

"单一来源"的真实诉求是**分发**，但用运行时共享解决它在 Orbit 里是反效果：规则被 digest 钉死，共享目录一改，所有项目的判据在无人复核的情况下静默改变——正是 alpha #7「审核标准移动」的机制。

**分发方式**：skill 目录保留母版，身份从运行时来源降级为分发来源。`init` 拷入项目（`init` 本就是每项目必跑，不新增步骤）；后续用一条更新命令拷入新版本，在项目里产生**可评审的 diff**。规则变更因此是有版本、能被看见、能被拒绝的事件。

旁证：DeepSeek 的 11 个 skill 同样放在仓库内 `.agents/skills/`；[Codex AGENTS.md 加载规则](../reference/codex-agents-md-loading.md) §3 的"项目增量规则"也预设规则随项目走。

#### 裁决 2（2026-08-17）：结构做完整重切，投递按 4–5 条控制

两件事分开定，因为代价曲线相反：

- **结构改动的代价随时间上升**。规则被 `content_sha256` 钉死，改一个字会让引用它的新 dispatch fail closed。370 行一个文件意味着改一条测试取舍规则会连带作废所有引用 `coding-guideline` 的 attempt。**细粒度切分不只是上下文经济，是变更隔离**。所以结构一次做对，原三个角色文件（coding 370 / testing 267 / quality 264）退役。
- **内容扩张的代价可以摊开**。初始只把 4–5 条接进 `dispatch` 默认；其余重切后的文件先落地不接线。在规则能被循环检验之前建全套投递，是 alpha 第 5 条"先把底座加固到很深，核心循环没接上"的重演。

即：**重切保证不丢内容，限额约束投递面**。

#### 三层结构

```text
常驻层     项目 AGENTS.md ——极短，只写项目增量 + 路由触发条件
任务规则层  dispatch --rule 的目标 ——每任务一文件
参考层     深度材料 ——只在规则显式指向时读
```

体量纪律取自 deepseek-harness 的经验值（14 个 AGENTS.md 共 500 行，根 149；11 个 skill 共 957 行，最大 146）：**任务规则单文件 ≤150 行，常驻层 ≤150 行**。对照现状，Orbit 单个 `core-operating-model.md` 947 行比对方整个 AGENTS.md 体系还长。

需要区分两条投递通道，不要混谈：[Codex AGENTS.md 加载规则](../reference/codex-agents-md-loading.md)描述的是 Codex 的**自动发现链**（路径决定、常驻、32 KiB 上限）；`--rule` 是**另一条通道**（按 attempt 显式钉入、digest 验证、控制流投递）。两者的关系是：该文档误区三指出"链接了专项文档 ≠ 加载了专项文档"，路由仍依赖 agent 自觉去读；**Orbit 正是这层路由缺的强制力**——不让 agent 自己决定读不读，而是投递内容并记录投递了什么、评审者拿到的是否同一份。因此 Orbit 的规则文件应照该文档 §5 的**专项文档**设计（单一主题、明确触发条件），而非照 `AGENTS.md` 本身。

#### 单文件模板（D8：八项必备 + 三项条件性）

**本节是模板规格的唯一出处。** 工单只引用，不复制。

必备（每条规则都要有）：

0. **所有权边界声明** —— 开头一句写明本文拥有什么、不拥有什么。范例（`zeen/docs/agents/AGENTS-*.md` 三份文件逐字相同的那句）：*"本目录只拥有 agent 的读前置、决策流程、交付门与禁止行为。产品事实、模块关系、技术选择由 X／Y／Z 拥有，本目录只链接锚点，不复制正文。"*
   **对 Orbit 尤其重要**：规则被 digest 钉死，一条开始断言产品事实的规则就变成冻结的第二真值源——改产品事实要么改不动，要么作废所有引用它的 attempt。边界声明是防这个的最便宜手段。

1. **`description` 前言块** —— 供 dispatch 机器选择，`Use when...` 句式。这是从"人读"到"机器选"的最小必要改动。
2. **判据** —— 一句可判定的测试，而非"应该／不要"。优先写成反事实提问（"删掉它谁会坏""删掉之后还能不能从别处读出来"）。范例是 vantage test：*could a reader at HEAD, with no access to any session transcript, PR thread, or uncommitted draft, resolve every reference and verify every claim?*
   **目标形态是「问题 → 判定 → 动作」三段式**，`zeen/docs/agents/AGENTS-development.md` §二是现成范本：*"这个抽象现在有真实调用方或真实复用吗？没有 → 不写。""是在为未知未来或假设场景设计吗？是 → 删掉。""旧代码路径还有实际调用方吗？没有 → 删除，不加兼容层。"* 该节整体声明"规则为判据式：通不过判据就不做"。
3. **反向约束** —— "什么不算"，且**每项要给放行依据**。对必然被检索探针命中的项直接标注"会被永久命中，别每轮重推"，让自动循环里的评审者停止反复重判同一件事。**对自动循环最关键的一项**：全是禁令的规则会让评审者一路 block 到底，正是 alpha #8/#10 的机制。
4. **降级路径** —— "够不上就降级到哪"。范例："想法对但太小 → 改成 TODO"。避免评审者只能放行或 block 的二值化。
5. **规则内优先级** —— 写进规则的止损条款。范例：*"一份带一个已证实阻断项的短评审，好过一串鸡毛蒜皮"*、*"少数已证实的候选胜过一堆薄弱猜测"*。
6. **自我限定句** —— "本文是判断依据，不是可以机械勾选的清单"。规则声明自己不是清单，才挡得住机械执行，与本仓库 `AGENTS.md` 防"为测试而测试"的立场同源。
7. **升格条件** —— 什么情况停下交给人。两段式：
   - **何时算真边界**：只有当两个以上版本都满足规则、但在已接受的原则之间做了不同取舍，且本规则没有直接裁定时才算；**有唯一答案的改写不是边界情况**。
   - **停下时交什么**：payload **按升格类型分型**，不是一种格式打天下。三型各有出处：

     | 升格类型 | payload | 出处 |
     | --- | --- | --- |
     | 裁不了的缺口 | 问题 + 2–3 个候选 + 各自代价 | `zeen-module-handbook:29` |
     | 报一条缺陷 | 位置（文件:行）+ 可自己复现的证据 + 影响 | `zeen-change-review:44` |
     | 发现范围外问题 | 问题描述 + 影响范围 + 建议方案 | `zeen/docs/agents/AGENTS-development.md` §三 |

     缺口型在交付摘要里单独列出。配套禁令：**不自选答案**、**不含糊绕开**（"按需返回""视情况"这类措辞被点名）。裁定后**删干净**，不留"原本这里有一条，现已裁定"。

条件性（适用时才写，不适用不要凑）：

8. **反问法警告** —— 存在"看起来对但会给反答案"的判据时，点名它并说明为什么错。范例：*"不要用「这句话会不会被改写」提问——它对动机是实现绑定、但内容是对外承诺的句子给反答案。要问「删掉它谁会坏」。"*
9. **反发明边界** —— 规则要求补充／重述内容时必写。界线：*只记录已经发生过的备选，不发明；原文里的否定句本身就是备选记录，提取重述是重构不是发明；引入原文之外的辩论是越线。* **必须给逃生口**——"判不了就写「未记录」"，否则 agent 会为了填格子而虚构。
10. **过度纠正陷阱** —— 清理／删除／精简类规则必写。五个：把义务改成许可、把设想说成已落地、删掉一条真事实、丢了出处、**删掉修复承诺却不修缺口**。第五个是自动循环特有的。

另有一项属于写法而非结构：**判据前先做语料分类**。先把消费者分成 production / non-production / ambiguous 再判断，把"有没有消费者"从主观变成可核查。适用于所有需要举证的规则。

### 阶段 I：bounded runner（先用 stub 执行器）

**为什么在真实执行层之前**：runner 的正确性是确定性的、可精确测试的；真实 agent 不是。用 stub 先把四个停止态、checkpoint 追加、预算累计测准，比掺进 agent 的非确定性后再调试便宜得多。

按 ADR-006 冻结的形态实现外层驱动：

```text
collect authoritative facts → reconcile → 受控 writer 原子 compare-and-append
accepted checkpoint → 执行恰好一个允许动作 → 下一轮
```

四个互斥停止态：`completed` / `blocked` / `frozen` / `needs_user`。

**stub 执行器的硬约束**：必须显式标注为临时、写明移除条件，并在阶段 J 移除。coding-guideline 明确禁止"为了通过 E2E / dogfood 加业务层兜底，掩盖 runner、schema、状态机、provider、tool 或真实入口未接通"——stub 若留成永久件，本计划即自我违规。

**交付**：一条命令能把一个 task 驱动到四态之一，预算/熔断/continuation 首次可达。

### 阶段 J：真实执行层 + 可信观测

**最大且风险最高的一段。唯一没有任何现成实现的部分。**

两个必须同时解决的问题：

**启动**：怎么真正拉起一个 coding agent（herdr pane / 子进程）。先读 `8b5ab8c^` 的 3,202 行。

**观测**：自动循环里 evidence 谁写？如果由干活的 agent 自己写，就是自报——违反 Orbit 全部前提。ADR-006 已定调："计数只来自真实 change surface 与 trusted provider（CI/test-runner 的 provider-verified 计数、repository 权威扫描），**不信 agent 自报**。"

所以执行层不只是启动器，还需要**可信观测者**（测试运行器、仓库扫描器）把 agent 的产出变成 provider 验证过的事实。

**这一步顺带解决一笔欠账**：阶段 D 的本地 provider（"一致性机制而非安全机制"）在此处升级——观测者本身成为 provider，事实来源从"CLI 递什么就签什么"变成"测出来什么就是什么"。这是[欠账台账](./debt-ledger.md)第 1 项"替换真实 provider"的真实解法，不需要单独立项。

**前置未知（必须在 J.1 设计时正面回答）**：ADR-002 已经推翻了 ADR-001 的 automatic session refresh，结论是"真实 Herdr 不提供对应信任原语"。因此**被拉起的 agent 的 provider-verified runtime subject 从哪来，是一个开放问题**，可能是本阶段最硬的一块。若答案是需要新的信任基础设施，停下上报，不要顺势建。

**交付**：`dispatch` 真正拉起 agent；evidence 从观测事实派生而非自报；stub 移除。

## 3.5 候选能力增量（2026-08-17 识别，**未承诺范围**）

来源：`/Users/yangke/Personal/omen/zeen/.agents/skills/`。这三项不是规则内容，是**控制层能承载的产品能力**，各自需要独立设计闸门后才进入范围。此处只记账，不排期。

### 可数的完整性下界

`zeen-doc-authority` 的"验算"：*"同步出边至少落 5 个文件……只改了一个文件的依赖边改动一定是漏了。"*

这打破了本文第 2 节的二分法。控制代码确实不能判断"改得对不对"，但**完整性下界是语义来源、机械可查**：判定"这是不是依赖边变更"需要判断，一旦定性，"至少动 N 个文件"控制层能数。

Orbit 现状：`CodeSurface` 记录改了哪些路径，但不问某类改动的完整性下界。这可能是成本最低的一次能力增量。

**开放问题**：下界从哪来？项目自己声明（配置）还是从规则文件里读？谁有权改它？

### `needs_user` 的 payload 规格

Orbit 有 `needs_user` 停止态，但没规定停下时必须交出什么。`zeen-module-handbook:29` 的格式可直接采用：

```text
待裁定：<问题> —— <2–3 个候选与各自代价>
```

配套禁令：不自选答案、不含糊绕开（"按需返回""视情况"被点名）、裁定后删干净不留痕。

**为什么重要**：没有 payload 规格的停止态，人接手时仍要重建全部上下文——等于没停对地方。

### Finding 质量门槛与多评审仲裁

`zeen-change-review:44`：*"每条缺陷 = 位置（文件:行）+ 证据（能自己复现的）+ 影响。三样缺一样就不是缺陷，是意见。"*

Orbit 的 `Finding` 是类型，但没有准入门槛。三要素可作 gate 的机械准入判据（"证据能自己复现"这一条尤其对治 agent 自报）。

仲裁规则（同文 §收口）也是缺口——Orbit 保证评审者独立于产出者，但两个评审者冲突时无规则：

- **可复现的缺陷一票即成立**，不看其他评审是否发现；
- **判断分歧才按多数**，且落败方理由要记录，否则同一分歧下轮重来；
- **收口方自己核过再采纳**——复核者也会报错误的缺陷。

## 3.6 规则字节漂移与共享正文（D11，2026-08-17 实测后裁决）

### 实测事实

阶段 G.2b 跑了这条路：dispatch implementer → 改 `rules/minimal-implementation.md` 一个字节 → dispatch reviewer（继承 subject 已记录的 `required_rules`）。

结果失败，`rule_resolution_digest: rule content_sha256 does not match canonical rule bytes`。

炸点是 `RuleResolution.build`（`rule_resolution.rb:88-89`）：它调用 `canonical_identity` 时不传 `verify_files:`，默认 `true`（L21），于是重读当前文件、与继承来的旧 digest 比对、在写入 control store 之前就 fail closed。比 `control_store.rb:2267` 那条更早，`if policy` 根本没走到。

### 裁决 1：fail closed 是正确行为，不削弱

Orbit 结构上拒绝记录一个与磁盘不符的 pin。规则以 **path 交付**，agent 读的是路径上的文件——文件改了，agent 读到的就是新字节，此时还钉旧 digest 只是记录一句假话。

因此"评审者与实现者同一份字节"只在任务期间规则文件不变时成立。文件一改，那些字节真的不存在了，系统拒绝假装是诚实而不是缺陷。

补救是**重新分派**，不是把校验放宽。任何"让继承路径跳过 `verify_files`"的改法都会让 pin 与磁盘脱钩，被否决。

### 裁决 2：升格 payload 格式抽成一份共享钉入文件

G.1 设计稿原方案是把三型 payload 表逐字复制进全部 8 份规则。**否决**。

先纠正一个直觉错误：抽成共享文件**并不减小爆炸半径**。复制进 8 份时，改表等于改 8 个文件，所有在飞 subject 中招；抽成一份每次 dispatch 都钉时，改它等于改 1 个文件，但所有 attempt 都钉了它，同样全部中招。两者完全相同。

决定因素是**单一事实源**：8 份手工维护的副本会漂移，而这正是规则库自己要教人避免的失败（源素材"字段族和单一事实源"一节已归 `structured-boundary`）。用一个违反该原则的结构去承载教该原则的内容，站不住。

落法：`skills/orbit/assets/rule-library/shared/escalation-payload.md`，随 `init` 拷进项目 `rules/`，每次 dispatch 以 `relation: supplements` 钉上。这引入一个新类别——**被钉的共享层**，区别于 `resident/`（不被钉）与 `tasks/`（按任务选）。

**留在各规则文件里的**：何时算真边界（升格触发条件）。那是规则特有的判断，八份各不相同，见 G.1 设计稿 Q1 升格表。
**移出到共享文件的**：停下时交什么（三型 payload 的格式与禁令）。那是统一协议，与具体规则无关。

### 未采用

- 放进不被钉的常驻层（项目 `AGENTS.md`）：改它永不破坏任何 attempt，爆炸半径为零。但常驻层靠 Codex 自动发现，"链接不等于加载"，投递不可靠——升格格式会变成看运气的东西。
- 把升格格式产品化进 `dispatch` 输出：投递可靠且零 pin，但让 Orbit 在代码层对 agent 输出格式定型，与"规则是项目可编辑的文件"冲突，且超出 D10 的承诺范围。
