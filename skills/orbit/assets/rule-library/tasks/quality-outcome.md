# 质量结果

**所有权边界**：本文只拥有「成功标准是不是可判定的质量属性，以及哪些完成方式无效」。内部结构由程序整理。对照已有标准做检查归 `review`。实现归 `minimal-implementation`。停下与交接见 [共用职责](../shared/escalation-payload.md)。

本文是判断依据，不是可以机械勾选的清单。复核只报告不修改。明确执行指令可以开工；不要为补结果表停下。

## 判据

- 原始指令、指定文档或用户明确修改，能不能判断「变好了」或「做完了」？能 → 用它当成功标准，不要另填表。
- 完成标准写的是动作（拆文件、加测试）还是质量属性？是动作 → 把动作当手段，用用户要的结果当标准。
- 删掉一条阈值，检查者还能不能判断结果变好了？不能 → 标准不够，但只在它真实影响执行时才询问。
- 某个完成方式属于无效完成吗？触发 → 即使做了动作也不算完成。
- 缺少固定字段、数字阈值或无效完成列表 → 由程序整理内部结构；不要编造阈值和没人走过的无效完成。

## 反问法警告

不要问「动作做了没有」。它对「7000 行变 6900 行」给反答案。要问「维护者 / 用户现在少读或少受什么罪」。也不要问「表填齐了没有」。

## 反发明边界

补无效完成或被否备选时，只记录已经出现过的失败方式。判不了写「未记录」，不要发明一套没人走过的无效完成。

## 反向约束

| 看起来像标准不够 | 为什么放行 |
| --- | --- |
| 阈值不是数字，但检查者能判断变好 | 阈值不必是数字 |
| 原始指令没有固定结果表 | 明确指令可以开工 |
| 已有冻结合同上的实现任务 | 本文不在实现过程改标准 |

## 降级路径

- 说明只有动作没有结果 → 按原始指令执行，把动作当手段；不要因此拒绝开工。
- 两个解释都能量化「变好」，但选哪一个会改变任务范围或授权 → 交用户。
- 发现原设计不可行 → 说明具体缺口，不在代码里静默缩小目标。

## 规则内优先级

质量结果是完成标准，动作是手段。先识别无效完成方式，再写要实现什么。

## 升格条件

只有当两种对原始指令的解释会改变范围或授权时，才算边界。缺固定结果表仍开写实现，不是边界。

## 无效完成要写具体

每个改善类任务用已经出现过的无效完成，而不是空表：只抽无状态 helper、只减单次成本却增加失败率、只换文案但路径仍不清、只补 try/except 但状态不可恢复、只加 facade 但旧路径仍写权威结果、只加 mock happy path。
