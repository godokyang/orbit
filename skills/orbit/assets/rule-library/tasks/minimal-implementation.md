# 最小实现

**所有权边界**：本文只拥有「这处改动是否满足当前任务的最小变化」。根因归 `targeted-fix`；写不写测试归 `test-selection`；对外命名归 `vantage-audit`；名单／字段族／旧路径关闭归 `structured-boundary`。停下与交接见 `rules/escalation-payload.md`。

本文是判断依据，不是可以机械勾选的清单。复核只报告不修改。不要为了让 diff 看起来更完整而制造改动。

## 判据

先把被讨论的符号、抽象或依赖的消费者分成 production / non-production / ambiguous，再问：

- 当前依据是原始指令、指定文档和用户明确修改，还是模型计划？是后者 → 回到前者。
- 删掉这处改动，原始指令里哪一条会失败？指不出 → 不写。
- 更小的改动能满足同一条要求吗？能 → 选它。
- 这是只为当下、下一轮注定整段替换的壳吗？是 → 换成能留下的路径。
- 这个抽象降低了当前复杂度、满足实际边界，或复用了已有成熟能力吗？都不是 → 不引入。不要用「还没有第二个 production 调用方」禁止有价值的封装。

## 反问法警告

不要问「这样是不是更完整 / 更通用 / 以后更好改」。那个问法对「单一用例上的提前抽象」给反答案。要问「删掉它谁会坏」。

## 反向约束

| 看起来像多余 | 为什么放行 |
| --- | --- |
| 复用项目已有 helper / 模式，即使多碰一个文件 | 复用降低已经存在的复杂度，不是为第二个实现预留 |
| 清理本次改动造成的 unused import、dead branch、fixture | 精准修改的一部分 |
| 原始指令或项目既有模式已经要求的接口、配置、扩展点 | 需求已在指令里，不是发明未来 |
| 项目流程或本任务明确要求跑 formatter，因而改动了格式 | 格式探针会永久命中这些 diff |

## 降级路径

- 想法对，但删掉它当前要求仍成立 → 不写进本 diff。需要记住就记已知缺口，不升级成抽象。
- 修复或实现开始级联到无关模块 → 范围外问题，本任务不改完。
- 风格偏好、注释拼写、import 顺序 → 不改，也不报缺陷。
- 多个实现都满足原始指令和当前任务范围 → 选更小或更能复用现有能力的，继续做。

## 规则内优先级

先保住指令内最小可验证、且不注定被替换的变化。一处能指到原始要求的删除，好过一组指不到要求的「以后会用到」的新增。

## 升格条件

只有当取舍会改变目标、验收或权限，或引入当前任务未覆盖的真实风险时，才算边界。普通工程选择不是边界。有唯一答案的改写——删掉无条款可指的 service、strategy、provider、base class、interface 或配置层——不是边界。

## 先读再写

写之前读改动面：目标文件和相邻实现、同类 route / service / test 的既有模式、文件顶部 imports、相关测试里的真实预期。代码库没有可复用模式时，说明这一点并给出最小一致方案；不要默默引入外来风格、库或架构。

先查现有能力，再决定改什么。按完整用户行为完成所分配工作，不要按按钮、路由或测试文件机械拆开后只做一半。明确执行指令可以开始实现，不要为补结果表停下。

## 精准修改

不改无关文件、无关命名、注释拼写或 import 顺序。不跑会重排大文件的 formatter，除非项目流程或当前任务明确要求。没写进明确排除范围的原始要求默认仍要满足；发现原设计不可行时说明具体缺口，不在代码里静默缩小目标。

## 依赖

新增依赖前先证明：项目已有能力、标准库或平台 API 不够用。确实新增时说明原因，并同步 lockfile。

## 假完成

不能用下面这些让当前任务看起来通过：删除或弱化已有必过检查；把必须项静默改成范围外；用「后续再补」替代当前必须能力；用业务层兜底掩盖未接通的入口。用户可以接受风险，但必须写进交付说明，不能包装成已验证完成。

结束时报告实际改动路径、验证结果和具体阻断。
